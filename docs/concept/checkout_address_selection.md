# Концепт: Выбор варианта доставки (Мои варианты)

## Описание функциональности
В форме чекаута (рядом с заголовком секции **«Доставка»**) отображается ссылка **«Мои варианты»**. При клике по ссылке открывается модальное окно со списком из 5 последних использованных **сценариев доставки** авторизованного пользователя. Каждый сценарий — это уникальная комбинация: адрес + тип доставки + тариф/ПВЗ. При выборе одного из вариантов данные подставляются в форму оформления заказа, после чего ядро Shop-Script автоматически пересчитывает доступность и стоимость доставки.

> **Концептуальный сдвиг:** Это не «список адресов», а «список сценариев доставки». Один физический адрес может иметь несколько вариантов (Курьер СДЭК, Почта России, ПВЗ Boxberry) — и каждый из них будет отдельной строкой в списке.

---

## 1. Какие поля будут подставляться?

При выборе варианта из модального окна происходит подстановка **всего сценария доставки** целиком:

1. **Поля адреса (регион, город, индекс, улица и т.д.):** Полный физический адрес доставки.
2. **Тип доставки (`shipping_id`):** Курьер, Самовывоз, Почта и т.д.
3. **Тариф/ПВЗ (`shipping_rate_id`):** Конкретный пункт выдачи или тариф (Стандарт/Экспресс).

> **Важно:** Поля других секций (контактные данные покупателя, секция оплаты, комментарий к заказу) **не затрагиваются**, **не перерасчитываются** и **не очищаются**. Смена варианта доставки влияет только на блок доставки.

**Итог:** Подставляется адрес + тип доставки + тариф, после чего ядро Shop-Script перерисовывает секцию доставки.

---

## 2. Логика реализации (AJAX + `waOrder` Reload)

Работа через DOM-инпуты формы (поиск по селекторам и вызов `.val()`) может быть нестабильной, так как кастомные темы Shop-Script часто меняют верстку, селекторы или логику работы событий. Мы также хотим избежать жесткой перезагрузки страницы `window.location.reload()`, если есть нативные инструменты ядра.

Вместо этого мы применим надежный подход: **подмена данных в сессии на бэкенде + перезагрузка формы через API `waOrder`.**

### Фронтенд (JS - `ParamsChoiceManager.js`):
1. **Передача данных в модалку:** Экшен `shopPrefillPluginFrontendParamsChoice.action.php` отдает список вариантов. На каждый элемент `<button>` или ссылку в списке нужно повесить data-атрибуты с необходимыми параметрами или полный JSON варианта.
2. **Перехват клика:** В `ParamsChoiceManager.js` слушаем выбор варианта.
3. **AJAX-запрос на бэкенд:** Извлекаем данные выбранного варианта и отправляем фоновый POST-запрос на наш новый контроллер в плагине (например, `shopPrefillPluginFrontendApplyDelivery.controller.php`), передавая ему выбранный `order_id`.
4. **Перерисовка формы (через API):** Дождавшись успешного ответа `{status: 'ok'}`, мы вызываем команду обновления чекаута через глобальный объект Shop-Script:
   ```javascript
   if (window.waOrder && window.waOrder.form) {
       window.waOrder.form.update({ reload: true });
   }
   ```
   *Параметр `reload: true` заставляет ядро Shop-Script (`waOrder`) принудительно перерисовать блоки доставки/оплаты, подтянув новые данные напрямую из сессии на сервере.*

### Бэкенд (PHP) - Элегантная логика переиспользования:

1. **Новый метод в провайдере хранилища:** 
   Метод применяет полный сценарий доставки — **`applyDeliveryAddress`**.
   ```php
   public function applyDeliveryAddress(shopPrefillPluginFillParams $fill_params): void
   {
       $checkout_params = $this->getCheckoutParams() ?: [];
       $final_params = [];
       
       // Обновляем физический адрес, регион и выбранный способ доставки (ПВЗ, Курьер и т.д.)
       $this->prepareRegionSectionParams($fill_params, $final_params, null);
       $this->prepareDetailsSectionParams($fill_params, $final_params, null);
       $this->prepareShippingSectionParams($fill_params, $final_params, null);
       
       $merged = shopPrefillPluginHelper::deepMergeArrays($checkout_params, $final_params);
       
       $this->setCheckoutParams($merged);
       $this->saveSnapshot($merged);
   }
   ```

2. **Новый контроллер (`shopPrefillPluginFrontendApplyDelivery.controller.php`):**
   Его задача становится предельно минималистичной — просто связать два готовых провайдера:
   ```php
   $order_id = waRequest::post('order_id', null, waRequest::TYPE_INT);
   
   // 1. Получаем готовый объект параметров
   $fill_params = shopPrefillPlugin::getInstance()
       ->getFillParamsProvider()
       ->getFillParams($order_id);
       
   // 2. Делегируем провайдеру сессии обновление (он сам обновит shop/checkout и shop/prefill_snapshot)
   shopPrefillPlugin::getInstance()
       ->getSessionStorageProvider()
       ->applyDeliveryAddress($fill_params);
   ```

3. **Ответ:** Отправляем в JS JSON `{"status": "ok"}`.

### 3. Все ли мы учли? (Граничные случаи логики)

**Установка способа доставки (`shipping_id`)**
Суть функции «Мои варианты» — быстрый выбор готового сценария: «домой курьером», «самовывоз из ПВЗ на Таганской», «почтой в пятницу». Поэтому метод `$this->prepareShippingSectionParams()` **обязательно** вызывается.

*А что будет, если старый способ доставки больше не существует или отключен администратором?*
Ничего страшного не произойдет. Ядро Shop-Script 9 (`waOrder`) при релоаде формы и перерасчете блоков проверяет доступность переданного `shipping_id`. Если метод доставки недоступен для выбранного региона (или вообще удален), Shop-Script плавно сбросит этот выбор и автоматически отрендерит список заново, выбрав дефолтный или первый доступный вариант.

Делегирование проверки актуальности тарифов нативному ядру Shop-Script — это самое правильное и стабильное решение!

## 3. Удаление варианта из списка

**Стоит ли реализовывать?**
На старте (для MVP) реализовывать удаление **не рекомендуется** по ряду причин:
* **Происхождение данных:** Варианты берутся из реальных заказов в БД. Удаление — это скорее скрытие, а не физическое удаление.
* **Сложность UI/UX:** Добавляется потребность в диалогах подтверждения («Точно удалить?»).
* **Крайне редкий сценарий в чекауте:** В процессе чекаута клиент хочет быстро оформить заказ, а не заниматься наведением порядка. Если в списке есть неактуальный вариант — клиент просто выберет нужный.

*Рекомендация:* На данном этапе стоит отказаться от функции удаления или сделать визуальное скрытие (только во фронтенде через Cookies/Local Storage) без реального удаления из базы данных заказа/контакта.

## 4. Что еще упущено? (Дополнительные пункты для обдумывания)

1. **Источники данных (Откуда берем 5 вариантов?):**
   - Функция доступна **исключительно для авторизованных пользователей**.
   - Для *неавторизованных* сценарий отключен. Ссылка «Мои варианты» выводиться не будет, и доступ к прошлым заказам предоставляться не будет ни при каких условиях из соображений безопасности и конфиденциальности.
2. **Дедупликация (Уникальность сценариев):**
   - Уникальность определяется по всем полям `shipping_*`: адрес + `shipping_id` + `shipping_rate_id`. Два одинаковых курьерских заказа на один адрес — это дубль. Но СДЭК и Почта на один адрес — это **два разных варианта** и оба должны отображаться. Текущая реализация через `removeDuplicateSubArrays + serialize()` уже работает корректно.
   - Что стоит улучшить: нормализация строк (`trim()` + `mb_strtolower()`) для полей `city`, `street`, `zip` перед сравнением, чтобы «Москва» и «москва» считались одним сценарием.
3. **Форматирование варианта для отображения:**
   - Вывод в модальном окне должен осуществляться через общий кастомный Smarty-шаблон (отдельный `.html` файл в плагине). Главным в карточке является **тип доставки** (Курьер / Самовывоз / Почта), вторичным — адрес. Например: `🚚 СДЭК Экспресс — г. Москва, ул. Ленина, 5`.
4. **Сценарий пустого списка:**
   - Если у пользователя нет прошлых заказов (новый клиент) или нет вариантов кроме текущего — ссылку «Мои варианты» в UI отображать **не нужно**. Бэкенд должен передавать флаг `has_saved_delivery_variants = true/false` в шаблон формы.
5. **Безопасность и приватность:**
   - Как указано выше, фича активируется только при условии `$wa->user()->isAuth() == true`. Любой попытавшийся запросить варианты через AJAX без сессии авторизованного пользователя получит отказ. Это самая надежная защита от утечки данных.
6. **Выделение «Текущего» варианта:**
   
   Текущий вариант определяется путём сравнения данных **каждого элемента коллекции** с тем, что сейчас лежит в сессии `shop/checkout`. Сравнение должно охватывать весь сценарий целиком — адрес + тип + тариф — ровно так же, как это делает дедупликация (`removeDuplicateSubArrays` сравнивает все поля с префиксом `shipping_`, включая `shipping_address.*`).

   **Реализация в `shopPrefillPluginFrontendParamsChoice.action.php`:**
   ```php
   // Получаем текущее состояние сессии и парсим его в FillParams
   $checkout_params = $instance->getSessionStorageProvider()->getCheckoutParams() ?: [];
   $current = $instance->getFillParamsProvider()->getFillParamsByCheckoutParams($checkout_params);

   foreach ($fill_params_array as &$item) {
       $item['is_current'] =
           $item['country']          === $current->getCountry()         &&
           $item['city']             === $current->getCity()            &&
           $item['street']           === $current->getStreet()          &&
           $item['shipping_type_id'] ==  $current->getShippingTypeId() &&
           $item['shipping_rate_id'] === $current->getShippingVariantId();
   }
   unset($item);
   ```

   **Визуальное поведение в шаблоне Smarty:**
   - Карточка с `is_current = true` получает CSS-класс `is-active` (например, обводка или галочка).
   - Кнопка «Выбрать» для активного варианта скрывается или меняется на «Выбран» (disabled).
   - Список полностью **не сокращается** — текущий вариант остаётся в списке, просто выделен визуально, чтобы пользователь понимал контекст.

## 5. Анализ плана: что нужно исправить перед реализацией

### Общее впечатление

Концепт **хорошо продуман стратегически**: правильный выбор паттерна «сессия на бэкенде + `waOrder` reload», верное разграничение ответственности провайдеров. Архитектура соответствует существующему коду плагина и максимально переиспользует готовую инфраструктуру. Однако при детальном анализе кода есть ряд **реальных проблем**, которые необходимо устранить до начала реализации.

---

### ✅ Что сделано правильно

1. **Стратегия «сессия + `waOrder.reload`»** — отказ от DOM-манипуляций через `.val()` и `window.location.reload()` — максимально стабильное и темо-независимое решение.
2. **Переиспользование инфраструктуры** — `getFillParams(order_id)`, `getFillParamsCollection()`, `deepMergeArrays()`, `removeDuplicateSubArrays()` всё уже есть. Контроллер получается из ~5 строк.
3. **Делегирование валидации доставки ядру** — Shop-Script 9 сам проверяет актуальность `shipping_id` при релоаде. Не нужно проверять самостоятельно.
4. **Авторизационный барьер** — ограничение по `isAuth()` корректно. Неавторизованный пользователь не получит доступ к вариантам.

---

### ❌ Критические проблемы

#### 1. IDOR — нет проверки владения заказом

В планируемом контроллере:
```php
$order_id = waRequest::post('order_id', null, waRequest::TYPE_INT);
$fill_params = shopPrefillPlugin::getInstance()->getFillParamsProvider()->getFillParams($order_id);
```

В `getFillParamsForAuthorized($order_id)` нет проверки, что переданный `order_id` принадлежит **текущему** пользователю. Авторизованный пользователь А может подставить `order_id` заказа пользователя Б и получить его данные доставки. Это **IDOR (Insecure Direct Object Reference)**.

Метод `getContactIdFromOrder()` уже есть в `FillParamsProvider` — необходимо добавить проверку в `getFillParamsForAuthorized`:

```php
if ($order_id) {
    // Проверяем что заказ принадлежит текущему пользователю
    $order_contact_id = $this->getOrderProvider()->getContactIdFromOrder($order_id);
    if ($order_contact_id && $order_contact_id === $contact_id) {
        $order_params = $this->getOrderProvider()->getOrderParams($order_id);
        if ($order_params) {
            return $this->getFillParamsByOrderParams($order_params, $order_id);
        }
    }
}
```

#### 2. Неправильное сравнение `shipping_rate_id` в `is_current`

В плане для определения текущего варианта:
```php
$item['shipping_rate_id'] === $current->getShippingVariantId();
```

`$item` — это результат `FillParams::toArray()` = `get_object_vars()`. Поле `shipping_rate_id` в объекте `FillParams` хранит **только суффикс** (например, `"cdek-express"`). В то же время `getShippingVariantId()` возвращает составной ключ `"{shipping_id}.{shipping_rate_id}"` (например, `"5.cdek-express"`). Сравнение **всегда будет `false`** — ни один вариант никогда не получит `is_current = true`.

Правильное сравнение:
```php
$item['shipping_rate_id'] === $current->getShippingRateId(); // "cdek-express" === "cdek-express"
```

Также в сравнении стоит добавить `region` и `zip` — без них город «Пушкин» в Московской и Ленинградской областях будет считаться одним сценарием.

---

### ⚠️ Важные замечания

#### 3. Рассинхрон сессии при ошибке `setCheckoutParams`

В методе `setCheckoutParams` исключение ловится внутри и возвращается `false`. Если запись в сессию не удалась, а `saveSnapshot` вызовется следующей строкой — возникнет **рассинхрон** между `shop/checkout` и `shop/prefill_snapshot`. Необходима проверка:

```php
if ($this->setCheckoutParams($merged)) {
    $this->saveSnapshot($merged);
}
```

#### 4. Нет fallback в JS при недоступности `waOrder.form`

В кастомных темах Shop-Script `window.waOrder.form` может быть недоступен (старая JS-сборка, кастомная тема). В плане нет обработки этого случая. Минимально необходимо:

```javascript
$.post(url, data)
  .done(function(response) {
    if (response.status === 'ok') {
      if (window.waOrder && window.waOrder.form) {
        window.waOrder.form.update({ reload: true });
      } else {
        window.location.reload(); // Fallback для нестандартных тем
      }
    } else {
      // Показать сообщение об ошибке пользователю
    }
  })
  .fail(function() {
    // Обработка сетевой ошибки
  });
```

#### 5. Не описаны обязательные детали реализации

- **Где рендерится ссылка «Мои варианты»?** — через какой хук (`checkoutRenderShipping` или `checkoutRenderDetails`) подключается HTML-блок со ссылкой?
- **Регистрация нового контроллера** — в Webasyst фронтенд-контроллеры плагина должны быть зарегистрированы в `routing.php`.
- **UX в момент загрузки** — кнопка «Выбрать» должна быть задизейблена или иметь спиннер, пока идёт AJAX-запрос + `waOrder.reload`.
- **Закрытие модального окна** после успешного выбора — автоматически или нет?

#### 6. Нет CSRF-защиты для нового контроллера

`waJsonController` в Webasyst **не имеет автоматической CSRF-защиты** (в отличие от бэкенда). Для POST-запроса, меняющего сессионные данные, рекомендуется добавить проверку `_csrf` токена или как минимум заголовка `X-Requested-With: XMLHttpRequest`.

---

### 🟠 Мелкие замечания

- **Мёртвый код в `ParamsChoiceAction`**: `$tt = $instance->getPluginsProvider()->getShippingMethods()` — переменная нигде не используется и не передаётся в шаблон. Убрать перед реализацией.
- **Лимит `5` захардкожен** в `toArray(false, 5)` — лучше вынести в константу плагина или настройку витрины.
- **Нормализация строк для дедупликации**: упомянутая `trim() + mb_strtolower()` нормализация должна применяться при **установке значений** в `FillParams` (сеттеры `setCity`, `setStreet`, `setZip`), а не в хелпере — тогда она автоматически покроет и дедупликацию, и сравнение `is_current`.
