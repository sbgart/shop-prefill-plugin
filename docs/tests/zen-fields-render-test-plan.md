# Zen Mode — адекватность отображения полей сводки на витрине

**Статус:** план, не выполнялся. Отдельный документ, **не входит** в реестр ФО `TEST-PLAN.md` — не
имеет критериев выпуска и не блокирует релиз. Цель — проверить, что каждое из 35 полей Zen-сводки
(`shopPrefillPluginZenData::getAvailableFields()`) выглядит на живой витрине адекватно источнику
(в т.ч. как ядро показывает те же данные в развёрнутом виде), а не только структурно корректно.

**Повод:** реальный магазин `santeh-city66.ru` (Shop-Script, ядровый виджет самовывоза, не наш
плагин) в развёрнутом виде показывает часы работы, адрес, «Как добраться» и фотогалерею пункта
выдачи — см. [external-sites-survey.md](external-sites-survey.md). Вопрос: показывает ли **наш**
плагин те же данные так же адекватно, когда сворачивает такую секцию в Zen-карточку. Предметно это
никогда не проверялось.

## 1. Ключевая находка, определяющая приоритет (уже подтверждена в исходниках)

**G3 — Zen-карточка технически не может унаследовать CSS ядра для фото/расписания.** Гипотеза, а не
факт: подтверждена статически (grep CSS + чтение шаблона), не подтверждена в браузере. Первый шаг
исполнения (§7, шаг 0) обязан подтвердить/опровергнуть её за 2 минуты в DevTools — вся
приоритизация документа строится вокруг результата.

- Ядро (`wa-apps/shop/css/frontend/order/form.css`) стилизует галерею и расписание строго через
  4–5-уровневый селектор-предок:
  ```css
  .wa-order-form-wrapper .wa-step-details-section .wa-details-rates-section .wa-photos-section .wa-photos-list .wa-photo-wrapper { width: calc(25% - 15px); ... }
  .wa-order-form-wrapper .wa-step-details-section .wa-details-rates-section .wa-schedule-wrapper .wa-days-wrapper .wa-day-wrapper { display: table; table-layout: fixed; ... }
  ```
- Плагин (`shopPrefillPluginZenData::buildPhotosHtml()` / `shopPrefillCheckoutState::renderPickupScheduleDays()`)
  генерирует те же самые классы (`.wa-photos-section`, `.wa-photo-wrapper`, `.wa-day-wrapper`),
  явно рассчитывая переиспользовать CSS и JS ядра (лайтбокс `js-show-photo`, скролл `js-scroll-prev/next`).
- Но сама Zen-карточка (`templates/zenmode/CollapseBlock.html`) — плоская структура
  `.prefill-zen-collapse-block > .prefill-zen-content > .prefill-zen-summary`, без предков
  `.wa-step-details-section`/`.wa-details-rates-section`/`.wa-schedule-wrapper`.
- **Вывод (гипотеза):** ни одно из процитированных правил, скорее всего, не применяется внутри
  свёрнутой карточки — фото откатываются на голый inline-block без размеров, расписание — на
  `display: table` без `table-layout: fixed` (может выглядеть иначе, но не обязательно ломается).
  JS-инициализация лайтбокса/скролла (`Details.prototype.initPhotos()`, `shop/js/frontend/order/form.js`)
  тоже не проверялась — плагин не вызывает её сам.

Дополнительно подтверждено (`shopPrefillPluginSettingsTemplatePreviewController::handle()`):
админский предпросмотр шаблона **всегда** рендерит на фейковых данных `ZenData::getSampleData()`
(строка `$data = shopPrefillPluginZenData::getSampleData($group);`), никогда на реальном состоянии
чекаута. Значит, существующий K-08 (превью совпадает с витриной) по конструкции проверяет только
согласованность экранирования между превью и рендером — не может подтвердить адекватность вида
реальных фото/расписания в реальном DOM. Нужен обязательно живой чекаут (§7).

## 2. Термины и опорные факты

- Группа → секция (`TEMPLATE_EDITOR_FIELD_GROUPS`): `customer` → шаг `auth`, `delivery` → шаги
  `region`+`shipping`+`details`, `payment` → шаг `payment`. `confirm` не участвует (Z6).
- 4 группы полей (`getAvailableFields()['group']`): `contact` (доступна в customer/delivery/payment),
  `delivery`, `address` (обе — только в группе `delivery`), `payment` (только в группе `payment`).
- 35 полей всего: contact — 8, delivery — 16, address — 7, payment — 4 (см. таблицы §5).
- 6 HTML-полей (`is_html`, не экранируются, `escapeValue()` их не трогает): `service_agreement_hint`,
  `shipping_rate`, `delivery_description`, `delivery_schedule`, `delivery_photos_html`,
  `payment_description`. Остальные 29 — экранируются `htmlspecialchars(ENT_QUOTES)` в
  `extractSummaryData()`/`getSampleData()` (Z7).
- 4 array-поля (`is_array`): `contact_custom`, `shipping_custom`, `address_custom`, `payment_custom`
  — ассоциативные массивы `[ключ => значение]`, требуют `{foreach}`/`snippet_loop` в шаблоне, не
  выводятся дефолтными шаблонами вовсе.
- Дефолтные `summary_template` (`lib/config/storefront.settings.php`) используют лишь малую часть
  каталога:
  - `customer`: `{if $company}{$company} • {/if}{$firstname} {$lastname} • {$phone}`
  - `delivery`: заголовок `{$delivery_plugin}`, `{$shipping_name}` • `{$shipping_rate}`, затем адрес
    (`{$delivery_pickup_address}` либо `{$city}, {$street}, {$building}, {$apartment}`), затем
    `{$delivery_est_delivery}`
  - `payment`: заголовок `{$payment_name}`, затем `{$payment_description}`
  - Ни один дефолтный шаблон не выводит `delivery_schedule`, `delivery_photos_html`,
    `delivery_way`, `delivery_storage_days` и ни один из 4 `*_custom` — эти поля видны только через
    **кастомный** шаблон группы (редактор K-07, `custom_templates[$id]`), который должен собрать
    исполнитель этого плана (§6 шаг 4).
- **Ключевое ограничение методологии:** админ-превью (`SettingsTemplatePreviewController`) всегда на
  `getSampleData()` (фейк) — не годится для проверки визуальной адекватности фото/расписания в
  реальном DOM. Единственный источник правды — живой `/order/` с реальными данными (§7).

## 4. En_US: делегирование, не дублирование

`zen-field-examples.md` уже фиксирует, что `zen.delivery.type.pickup/courier/post` — пустой
`msgstr ""` в `en_US.po`, то есть `{$delivery_type}` на английской локали рендерится пустой строкой.
В матрице §5 это одна строка у `delivery_type` со ссылкой на находку, а не повторный прогон
локализационного аудита. Единственное, что стоит проверить именно здесь (не там) — как пустая
строка выглядит **в контексте** кастомного шаблона на витрине (лишний пробел/разделитель вокруг
пустого значения), потому что дефолтный шаблон `$delivery_type` вообще не использует.

| `payment_description` | **HTML** | Описание способа оплаты (контент администратора, используется в дефолтном шаблоне) рендерится как задумано | Способ оплаты с заполненным описанием | средний — та же категория риска, что `delivery_description` |
| `payment_custom` | array | Пары `ключ: значение` читаемы (пример — ИНН) | Доп. поле оплаты (юрлицо/ИНН) через настройки | средний — не проверялось |

## 7. Как выполнять

- **Шаг 0 (первым, ~2 минуты).** Подтвердить/опровергнуть G3 в DevTools: временно вставить
  `{$delivery_schedule}` в шаблон группы `delivery` (дефолтный шаблон его не использует), сохранить,
  открыть `/order/` с фикстурой СДЭК ПВЗ, свернуть карточку, открыть DevTools → Computed на
  `.wa-day-wrapper` внутри `.prefill-zen-summary` → проверить, применилось ли правило
  `display: table; table-layout: fixed` из §1. Результат определяет приоритет всего остального:
  подтвердилось — G3 сразу заводится в `docs/bugs/`, остальные HTML-поля (`delivery_photos_html` в
  первую очередь) проверяются с ожиданием того же дефекта; опроверглось — гипотеза закрывается одной
  строкой в журнале прогонов (§8), приоритет полей выравнивается по общему риску.
- **Шаг 1.** Проверить факт наличия данных `delivery_photos`/`delivery_storage_days`/`delivery_way`/
  `shipping_custom` на стенде: временно дописать диагностику
  `{$delivery_photos|@count} / {$delivery_storage_days} / {$delivery_way}` в живой `summary_template`
  группы `delivery`, посмотреть на витрине с разными способами доставки, вернуть шаблон обратно. Если
  ни один активный на стенде плагин доставки не отдаёт фото — зафиксировать в журнале (§8) как
  ⬜ «нет фикстуры на стенде», не изобретать синтетические данные в обход реального `custom_data`.
- **Debug.** Редакторы шаблонов — backend-экшены (`isAdmin('shop')`), от `waSystemConfig::isDebug()`
  не зависят. Рендер витрины тоже не зависит от debug (debug влияет только на J-08/бандлы и
  debug-панель, `TEST-PLAN.md` ФО-12). Держать debug выключенным, как в прогоне
  `runs/1.0.0-2026-08-28.md`.
- **Фикстуры для `*_custom`.** Доп. поля создаются через Настройки магазина → Оформление заказа
  (это функциональность ядра Shop-Script, не код плагина, B1) — завести, использовать, вернуть/удалить
  по той же дисциплине «что трогалось и возвращено», что применялась в прогоне 28.08.2026.
- **Ширины экрана.** Тестировать и на мобильной ширине DevTools (375/390px), и на обычной desktop —
  тема `default` не резиновая на 100% ширины, инфоблоки ядра рассчитаны на фиксированную ширину шага.
