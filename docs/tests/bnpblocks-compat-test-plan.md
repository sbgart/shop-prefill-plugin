# `bnpblocks` («Свои блоки доставки») — совместимость с Zen Mode

**Статус:** ✅ **закрыто 09.09.2026 разбором кода** — коллизии нет ни в одном состоянии.
Вживую в браузере не проверялось: лицензия на стенде истекла раньше, чем дошли до прогона (см. §0.1).
См. «Проверено 09.09.2026» в конце файла. Закрывает S-05 в [TEST-PLAN.md](TEST-PLAN.md).

**Повод:** в [snapshot-removal-and-html-ownership.md:152](../plans/snapshot-removal-and-html-ownership.md)
названы два плагина студии bodysite.ru, с которыми предстояло проверить совместимость: «SEO-регионы»
(уже интегрирован, S-04 ✅) и «Информация о доставке и оплате». На стенде 09.09.2026 установлен
`bnpblocks` — «Свои блоки доставки» (`wa-apps/shop/plugins/bnpblocks`, vendor 986052, hooks
`checkout_render_shipping` / `checkout_render_details` / `checkout_before_details`) — тот самый второй
плагин по смыслу: он группирует стандартные способы доставки в собственные именованные блоки с
логотипом и опциями отображения. Лицензия куплена на 1 месяц — см. §0 и §4 про истечение.

**Что не делаем.** Если лицензия `bnpblocks` истечёт до конца прогона — не патчим `checkLicense()`
ни в ядре, ни в самом плагине, чтобы обойти проверку. Это платный сторонний продукт, обход его
лицензии не рассматривается как решение независимо от того, что стенд демонстрационный. Путь на
этот случай — §4 (фикстура вместо живого плагина).

## 0. Активация — проверить первым шагом (5 минут)

Хук `checkoutRenderShippingHook()` и `workupType()` внутри плагина проверяют
`themeFileExists() === 1`: в активной теме должен лежать файл `order.shipping.html` с описанием
`'BNP Блоки доставки в оформлении'` (`shopBnpblocksPlugin.class.php:30-46`). У темы `default` такой
файл уже есть и ссылается на `$bnp_types_list` — интеграция с темой, похоже, сделана заранее. У темы
`kmfast` (стояла на стенде 08.09.2026, возвращена на `default`) файла нет вовсе — на ней хук молчит
всегда, независимо от лицензии. **Прогонять этот план только на `default`.**

Отдельно от темы, `checkoutRenderShippingHook()` зовёт `installerHelper::checkLicense('shop/plugins/bnpblocks')`
(строки 61-73) — если лицензия не отвечает или просрочена, `$has = false` и хук молча возвращает
`void`, ничего не меняя. Внешне это неотличимо от «не настроено ни одного блока» (та же ранняя
ветка `return`, если `$blocks` пуст). Разделить эти два случая перед тем, как делать выводы:
если после создания блока в бэкенде (§1) в `$params['vars']` на витрине по-прежнему нет
`bnp_types_list` — смотреть, отвечает ли `checkLicense()`, а не считать план проваленным.

## 1. Настроить один блок

В бэкенде плагина (`?action=settings#/bnpblocks/`) создать блок типа `pickup`, привязать к способу
доставки id 37 (`sd`, «Пункт выдачи заказов») — та же фикстура с адресом/координатами/расписанием/
фото, что уже настроена для [zen-photos-css-scope-broken.md](../bugs/zen-photos-css-scope-broken.md).
Один прогон закрывает два долга сразу. Включить в блоке опцию «Скрыть срок» ИЛИ «Скрыть стоимость» —
без неё сценарий 1 ниже не воспроизводится вовсе (см. §2).

## 2. Разбор коллизии — единственная находка, подтверждённая чтением кода (не гипотеза о рисках вообще, а конкретный механизм)

Три факта, каждый подтверждён построчно, вместе дающие эффект:

1. Ядро оборачивает **каждый** вывод хука `checkout_render_details` в свой собственный
   `.wa-plugin-hook`, независимо от того, какой плагин его вернул:
   ```smarty
   {foreach $event_hook.details as $_}
       <div class="wa-plugin-hook">{$_}</div>
   {/foreach}
   ```
   (`wa-apps/shop/templates/actions/frontend/order/form/details.html:339-341`)
2. Наш CSS сворачивания прячет всё в секции, КРОМЕ `.wa-plugin-hook` — не различая, чей это hook:
   ```css
   .wa-step-details-section .wa-section-body form > *:not(.wa-plugin-hook) { display: none !important; }
   ```
   (`shopPrefillPluginZenMode::generateGroupStyles()`, `lib/classes/zenmode/shopPrefillPluginZenMode.class.php:455`)
3. `bnpblocks::checkoutRenderDetails()` (`shopBnpblocksPlugin.class.php:196-227`) возвращает непустой
   HTML ровно когда одновременно: выбранный `shipping[type_id]` начинается с `bnp_`, блок найден по
   id из этого type_id, и у блока включена хотя бы одна из опций `hide_est`/`hide_cost`.

**Гипотеза (не факт — не проверялась в браузере):** при выполнении условия из пункта 3 и свёрнутой
карточке «Доставка» в DOM окажутся **два** `.wa-plugin-hook` рядом — наш (Zen-сводка) и bnpblocks
(текст об урезанном отображении) — оба видимые, оба пережившие правило `:not(.wa-plugin-hook)`.
Сценарий воспроизведения — §3, сценарий 1.

Остальные два хука `bnpblocks` коллизии не создают — проверено чтением обоих кодовых баз, не
предположением:

| Хук `bnpblocks` | Что мутирует | Наш код читает то же? |
|---|---|---|
| `checkoutRenderShippingHook` (`checkout_render_shipping`, возвращает `void`) | `$params['vars']['shipping']['types']` — только группировка табов для отображения, id вида `bnp_pickup_3` | Наш `handleCheckoutRenderShipping()` зовёт только `renderSectionErrorsAndDebug($state, ...)`, `vars.shipping.types` не читает вовсе |
| `checkoutBeforeDetails` (`checkout_before_details`) | `$params['data']['shipping']['is_free_shipping'] = true`, если сработало правило магазина | Ни один геттер `shopPrefillCheckoutState` это поле не читает |

Идентичность варианта (`getShippingType()`, `getShippingVariantId()`, `getShippingInstanceId()` в
`shopPrefillCheckoutState`) читается из `data.shipping.selected_variant` / `vars.shipping.shipping_rate`
/ `data.shipping.id` — ни один из трёх геттеров `bnpblocks` в эти ключи не пишет, он только
перекладывает уже существующий объект варианта внутрь своей группы для отображения
(`$newBlocks[$mappingBlock]['variants'][$variantId] = $variant;`, строка 122), не трогая сам объект.
По коду коллизии здесь не ожидается — сценарии 3-4 ниже нужны как подтверждение, а не как охота на
гипотетический риск.

## 3. Сценарии

1. **[Главный]** Создать bnp-блок с `hide_est` или `hide_cost` (§1), выбрать его на чекауте, свернуть
   карточку «Доставка» → DevTools: сколько `.wa-plugin-hook` внутри `#wa-step-details-section`,
   `getComputedStyle().display` у каждого. Ожидание по гипотезе §2 — два элемента, оба `block`.
2. **[Контроль]** Тот же bnp-блок, но БЕЗ `hide_est`/`hide_cost` → по коду `checkoutRenderDetails()`
   должен вернуть `''` → в DOM должен остаться только один `.wa-plugin-hook` (наш). Если это не так —
   §2 разобран неверно, коллизия не в том месте.
3. Оформить заказ через bnp-сгруппированный вариант → Zen-сводка доставки (имя тарифа, тип, сумма)
   должна быть идентична обычному варианту без группировки.
4. Повторный визит тем же контактом → диалог «Мои варианты» находит этот заказ и подсвечивает
   правильный вариант.
5. Прогонять 1-4 только на теме `default` (см. §0) — на `kmfast` `bnpblocks` не активируется, тест
   ничего не покажет.

## 4. Если лицензия истекла до прогона

Не патчим `checkLicense()` (см. преамбулу). Вместо живого плагина — фикстура без единого вызова
стороннего кода: файл шаблона `templates/hooks/checkout_render_details.html` внутри `bnpblocks`
читается статически (лицензия не нужна, чтобы прочитать файл с диска), по нему вручную собирается
HTML, который вернул бы `checkoutRenderDetails()` при `hide_est=1`, и вставляется вторым
`.wa-plugin-hook`-сиблингом в живую карточку тем же приёмом, каким проверялись фото 08.09.2026
(`javascript_tool` + `appendChild` в `#wa-step-details-section .prefill-zen-summary`'s родитель).
Так сценарий 1 проверяется без единого запущенного вызова платного кода.

## 5. Уборка

- Тестовый bnp-блок — удалить или деактивировать после прогона.
- Настройки способа доставки `sd` (id 37) — общая фикстура с [zen-photos-css-scope-broken.md](../bugs/zen-photos-css-scope-broken.md),
  не удалять в рамках этого прогона, она нужна и там.
- Тема на `wa-dev.loc/*` должна остаться `default`.

## Проверено 09.09.2026

### 0.1 Лицензия истекла на самом стенде

Открыл карточку плагина в маркетплейсе (`?action=plugins#/` → «Все плагины» → поиск «Свои блоки
доставки»): `✗ Plugin's license is expired. To continue using the plugin, extend its license.`
Продлевать (покупка) не рассматривается — вне контура работы, да и не требуется для вывода ниже.

Практическое следствие для §1: плагин при этом **не появляется вовсе** в левом сайдбаре
«Установлены» на `?action=plugins#/`, и прямой hash-роут `#/bnpblocks` не резолвится (SPA
откатывается на первый плагин списка). То есть настроить блок через штатный бэкенд на этом стенде
нельзя вообще, независимо от решения про фикстуру — SPA прячет истёкшие по лицензии плагины из
собственного роутинга, это не специфика прав или бага, а нормальное поведение инсталлятора.

### Разбор коллизии кодом — гипотеза §2 не подтвердилась

Не хватало одного файла в исходном разборе — Smarty-шаблона, который реально рендерит
`checkoutRenderDetails()`. Прочитан целиком:
`wa-apps/shop/plugins/bnpblocks/templates/hooks/checkout_render_details.html` — это **не блок
видимой разметки**, а голый `<script>`, который через jQuery ищет `.wa-delivery-price` и
`div:contains("Срок доставки")` внутри уже отрендеренной **ядром** секции доставки и вызывает на
них `.hide()`. Видимого контента (текста, изображений, карточек) хук вообще не возвращает.

Второй недостающий кусок — как `waEvent::runPlugins()` (`wa-system/event/waEvent.class.php:244`)
собирает результаты хуков: проверка `if ($plugin_result !== null)` — **пустая строка проходит эту
проверку** (`'' !== null` истинно), значит даже когда `checkoutRenderDetails()` возвращает `''`
(нет `hide_est`/`hide_cost` — контрольный сценарий §3.2), Smarty всё равно получает элемент массива
и оборачивает его в `<div class="wa-plugin-hook"></div>` — пустой, но структурно существующий.
Ожидание сценария 2 в §3 («в DOM останется только один `.wa-plugin-hook`») было неточным — их
будет два в обоих сценариях, просто второй либо пуст, либо содержит невидимый `<script>`.

Отсюда вывод по обоим сценариям §3.1/§3.2, без единого запуска платного кода (достаточно двух
файлов ядра/плагина, лицензия на их чтение не влияет):

- **Визуальной коллизии нет.** `<script>` не занимает места в потоке документа — второй
  `.wa-plugin-hook` в DOM есть, но пустой визуально что при `hide_est`/`hide_cost`, что без них.
  Гипотеза «два видимых блока рядом» не подтвердилась структурой самого хука bnpblocks —
  теоретический механизм (§2, пп. 1-2) реален для хуков, которые возвращают разметку, но у этого
  конкретного плагина на этом хуке разметки нет.
- **Функциональной коллизии тоже нет.** В свёрнутом состоянии карточки «Доставка» её содержимое уже
  скрыто нашим `display:none !important` — вызовы `.hide()` из скрипта bnpblocks находят те же
  элементы (уже невидимые) и не делают ничего лишнего, ошибок jQuery на пустой выборке не бывает. В
  развёрнутом состоянии наше CSS-правило вообще не генерируется (оно строится только для реально
  свёрнутой группы), то есть скрипт bnpblocks работает ровно так, как задуман автором, — Zen Mode в
  этот момент никак не вмешивается в разметку секции.

Два прежних хука (`checkout_render_shipping`, `checkout_before_details`) — коллизии не было и по
первому разбору (см. таблицу в §2), это не изменилось.

### Итог

Статическим разбором закрыты все три хука `bnpblocks`, коллизий с Zen Mode нет ни в одном. Сценарии
§3.3-§3.4 (сквозной заказ через bnp-группировку, подсветка в «Мои варианты») остаются формально не
прогнанными вживую — лицензия истекла и настроить блок через бэкенд на этом стенде физически нельзя
(см. §0.1), а собирать фикстуру ради них не имеет смысла: они лишь заново проверяют то, что уже
установлено чтением кода в §2 (ни один геттер идентичности варианта не читает поля, которые пишет
bnpblocks). План закрывается без живого прогона; переоткрыть, если лицензия появится снова и
захочется визуального подтверждения, а не только разбора кода.
