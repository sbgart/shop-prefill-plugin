# Кэш сводки Zen показывает данные предыдущей личности после смены гость↔авторизован в той же сессии

**Статус:** факт, не разобран.

## Воспроизведение (28.08.2026, прогон R, ФО-05)

1. Выйти из бэкенда (`?action=logout`) — сессия становится гостевой, но PHPSESSID **не меняется**
   (уже отмечено ранее в CLAUDE.md как грабли: логаут не создаёт новую сессию).
2. Гость оформляет заказ с доставкой в Москву, «Проспект Мира 1» (в этом прогоне — заказ #109,
   контакт 51, см. [TESTS.md ФО-04](../tests/TESTS.md)).
3. Заново войти в бэкенд под тем же браузером (`admin`) — та же сессия, теперь `user:1`.
4. Открыть `/order/` (товар в корзине, `/prefill/clear-storage` вызван перед этим).

**Ожидание:** карточка «Доставка» в свёрнутом виде показывает данные **текущей** личности
(контакт 1, история — Новосибирск, ул. Дзержинского/Брестская пр-кт).

**Факт:** свёрнутая карточка показывает **«Москва, Проспект Мира 1»** — адрес гостя из шага 2,
хотя контакт сменился на 1. Лог подтверждает: `Zen summary for 'delivery' rendered from cache`.

При этом сам **живой источник данных корректен**: разворачивание карточки («Изменить») показывает
правильные поля формы — регион «Новосибирская область», город «Новосибирск». Расхождение — только
в закэшированной сводке для свёрнутого вида, не в реальных данных формы/сессии.

`shop_customer` контакта 1 не пострадал (`last_order_id=106`, не тронут), заказ #109 корректно
привязан к контакту 51 — путаницы в БД нет, только в отображении кэша сводки.

## Не разбиралось

Какой ключ кэша сводки Zen используется (видимо, привязан к PHPSESSID, а не к личности/маркеру
источника) и почему он не инвалидируется при `Loading fill params for authorized user`, которая
в этот же момент отработала корректно.
