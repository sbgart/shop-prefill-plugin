# Диалог «Мои варианты»: подсветка активной карточки не появляется сразу после смены «Типы доставки»

**Статус:** Подтверждён вживую в браузере 20.08.2026.

## Симптом

После выбора адреса в диалоге «Мои варианты» и последующей смены **типа** доставки (вкладки «Курьер / Самовывоз / Почта») на тип, который однозначно соответствует одному из вариантов в истории, диалог при повторном открытии **не подсвечивает** совпадающую карточку — хотя выбранный сейчас способ доставки объективно совпадает с одним из вариантов в списке.

Стоит вызвать любой другой пересчёт чекаута (например, кликнуть «+» у товара в корзине) — при следующем открытии диалога подсветка корректно появляется на верной карточке, без каких-либо действий пользователя в самом диалоге.

## Воспроизведение (подтверждено)

Условие: сумма корзины ≥ 15000 ₽, чтобы у типа «Почта» остался ровно один вариант доставки (тогда переключение типа не порождает второй AJAX-запрос выбором варианта из открывшегося дропдауна).

1. Открыть диалог «Мои варианты», выбрать любую карточку, кроме почтовой (например, «СДЭК (Курьер)») — страница перезагружается, тип доставки «Курьер», вариант «Курьер».
2. Переключить «Типы доставки» на «Почта» (без открытия дропдауна «Варианты доставки» — там всего один вариант, и он подставляется автоматически).
3. Открыть диалог «Мои варианты» — **ни одна карточка не подсвечена**, хотя карточка «Почта России (Webasyst) (Посылка)» ей соответствует.
4. Вызвать любой пересчёт чекаута, не трогая доставку (клик «+» на количестве товара в корзине).
5. Открыть диалог «Мои варианты» повторно — карточка «Почта России (Webasyst) (Посылка)» подсвечена как активная.

Скриншоты шагов 3 и 5 (до/после пересчёта) — в этой сессии работы, не сохранены отдельно; воспроизводится стабильно.

## Где искать (гипотеза, не подтверждена по коду/сети)

Подсветка считается в [`shopPrefillPluginFrontendParamsChoiceAction::execute()`](../../lib/actions/frontend/shopPrefillPluginFrontendParamsChoice.action.php):

```php
$checkout_params = $instance->getSessionStorageProvider()->getCheckoutParams(); // shop/checkout из сессии
$current         = $instance->getFillParamsProvider()->getFillParamsByCheckoutParams($checkout_params);
...
$item_array['is_current'] = $item_obj->isSameDeliveryOption($current);
```

`getCheckoutParams()` читает сырой `shop/checkout` — это структура **ядра** Shop-Script (`waCheckout`), плагин её не пишет и не кэширует, только читает. Сравнение идёт по `shipping.type_id` + `shipping.variant_id` (см. `shopPrefillPluginFillParams::isSameDeliveryOption()` и `getFillParamsByCheckoutParams()` в [`shopPrefillPluginFillParamsProvider`](../../lib/classes/fillparams/shopPrefillPluginFillParamsProvider.class.php)).

При ручной проверке в браузере (шаг 2 выше): после смены типа на «Курьер» (тип с несколькими вариантами) дропдаун «Варианты доставки» остаётся **не выбранным** («Выберите вариант доставки») до отдельного клика пользователя — то есть само переключение типа не отправляет `variant_id` на сервер. Похоже, что при переключении типа core-JS чекаута шлёт в `/order/calculate/` только `shipping[type_id]`, а `shipping[variant_id]` в сессию `shop/checkout` не попадает, пока не случится следующий AJAX-запрос с уже выбранным (в т.ч. автоматически, если вариант единственный) значением из формы. До этого момента `getCheckoutParams()` отдаёт **устаревший `variant_id`** — от типа доставки, который был активен до переключения — и `isSameDeliveryOption()` закономерно не находит совпадения. Любой следующий пересчёт (не обязательно связанный с доставкой) отправляет полный снимок формы, включая уже актуальный `variant_id`, и подсветка появляется.

Это предположение по логам/коду и одному прогону в браузере, не подтверждено чтением фактического тела POST `/order/calculate/` (сетевые запросы не инспектировались на уровне payload). Прежде чем чинить — стоит проверить в DevTools → Network тело запроса `calculate` на шаге 2 (есть ли там `shipping[variant_id]` и какое значение) и содержимое `shop/checkout` в сессии до и после пересчёта на шаге 4.

## Возможные направления решения

Не проработаны — нужно сначала подтвердить гипотезу выше. Если она верна, варианты:
- в диалоге сравнивать не по сырому `shop/checkout`, а по значению, реально отображённому в DOM формы на момент открытия диалога (но это ломает архитектуру: `FrontendParamsChoice` — серверный экшен, без доступа к DOM);
- смотреть, не может ли плагин на своей стороне (например, в JS, который уже слушает клики по вкладкам типа доставки) форсировать досылку актуального `variant_id` в том же `calculate`-запросе, если он единственный.
