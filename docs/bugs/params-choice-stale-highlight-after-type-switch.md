# Диалог «Мои варианты»: подсветка активной карточки не появляется сразу после смены «Типы доставки»

**Статус:** Подтверждён вживую в браузере 20.08.2026. ⚠️ Блокирует релиз плана [delivery-variant-identity.md](../plans/delivery-variant-identity.md) — см. «Симптом меняется» ниже.

## Симптом меняется 23.08.2026 — сравнение по типу больше недоступно

`shopPrefillPluginFillParams::$shipping_params` (см. «Где искать» ниже) до 23.08.2026 включал `shipping_type_id` — именно несовпадение типа в окне рассинхрона давало сегодняшний симптом «ничего не подсвечено». План [delivery-variant-identity.md](../plans/delivery-variant-identity.md) убрал `shipping_type_id` из плагина целиком: `isSameDeliveryOption()` сравнивает только `shipping_id`+`shipping_rate_id`. В том же окне (новый `type_id`, старый `variant_id` в сессии) эти поля **совпадают** с ранее выбранным вариантом — вместо «ничего не подсвечено» подсветится **карточка, с которой покупатель только что ушёл**. Тихое «не знаю» (соответствует B2a) превращается в уверенную неправду.

Не регресс данной задачи как таковой — восстановленный симптом был случайно правильным побочным эффектом поля, которого больше нет по независимой причине. Но релиз `delivery-variant-identity.md` без фикса этого бага ухудшает поведение, поэтому оба должны выйти в одном релизе.

**Фикс перестал противоречить прежнему возражению.** Раздел «Возможные направления решения» ниже отклонял сравнение по DOM: «ломает архитектуру: `FrontendParamsChoice` — серверный экшен, без доступа к DOM». Это верно для чтения DOM сервером, но не для передачи значения В запросе: `ParamsChoiceManager` уже открывает диалог сам и может прочитать `.js-variant-field` (`shipping.html:233`) и переслать его в `prefill/params-choice`, где `FrontendParamsChoiceAction` сравнит `is_current` с полученным значением вместо значения из сессии. Экшен остаётся серверным, значение — обычный вход, используется только для подсветки.

## Симптом

После выбора адреса в диалоге «Мои варианты» и последующей смены **типа** доставки (вкладки «Курьер / Самовывоз / Почта») на тип, который однозначно соответствует одному из вариантов в истории, диалог при повторном открытии **не подсвечивает** совпадающую карточку — хотя выбранный сейчас способ доставки объективно совпадает с одним из вариантов в списке.

Стоит вызвать любой другой пересчёт чекаута (например, кликнуть «+» у товара в корзине) — при следующем открытии диалога подсветка корректно появляется на верной карточке, без каких-либо действий пользователя в самом диалоге.

## Воспроизведение (подтверждено)

Условие: сумма корзины ≥ 15000 ₽, чтобы у типа «Почта» остался ровно один вариант доставки (тогда переключение типа не порождает второй AJAX-запрос выбором варианта из открывшегося дропдауна).

1. Открыть диалог «Мои варианты», выбрать любую карточку, кроме почтовой (например, «СДЭК (Курьер)») — страница перезагружается, тип доставки «Курьер», вариант «Курьер».
2. Переключить «Типы доставки» на «Почта» (без открытия дропдауна «Варианты доставки» — там всего один вариант, и он подставляется автоматически).
3. Открыть диалог «Мои варианты» — **ни одна карточка не подсвечена**, хотя карточка «Почта России (Webasyst) (Посылка)» ей соответствует.
4. Вызвать любой пересчёт чекаута, не трогая доставку (клик «+» на количестве товара в корзине).
5. Открыть диалог «Мои варианты» повторно — карточка «Почта России (Webasyst) (Посылка)» подсвечена как активная.

Скриншоты шагов 3 и 5 (до/после пересчёта) — в этой сессии работы, не сохранены отдельно; воспроизводится стабильно.

## Где искать (гипотеза, не подтверждена по коду/сети)

Подсветка считается в [`shopPrefillPluginFrontendParamsChoiceAction::execute()`](../../lib/actions/frontend/shopPrefillPluginFrontendParamsChoice.action.php):

```php
$checkout_params = $instance->getSessionStorageProvider()->getCheckoutParams(); // shop/checkout из сессии
$current         = $instance->getFillParamsProvider()->getFillParamsByCheckoutParams($checkout_params);
...
$item_array['is_current'] = $item_obj->isSameDeliveryOption($current);
```

`getCheckoutParams()` читает сырой `shop/checkout` — это структура **ядра** Shop-Script (`waCheckout`), плагин её не пишет и не кэширует, только читает. Сравнение идёт по `shipping.type_id` + `shipping.variant_id` (см. `shopPrefillPluginFillParams::isSameDeliveryOption()` и `getFillParamsByCheckoutParams()` в [`shopPrefillPluginFillParamsProvider`](../../lib/classes/fillparams/shopPrefillPluginFillParamsProvider.class.php)).

При ручной проверке в браузере (шаг 2 выше): после смены типа на «Курьер» (тип с несколькими вариантами) дропдаун «Варианты доставки» остаётся **не выбранным** («Выберите вариант доставки») до отдельного клика пользователя — то есть само переключение типа не отправляет `variant_id` на сервер. Похоже, что при переключении типа core-JS чекаута шлёт в `/order/calculate/` только `shipping[type_id]`, а `shipping[variant_id]` в сессию `shop/checkout` не попадает, пока не случится следующий AJAX-запрос с уже выбранным (в т.ч. автоматически, если вариант единственный) значением из формы. До этого момента `getCheckoutParams()` отдаёт **устаревший `variant_id`** — от типа доставки, который был активен до переключения — и `isSameDeliveryOption()` закономерно не находит совпадения. Любой следующий пересчёт (не обязательно связанный с доставкой) отправляет полный снимок формы, включая уже актуальный `variant_id`, и подсветка появляется.

Это предположение по логам/коду и одному прогону в браузере, не подтверждено чтением фактического тела POST `/order/calculate/` (сетевые запросы не инспектировались на уровне payload). Прежде чем чинить — стоит проверить в DevTools → Network тело запроса `calculate` на шаге 2 (есть ли там `shipping[variant_id]` и какое значение) и содержимое `shop/checkout` в сессии до и после пересчёта на шаге 4.

## Гипотеза подтверждена по коду — 22.08.2026

Проверять POST в DevTools больше не нужно: механика видна в исходнике ядра. [`form.js:1646-1655`](../../../../js/frontend/order/form.js#L1646):

```js
if (that.variants_count === 1) {
    dropdown.lock(true);
    // Если кол-во вариантов = 1 (проверка в шаблоне) то автовыбор варианта
    if (that.variant_first && !$variant_field.val()) {      // ← только если поле ПУСТО
        $variant_field.val(that.variant_first.id).trigger("change");
        that.scope.$wrapper.one("ready changed", function () {
            that.update({ reload: true });                   // ← отложено на следующий цикл
        });
    }
}
```

Последовательность:

1. Покупатель переключает тип → `Shipping.prototype.update()` сериализует форму. Поле варианта в этот момент **ещё держит старое значение**, поэтому в POST уезжает пара «новый `type_id` + старый `variant_id`».
2. `calculateAction()` кладёт POST в сессию **целиком** — несогласованная пара становится состоянием заказа.
3. Сервер отдаёт перерисованную секцию доставки с вариантами нового типа; поле варианта обнуляется.
4. Автовыбор срабатывает **только если поле пусто** и откладывает свой `update()` до следующего `ready`/`changed`.
5. Этот отложенный запрос отправляет корректную пару — сессия чинится, подсветка появляется.

Окно между шагами 2 и 5 и есть баг. Для типов с несколькими вариантами автовыбора нет вообще, поэтому расхождение живёт до ручного выбора варианта — что совпадает с наблюдением в разделе «Где искать».

**Причина в ядре, не в плагине.** `FrontendParamsChoice` читает сессию честно; сессия в этот момент действительно содержит несогласованную пару. Это третий известный способ, которым сессия чекаута врёт о текущем выборе покупателя (первые два — вымывание при `region_change` и обеднение при коротком замыкании), и он же — обоснование правила **B2a** в [RULES.md](../concept/RULES.md).

Связь с [issue-65](../codereview/issue-65-prefill-overrides-current-input.md): общая тема (разорванная связная группа `shipping`), но **другая причина** — здесь несогласованную пару шлёт ядро, наше слияние не участвует. Отдельный баг; целевая архитектура issue-65 его не чинит.

## Возможные направления решения

Гипотеза подтверждена по коду (раздел выше), направление решения уточнено 23.08.2026 — блокирует релиз, см. «Симптом меняется» в начале файла:

- **Рекомендовано.** `ParamsChoiceManager` при открытии диалога читает `.js-variant-field` (`shipping.html:233`) из DOM формы и передаёт значение в запрос `prefill/params-choice`; `FrontendParamsChoiceAction` сравнивает `is_current` с этим значением, а не с `shop/checkout` из сессии. Не ломает архитектуру — значение едет как обычный вход запроса, экшен остаётся серверным, доступ к DOM ему не нужен. Требует правки JS (`js/modules/ParamsChoiceManager.js`) и экшена, пересборки min-бандлов (`/build-plugin-frontend`).
- Отклонённая альтернатива: форсировать досылку актуального `variant_id` из плагина на смене вкладки типа. Сложнее (нужно перехватывать событие ядра до его собственного отложенного `update()`) и лечит только часть окна — тип с единственным вариантом; для типов с несколькими вариантами incorrect-highlight держится до ручного выбора в любом случае.
