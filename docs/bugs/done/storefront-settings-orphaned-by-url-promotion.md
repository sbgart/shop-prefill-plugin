# Настройки витрины теряются при любом изменении её адреса

**Статус:** ✅ исправлено 07.09.2026 — идентичность переведена на `checkout_storefront_id`
(коммит `4ed3d90`, план — [storefront-identity-by-checkout-id.md](../../plans/done/storefront-identity-by-checkout-id.md)).
Обнаружено 05.09.2026 при подготовке D-07 (прогон R, ФО-04) как частный случай: «витрина
`wa-dev.loc/*` не имеет собственных строк настроек». Механизм и общий масштаб установлены
07.09.2026 — см. [«Механизм»](#механизм-установлен-07092026) в конце файла.

## Наблюдение

При попытке выключить `consent_required` только для витрины `wa-dev.loc` (чтобы проверить D-07)
правка строки `shop_prefill_settings` с `storefront_code = 'd2EtZGV2LmxvYy9zaG9wLyo='`
(= `wa-dev.loc/shop/*` в base64) не дала никакого эффекта на живом сайте — чекбокс согласия
остался виден при `consent_required = 0` в этой строке.

Причина найдена сверкой с `wa-config/routing.php`: маршрут магазина на домене `wa-dev.loc`
сегодня —

```php
'url' => '*',
...
'old_url' => 'shop/*',
```

То есть в какой-то момент (до этого прогона, дата неизвестна) приложение `shop` было
переключено на корень домена (`url = '*'`), а `old_url = 'shop/*'` оставлен ядром Webasyst для
редиректов со старых ссылок. Плагин же вычисляет код витрины как
`base64_encode($domain . '/' . $route['url'])` (`shopPrefillPluginStorefront::__construct()`) —
то есть **сегодняшний реальный код витрины `wa-dev.loc/*` — это `base64_encode('wa-dev.loc/*')`
(`d2EtZGV2LmxvYy8q`), а не `d2EtZGV2LmxvYy9zaG9wLyo=`.**

Проверено запросом: под правильным кодом `d2EtZGV2LmxvYy8q` в `shop_prefill_settings` **нет ни
одной строки** — эта витрина никогда не была настроена индивидуально. Под старым (мёртвым) кодом
`d2EtZGV2LmxvYy9zaG9wLyo=` лежит ~80 строк — полный набор настроек, включая `active`, все
кастомные шаблоны Zen-групп для доставки/оплаты и т.д. Эти строки нигде не читаются ни одним
живым запросом.

По умолчанию для невыставленной витрины `active = false` (см. CLAUDE.md плагина), поэтому
`getEffectiveStorefront()` для `wa-dev.loc` **всегда** фоллбэчит на глобальную витрину `*` —
подтверждено экспериментально: переключение `consent_required` у `*` (id=97) сразу меняет
поведение живого сайта, переключение той же настройки у мёртвого кода — нет.

## Возможная связь с уже известными багами

- [`storefront_code = '-'`](settings-storefront-code-dash-row.md) — отдельная псевдо-витрина.
- [Мастер-тумблер «active» — визуал расходится с реальным состоянием](settings-active-toggle-visual-state-desync.md) —
  инцидент 28.08 и его повтор 05.09 (см. `admin-contact-profile-overwritten-by-guest-checkout-data.md`
  соседний по времени баг для контраста) правились именно в строке `active` мёртвого кода
  `wa-dev.loc/shop/*` (id=12) — то есть обе «починки» не могли иметь никакого эффекта на живой
  сайт. Это не доказано как причина самих тех багов, но само наличие мёртвого кода означает, что
  предыдущие сессии почти наверняка редактировали не ту строку, когда чинили этот тумблер вручную
  через SQL.

## Что это значит для прогона R

Все сценарии ФО-01/ФО-02/…, отмеченные конфигурацией **K1** («плагин и витрина активны») на
`wa-dev.loc`, фактически всё это время проверяли **K8** (фоллбэк на глобальную витрину), а не
самостоятельную настройку конкретной витрины — потому что настраивать было нечему, витрина пуста.
Функционально это не обязательно баг (фоллбэк — задокументированное поведение), но методически
K1 и K8 на этом стенде для `wa-dev.loc` неразличимы, пока у витрины нет собственных строк.

## Механизм (установлен 07.09.2026)

Наблюдение выше — не про конкретную витрину, а частный случай общего дефекта. Код витрины
вычислялся из её адреса (`shopPrefillPluginStorefront::__construct()`):

```php
$this->code = $domain === '*' && $url === '*' ? '*' : base64_encode($domain . '/' . $url);
```

`storefront_code` — первичный ключ всех строк в `shop_prefill_settings` и имя per-storefront
CSS-файла. То есть идентичность настроек висела на значении, которое ядро переписывает по
действию администратора и молча.

Триггеры — штатные операции:

1. **«Сделать главной страницей»** в карте сайта. `siteMainPage::setNewMainPage()` (`site`,
   строка 169) ставит `url = '*'`, старый адрес кладёт в `old_url`. Вызывающий
   `siteMapSetMainPageController` **не шлёт ни одного события** — `route_save.before/after` и
   `update.route` живут только в `siteConfigureRedirectSave`/`siteRoutingSave`. Поэтому
   «ловить изменение и мигрировать строки» было бы нереализуемо в принципе.
2. **Переименование URL раздела** в настройках домена.
3. **Переименование домена.**

Именно первый триггер и породил исходное наблюдение: приложение `shop` когда-то перенесли на
корень домена, `url` стал `*`, а 87 строк настроек остались под `wa-dev.loc/shop/*`.

## Воспроизведение штатными средствами (07.09.2026)

Без единой правки кода и конфигов, только через интерфейс:

| Шаг | Действие | Результат |
|---|---|---|
| 1 | Карта сайта → «+ Добавить» → «Онлайн-магазин», URL `shop-2` | Ядро выдало свежий уникальный `checkout_storefront_id = 6fa12cba…` |
| 2 | Плагин → витрина `wa-dev.loc/shop-2/*` → «Использовать индивидуальные настройки» → Сохранить | 70 строк под `d2EtZGV2LmxvYy9zaG9wLTIvKg==` |
| 3 | Настройки раздела → URL `shop-2` → `shop-3` → Сохранить | `url=shop-3/*`, `checkout_storefront_id` не изменился |
| 4 | Плагин → селектор витрин | `⚪ wa-dev.loc/shop-3/*` — «настроек нет». 70 строк живы в БД и не читаются ничем |

## Фикс

Идентичность переведена на `checkout_storefront_id` — тот же ключ, по которому ядро хранит
конфиг чекаута (`$full_config[$storefront_id]` в `shopCheckoutConfig::commit()`). Единственная
точка вычисления — `shopPrefillPluginStorefrontCode::fromRoute()`; её зовут и конструктор
витрины, и `findCurrentStorefront()` (раньше код считался в двух местах независимо).

Маршруты, заведённые до checkout2, `checkout_storefront_id` не получают даже задним числом:
`routing_params` применяются только при создании маршрута. Для них сохранён фоллбэк на прежнюю
схему — иначе этот же фикс осиротил бы уже их настройки.

Миграции в `lib/updates/` не делалось: плагин не выпущен, пострадавших установок снаружи нет.
Строки стенда перевешены разовым SQL (87 → `ccce8c20…`, 70 → `4bed6573…`).

## Проверка фикса в браузере (07.09.2026)

- **Переименование URL раздела.** `wa-dev.loc/shop-1/*` → `shop-9` → обратно: витрина остаётся
  зелёной в селекторе, 70 строк читаются. По старой схеме стала бы белой, как `shop-2` → `shop-3`
  в таблице выше.
- **«Сделать главной страницей».** Витрина `ccce8c20…` уехала с корня на `wa-dev.loc/shop/*` и
  осталась зелёной со своими 87 строками; корень занял `4bed6573…` со своим `active=false` и
  показан белым — корректно. Возврат главной страницы вернул маршруты в исходное состояние.
- **Сквозной путь.** Запрос к `https://wa-dev.loc/order/` при заполненном `styles.custom_css`
  только у витрины (у глобальной он пуст) создал `frontend_ccce8c208c86784e78817b593a93faa5.css` —
  значит `findCurrentStorefront()` нашёл витрину по новому коду и прочитал её собственные
  настройки, а не глобальные. Проба снята сразу после проверки.

## Смежное: дубли `checkout_storefront_id`

Два маршрута с одним id — легальная, но недостижимая через интерфейс ситуация: создание раздела
всегда генерирует уникальный id (`generateStorefrontId()` проверяет уникальность по всем
маршрутам). Единственный путь ядра к дублю — копирование сайта (`siteDomainsDuplicate` копирует
маршруты дословно, обработчиков события `domain_duplicate` нет ни в одном приложении), а это
премиум-функция.

Если дубль всё же возникнет, `StorefrontCollection::add()` схлопнет такие маршруты в одну витрину:
настройки не теряются, а делятся — ровно как делится их общий конфиг чекаута. Отдельного кода под
это не писалось.

Дубль на стенде (`wa-dev.loc/shop-1/*` и `shop-1.wa-dev.loc/*` под `4bed6573…`) был артефактом
ручной правки `routing.php` по инструкции проектного `CLAUDE.md`, которая велела списывать поля
маршрута с соседнего домена включая `checkout_storefront_id`. Инструкция исправлена, поддомену
выдан собственный id штатным способом — раздел удалён и создан заново.

**Побочная находка при этом:** удаление раздела на поддомене снесло конфиг чекаута `4bed6573…`,
который был **общим** с `wa-dev.loc/shop-1/*` — вторая витрина осталась без своих настроек
чекаута. Восстановлено из бэкапа. Ещё один довод против общих id, и предупреждение на будущее:
удаление одной из витрин с общим id молча уносит настройки чекаута всех остальных.
