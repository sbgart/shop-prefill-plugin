# Апостроф в переводе ломает Smarty-шаблон на старом Webasyst (installer 2.9.0 / Shop-Script 10.0.0)

**Статус:** исправлено 30.08.2026.

## Наблюдение

Поднято Docker-окружение на минимально заявленной в `requirements.php` версии
(`webasyst-framework v2.9.0` + `shop-script v10.0.0`, см. `~/Project/shop10-docker`).
При открытии настроек плагина (`?action=plugins#/prefill`) — `Error #0`:

```
Syntax Error in template ".../templates/actions/settings/blocks/tabs/General.html" on line 80
"hint_after='Disabled by default. When enabled, the guest's latest order may be used for
automatic prefill on the next visit. ...'}" - Unexpected "s", expected one of: "}" , " " , ATTR
```

Причина: `hint_after='[\`hint.prefill.guest.enabled\`]'` — локаль-плейсхолдер `[\`key\`]`
подставляется текстом перевода **до** компиляции Smarty, и апостроф в переводе
(`guest's`) разрывает окружающую одинарную кавычку атрибута. На текущей рабочей версии
(Shop-Script 12.6.0) эта же строка отрабатывает без ошибки — судя по всему в новом ядре
локаль-плейсхолдер внутри атрибута экранируется, в 2.9.0 — нет.

**На чём это всплывает.** Проверены все 53 места в `templates/`, где локаль-плейсхолдер
стоит внутри одинарных кавычек Smarty-атрибута (`='[\`key\`]'`). Апостроф в EN-переводе
нашёлся у двух ключей:

- `hint.prefill.guest.enabled` — `templates/actions/settings/blocks/tabs/General.html:80`
- `hint.styles.accent_color_dark`

В RU-переводах апострофов у этих же ключей нет — баг воспроизводится только на `en_US`.
Не проверено: 29 мест с `="[\`key`]"'` (двойные кавычки) — там ломать будет двойная кавычка
в переводе, отдельно не искал.

## Фикс

Прямой ASCII-апостроф `'` в обеих EN-строках заменён на типографский `’` (U+2019) — визуально
неотличим, но не совпадает с символом, которым Smarty закрывает одинарную кавычку атрибута:

- `hint.prefill.guest.enabled`: "the guest's latest order" → "the guest’s latest order"
- `hint.styles.accent_color_dark`: "the customer's device" → "the customer’s device"

`.mo` пересобран (`msgfmt`), кэш локали и скомпилированные Smarty-шаблоны на Docker-стенде
очищены. Важный нюанс при проверке: `docker compose exec php rm -rf .../*` **не разворачивает
wildcard** — `exec` не идёт через шелл, команду нужно оборачивать в `sh -c '...'`, иначе `rm`
молча не находит файл `*` и ничего не удаляет (что и произошло при первой попытке чистки).

Проверено вживую: страница настроек плагина (`?action=plugins#/prefill`) открывается без
Smarty-ошибки, `guest’s latest order` подтверждён прямо в живом DOM через `document.body.innerHTML`.

Причина того, что баг не проявлялся на текущей рабочей версии (12.6.0) — **не** разница
версий framework: сам файл-прификтер `wa-system/vendors/smarty-plugins/prefilter.translate.php`
идентичен в обеих версиях и апостроф ломает Smarty tokenizer одинаково в любой версии. Скорее
всего дело в том, что скомпилированный Smarty-кэш (`wa-cache/*/apps/shop/templates/compiled`)
на рабочей машине не пересобирался после того, как в `.po` появился этот конкретный апостроф —
Smarty инвалидирует кэш по mtime `.html`-шаблона, а правка `.po`-перевода mtime шаблона не
трогает. Не проверялось: воспроизводится ли баг на 12.6.0 при полностью чистом `wa-cache`.

## Не разобрано

- Не проверено, воспроизводится ли на 12.6.0 при чистом `wa-cache` (см. гипотезу выше) — если
  да, это не «баг старой версии», а всегда-актуальная мина для любого свежего `wa-cache`.
- Остальные 90+ мест в локали с апострофом (`We'll`, `you'd` и т.д.) не в зоне риска — апостроф
  ломает парсинг только когда попадает **внутрь одинарных кавычек Smarty-атрибута**; свободный
  текст вне атрибутов апостроф переживает нормально.
