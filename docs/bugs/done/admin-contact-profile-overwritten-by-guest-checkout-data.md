# Профиль контакта admin периодически затирается гостевыми данными чекаута

**Статус: закрыто 11.09.2026 — причина найдена и подтверждена чтением кода. Баг ядра Shop-Script,
не плагина `prefill`.** Плагин не участвует в записи — см. «Причина найдена» ниже. Снято с блокеров
релиза плагина.

**Переоткрывалось 09.09.2026 — третье срабатывание, на этот раз с точными шагами повтора.**
Было закрыто 07.09.2026 как разовый глюк (аргументация в «Уточнение» ниже сохранена как есть), но
09.09.2026 при прогоне R (снова на сценарии D-02/D-03!) поймано живьём **на уровне сессии чекаута**,
не только на уровне БД — см. «Срабатывание №3» ниже. В этот раз есть воспроизводимая
последовательность действий, чего не было раньше.

## Причина найдена (11.09.2026, чтением кода ядра, без браузера)

Баг ядра `shop`, целиком снаружи плагина `prefill` — три независимых дефекта ядра складываются в
один эффект. Плагин лишь наблюдает уже отравленное состояние (P9-эхо зеркалит его), сам ничего не
пишет — собственный лог плагина за срабатывание №3 подтверждает: `no params were filled`.

**1. Сессия чекаута не привязана к личности и не чистится логаутом.**
[`shopFrontendOrder.actions.php:33-38`](../../../../../../lib/actions/frontend/order/shopFrontendOrder.actions.php#L33-L38) —
на каждый нефинальный (не `fast_render`) запрос чекаута сырой `$input` целиком (включая
`auth[data][firstname/phone/email]`) пишется в ключ сессии `shop/checkout`. Единственное место, где
ключ удаляется — [`строка 233`](../../../../../../lib/actions/frontend/order/shopFrontendOrder.actions.php#L233),
при успешном создании заказа. `?action=logout` этот ключ не трогает: чистит только `waAuth`,
`PHPSESSID` при логауте/логине бэкенда не меняется. Отсюда — гостевые значения переживают
`логаут → гостевой чекаут → логин` в одной вкладке, что и наблюдалось.

**2. Гард на чужой ввод в `shopCheckoutAuthStep` сломан.**
[`shopCheckoutAuthStep.class.php:125-128`](../../../../../../lib/classes/checkout2/shopCheckoutAuthStep.class.php#L125-L128):

```php
if ($contact_id && $user_id_from_input != $contact_id) {
    $input_values = array_filter($input_values);
}
```

Комментарий рядом («despite there being (empty) values in old input») выдаёт замысел: погасить
*пустые* старые значения при смене пользователя. Но `array_filter()` без колбэка выкидывает только
falsy — непустые гостевые `"TestGuest Runner"`, `"9990001122"` и т.п. проходят насквозь и на
строке 131 (`formatContactFields()`) перекрывают настоящие данные admin, потому что `input`
побеждает `base_values`. Значения сохраняются на `$contact` (реальный объект admin, `id=1`) через
`$contact->set()` на строках 159-163 — уже здесь, в памяти, чужие данные оседают на объекте
авторизованного контакта.

**3. При оформлении заказа объект контакта из шага 2 пишется в БД.**
[`shopOrder.class.php:1710-1792`](../../../../../../lib/classes/shopOrder.class.php#L1710-L1792),
`saveCustomer()`: `$this->data['customer']` (та же протухшая `auth.data`) применяется прямо на
`$this->contact[$fld_id] = $fld_data`, и следом `$this->contact->save()` — прямая запись в
`wa_contact`/`wa_contact_emails` авторизованного контакта.

**Это объясняет оба срабатывания один в один:**

- **№1 (28.08)** — гостевой чекаут довели до реального оформления заказа под сессией admin → шаг 3
  отработал → `wa_contact` реально перезаписан.
- **№3 (09.09)** — заказ не оформляли, только рендер `/order/` → отработал только шаг 2 (видно по
  P9-эху, зафиксировавшему курьера/оплату как «подтверждённый выбор»), `save()` не вызывался → БД
  чиста, заражена только сессия. Собственная гипотеза этого файла («либо не успела произойти, либо
  нужен ещё один шаг — реальное оформление заказа», см. срабатывание №3 ниже) подтвердилась
  дословно.

Все вопросы из раздела «Не разбиралось» ниже этим закрыты. Плагину чинить нечего — правка
принадлежит `wa-apps/shop/lib/` (ядро), трогать который вне мандата плагина. Осталось только решить,
сообщать ли в трекер Webasyst (реальная утечка/перезапись персональных данных между личностями, не
косметика) — вне TODO плагина, решение пользователя.

## Срабатывание №3 (09.09.2026, R-прогон)

Точные шаги: 1) залогинен `admin` в бэкенде (обычная сессия) → 2) `?action=logout` → 3) **в той же
вкладке браузера** (тот же `PHPSESSID`, только что разлогиненный) гостевой чекаут целиком: товар в
корзину → форма покупателя (`TestGuest Runner`, `9990001122`, `prefill-r-test@example.com`) →
Самовывоз/ПВЗ → Наличные → заказ оформлен (`#100131`, позже удалён как тестовый мусор) → 4) снова
`/webasyst/` в той же вкладке, логин `admin` → 5) на витрине `/order/` с **новым** товаром в корзине
(другой продукт, ещё не было ни в одном из двух предыдущих заказов).

Результат: чекаут-форма для `admin` показала не историю `admin` (Новосибирск, ПВЗ, наличные — как
было в этом же прогоне чуть раньше на скриншоте F-01), а данные гостя — `TestGuest Runner`,
`9990001122`, доставку **«Бесплатная доставка курьером»** (тип, который ни разу не выбирался явно
ни в одном из двух гостевых заходов — оба раза выбирался Самовывоз/ПВЗ). Воспроизвелось повторно
после перезагрузки страницы и после полного удаления/повторного добавления товара в корзину — не
разовый рендер-глюк, состояние держится в серверной сессии.

Лог плагина за этот рендер (`user:1`, то есть корректно определённый **настоящий** `admin`):
`Prefill was evaluated but no params were filled (empty final_params)` — плагин ничего не
предзаполнял. Тем же запросом: `Delivery echo cache updated with confirmed choice, variant_id:
33.courier` и `Payment echo cache updated with confirmed choice, id: 16` — то есть эхо-кэш P9
**зафиксировал** курьера/id16 как «подтверждённый выбор текущей сессии», а не как что-то, что
подставил плагин. Значит чужие данные уже лежали в core-сессии `shop/checkout` **до** любого
участия плагина в этом запросе — искать нужно в core-слое (persistent session across
logout→guest-checkout→login), не в `SectionChecker`/`FillParamsProvider`.

Проверено: сама запись `wa_contact` (`id=1`, `firstname`/`lastname`/e-mail) в этот раз **не
пострадала** — осталась `Admin`/`Admin`, оба email на месте (включая старый хвост
`review-guest-2608@example.com`, sort=1, оставшийся неубранным ещё с прошлого инцидента — см. ниже).
То есть в этот раз пойман промежуточный случай: заражение сессии чекаута состоялось, а перезапись
самого контакта в БД — нет (либо не успела произойти, либо триггер записи в БД требует ещё одного
шага, например реального оформления заказа под этой сессией).

**Не разбиралось (сознательно, по договорённости — баги разбираются отдельно):** сам механизм,
почему `shop/checkout` в core-сессии переживает `?action=logout` и подхватывается заново после
следующего логина в той же вкладке. Гипотеза не проверена: `?action=logout` инвалидирует только
`waAuth`, но не трогает прикладной ключ сессии `shop/checkout`, который живёт в том же `$_SESSION`
по `PHPSESSID` — а `PHPSESSID` не меняется при логине/логауте бэкенда, только при явном
`session_regenerate_id()`, если он вообще где-то вызывается в этом потоке.

**Живучесть подтверждена:** перепроверено ~10 минут спустя, новой навигацией `/order/` в той же
вкладке (не F5, полный переход) — состояние то же самое (`TestGuest Runner`, курьер). Не истекает
само по себе за разумное время, держится минимум четверть часа.

**Побочная находка, не убрано:** `wa_contact_emails` контакта `admin` (`id=1`) всё ещё содержит
`review-guest-2608@example.com` на `sort=1` — хвост инцидента №1 (28.08.2026), documented в
«Восстановление» ниже как «временно», но так и не удалён физически, только отодвинут. Не трогалось
в рамках сегодняшнего прогона — не создавалось этим прогоном, решение об удалении не принималось.

## История

- **28.08.2026** (прогон R, ФО-06, при подготовке F-01): обнаружено, что `wa_contact` id=1
  (демо-аккаунт `admin`) имел `firstname/lastname` и первичный email, перезаписанные тестовыми
  гостевыми значениями (`Гость`/`Ревьюшный`, `review-guest-2608@example.com`) — предположительно
  последствие более раннего гостевого сценария D-02/D-03 того же прогона, где форма `auth[...]`
  сохранила тестовые значения в профиль залогиненного admin вместо отдельного гостя. Исправлено
  вручную по решению пользователя: ФИО → `Admin`/`Admin`, email → `artem.shamberger@gmail.com`
  (сделан primary, `sort=0`), дубль-запись удалена. **Root cause самого механизма — почему форма
  сохранилась в профиль admin, а не осталась гостевой — не разбирался.**
- **05.09.2026** (при подготовке B-08 в том же прогоне R, другая сессия/машина): то же самое
  состояние обнаружено снова — `firstname/lastname` опять `Гость`/`Ревьюшный`,
  `wa_contact_emails.sort=0` снова указывает на `review-guest-2608@example.com` (запись с реальным
  email не удалена в этот раз, просто отодвинута на `sort=1`). Между 28.08 и 05.09 в рамках этой же
  сессии разговора никакого нового гостевого чекаута с такими данными не выполнялось — повторное
  проявление либо произошло на другой машине/сессии в промежутке, либо триггерится каким-то более
  общим действием (например, обычным логином после предшествующего гостевого просмотра в той же
  вкладке), а не только явным «гостевым заказом».

## Факт

Механизм, которым данные гостевой формы (или какое-то кэшированное состояние сессии) записываются
в `wa_contact`/`wa_contact_emails` **авторизованного** контакта, сработал минимум дважды независимо,
после явного ручного исправления между разами. Это не разовая случайность конкретного прогона.

## Не разбиралось

- Какой именно код-путь пишет в `wa_contact`/`wa_contact_emails` — форма `auth[...]` штатного
  чекаута обычно должна писать в `shop_order`/`shop_order_params`, а не напрямую в контакт.
  Подозрение (не проверено): core Shop-Script при определённых условиях синхронизирует данные формы
  оформления заказа в профиль текущего авторизованного контакта (стандартное поведение
  `shopCheckoutAuthStep` при сохранении «моих данных»?), и если сессия до этого была гостевой с
  тестовыми значениями в форме, синхронизация переносит их в чужой (admin) контакт при следующей
  авторизации в той же сессии.
- Является ли это багом плагина `prefill` вообще, или чистым поведением ядра Shop-Script
  (правдоподобнее) — плагин здесь не проверялся, разбор отложен обеими сессиями, обнаружившими факт.
- Точный триггер: обычный логин после гостевого просмотра, или обязательно нужен гостевой заказ.

## Уточнение (05.09.2026, вечер): 05.09 — вероятно не рецидив, а старый бэкап БД

Пользователь высказал гипотезу: при переносе на новый Мак развернулись из бэкапа, сделанного до
ручного фикса 28.08, а не «то же самое состояние стенда». Проверено сопоставлением текущей БД с
git-историей документации:

- `SELECT MAX(id) FROM shop_prefill_settings` → `325`. По документации сессии 28–29.08
  (коммит `80ec471`, см. `runs/1.0.0-2026-08-28.md`) в рамках той же сессии создавались и потом
  удалялись строки `id=326` (`zen.active=0`, F-16) и `id=327` (`remember_me.on_order=true`, I-06) —
  в текущей БД они отсутствуют не потому что удалены, а потому что `MAX(id)=325` — таблица никогда
  не доходила до них. Снимок БД сделан раньше их создания.
- `SELECT MAX(id) FROM wa_contact` → `51`. Та же сессия создала одноразовый контакт `id=52`
  (`create_contact`, I-06/I-09) — тоже отсутствует по той же причине.
- Значит текущая БД — это снимок с границы 28→29.08.2026, **до** конца той сессии, а не «тот же
  стенд, синхронизировано с файлами», как ошибочно записано в `runs/1.0.0-2026-08-28.md` в разделе
  «Смена машины 05.09.2026» при первом обнаружении расхождения.
- Ручной SQL-фикс профиля admin (см. «Восстановление» ниже) тоже относится к той же сессии —
  правдоподобно, что снимок предшествует и ему. Тогда «рецидив» 05.09 — это не второе независимое
  срабатывание бага в приложении, а просто повторное применение того же фикса к устаревшей копии
  БД, которая никогда не видела первого фикса.

**Вывод:** доказательная сила «двух независимых срабатываний» снята. Подтверждено только одно
исходное срабатывание (28.08, во время D-02/D-03). Сам факт того, **почему** гостевые данные вообще
попали в профиль `admin` 28.08, этим не объясняется и остаётся неразобранным.

## Восстановление (проверено дважды, один и тот же приём)

```sql
UPDATE wa_contact SET firstname='Admin', lastname='Admin' WHERE id=1;
UPDATE wa_contact_emails SET sort=99 WHERE id=1 AND contact_id=1;   -- временно, во избежание конфликта уникального индекса
UPDATE wa_contact_emails SET sort=0 WHERE id=21 AND contact_id=1;   -- реальный email → primary
UPDATE wa_contact_emails SET sort=1 WHERE id=1 AND contact_id=1;    -- гостевой email → вторичный
```
