**Статус:** ✅ ЗАКРЫТ 07.09.2026. Исходный баг исправлен 24.08.2026 эхо-кэшем, фикс работает.
Все 15 сценариев таблицы «Проверять после фикса» подтверждены — последние (7, 8, 9, 12, 13, 14) 09.09.2026.
Регресс, заявленный 05.09.2026, закрыт как **невоспроизводимый**: 4 цикла «сломал email → починил»
на том самом типе доставки с составным `variant_id` (Самовывоз + ПВЗ `43.NSK2:136:270`), обоими
способами ввода (`window.waOrder.form.update({})` и живой ввод с клавиатуры) — выбор
восстанавливается каждый раз, в логе `Delivery section restored from echo cache`. Код механизма
с 24.08 не менялся: правка 06.09 в `SectionChecker` добавила только диагностические методы,
`isSectionMechanicallyClean()` не тронут. Разделы 05.09/06.09 в конце файла оставлены как есть —
они описывают наблюдение, которое сегодня не подтвердилось; см. «Проверка 07.09.2026» там же.

`variant_id` ещё пуст) разобрана и отвергнута: в этом окне ветка стирания работает верно — у
покупателя и на экране нет выбора, защищать нечего. Поэтому критерий не меняли; вместо этого
поставлена страховка на случай рецидива — логирование состава секции в обеих ветках стирания
(коммит `44f6e1a`), теперь в логе видно, что именно пришло в `order.shipping`/`order.payment`.
**D1 подтверждён закрытым вживую (07.09.2026):** `data-blocked-by` сервер ставит на все
переключатели обеих групп, «Изменить» и «Свернуть» дают диалог «Сначала нужно исправить ошибку…
Ваши данные сохранены и вернутся сами», разворота в пустоту нет, осиротевшей кнопки «Свернуть» нет.
**Приоритет:** 🔴 был блокером релиза — любая жёсткая ошибка шага `auth` стоила покупателю выбора доставки и оплаты, без единого сообщения о потере
**Сложность фикса:** 🔧 средний — `SectionChecker`, `SessionStorageProvider`, `CheckoutHooks`, `ZenModeToggle`, правила Z5/P9
**Связано:** [баг zen-collapse](zen-collapse-on-upstream-checkout-error.md) (сценарии 1/1a/2 переоткрыты), [план снятия снапшота](../../plans/snapshot-removal-and-html-ownership.md) (регрессия появилась здесь), [план эхо-кэша payment](../../plans/done/payment-section-echo-cache.md) (механизм обобщается), [issue-86](../../codereview/done/issue-86-delivery-group-source-completeness.md)
**Правила:** [RULES.md](../../concept/RULES.md) — Z1, Z2, Z3, Z5, P1, P2, P9, B2a

## Симптом

Группа «Доставка» заполнена и свёрнута (курьер, вариант, адрес), способ оплаты выбран. Покупатель делает **одну** опечатку в email — убирает собачку — и тут же её исправляет. После исправления:

- ни один тип доставки не подсвечен, блока «Варианты доставки» нет;
- способ оплаты не выбран, секция оплаты скрыта целиком;
- адрес пуст.

Всё это надо выбирать заново. **Полная перезагрузка `/order/` не помогает** — данных нет в сессии.

Zen до этого успевает соврать: на запросе с ошибкой группа остаётся **свёрнутой** с полной сводкой из кэша, хотя выбора под ней уже нет на странице. Нажатие «Изменить» разворачивает группу в пустоту.

## Когда это срабатывает — не только опечатка в email

Потерю вызывает **любая** жёсткая ошибка шага `auth`: она кладётся в `$errors`, даёт `can_continue = false`, и [`shopCheckoutStep::processAll()`](../wa-apps/shop/lib/classes/checkout2/shopCheckoutStep.class.php#L288) после этого **не вызывает `process()` ни у одного следующего шага** — только `prepare()`, который рендерит пустой шаблон.

## Почему не спас существующий эхо-кэш payment (P9)

Расхождение в протоколе ядра: **одно и то же «просто перерисуй меня» кодируется двумя значениями**.

| Ветка `getData()` | `shipping` | `details` | `payment` |
|---|---|---|---|
| `disabled` | `'only'` | `'only'` | `'only'` |
| `options.clean` | `'only'` | `'only'` | `'only'` |
| обычный перерендер (`that.reload`) | `'only'` ([1871](../wa-apps/shop/js/frontend/order/form.js#L1871)) | `'only'` ([2429](../wa-apps/shop/js/frontend/order/form.js#L2429)) | **`1`** ([2660](../wa-apps/shop/js/frontend/order/form.js#L2660)) |

`isSectionMechanicallyClean()` проверяет только `=== 'only'`, поэтому для `payment` при коротком замыкании условие ложно → код падает в ветку «покупатель сам оставил пустым» и **стирает** эхо. Это и есть `Payment echo cache cleared` в логе.

## План правки

### Правка B (🔴). Критерий «секция промолчала» + эхо группы доставки

**B1. Починить критерий.** Не список принимаемых значений, а то, что заложено в названии метода: секция не прислала **ни одного собственного поля**.

```php
private const SECTION_INPUT_FIELDS = [
    'auth'     => ['mode', 'user_id', 'data', 'service_agreement'],
    'region'   => ['country', 'region', 'city', 'city_id', 'zip', 'location_id'],
    'shipping' => ['type_id', 'variant_id'],
    'details'  => ['shipping_address', 'custom'],
    'payment'  => ['id', 'custom'],
    'confirm'  => ['comment', 'terms'],
];

public function isSectionMechanicallyClean(string $section_id, array $checkout_params): bool
{
    $section    = $checkout_params['order'][$section_id] ?? null;
    $own_fields = self::SECTION_INPUT_FIELDS[$section_id] ?? null;

    if (!is_array($section) || $own_fields === null) {
        return false;
    }

    // Важно наличие ключа, а не его значение: пустой скрытый инпут — тоже разговор
    return empty(array_intersect_key($section, array_flip($own_fields)));
}
```

Протокол-независимо: переживёт и третье значение `html`, если ядро его заведёт. **Проверять «все ключи, кроме `html`» нельзя** — разбор в «Что выяснилось при реализации».

Побочно: гард `if (!empty($id)) return null;` внутри `syncPaymentEcho()` становится структурно недостижимым (если своих полей нет, то и `id` взяться неоткуда) — оставлен утверждением.

**B2. Эхо группы доставки** — `shop/prefill_delivery_echo`, по образцу существующего payment-эха. Хранит три вещи:

```php
[
    'variant_id' => '33.courier',
    'custom'     => ['desired_delivery' => '...'],          // order.details.custom
    'region'     => ['country' => 'rus', 'region' => '54',  // отпечаток адреса
                     'city' => 'Новосибирск', 'zip' => '630000'],
]
```

Отпечаток региона — **обязательная часть, а не украшение**: без него эхо не отличит починку email от смены города (разбор в «Что перепроверено», п. 1).

```php
public function syncDeliveryEcho(): array
{
    $checkout_params = $this->getCheckoutParams();
    $checker         = $this->getSectionChecker();
    $variant_id      = $checkout_params['order']['shipping']['variant_id'] ?? null;

    if ($checker->isSectionMechanicallyClean('shipping', $checkout_params)) {
        $echo = $this->getDeliveryEcho();
        if ($echo === null) {
            return [];
        }

        // Вариант доставки осмыслен только для адреса, под который выбран: список
        // вариантов, тариф и срок ядро считает от региона. Сменился адрес — выбор
        // недействителен, группа обязана развернуться (Z2, B2a).
        if ($echo['region'] !== $this->getRegionFingerprint($checkout_params)) {
            $this->clearDeliveryEcho();
            shopPrefillPluginLog::debug('Delivery echo dropped: region changed');
            return [];
        }

        $restored = ['shipping' => ['variant_id' => $echo['variant_id']]];

        // custom пишем, только если details тоже промолчала: иначе перезапишем
        // то, что покупатель прислал в этом же запросе (P1)
        if (!empty($echo['custom']) && $checker->isSectionMechanicallyClean('details', $checkout_params)) {
            $restored['details'] = ['custom' => $echo['custom']];
        }

        $this->setCheckoutParams(
            shopPrefillPluginHelper::deepMergeArrays($checkout_params, ['order' => $restored])
        );
        shopPrefillPluginLog::debug('Delivery section restored from echo cache', [
            'variant_id' => $echo['variant_id'],
        ]);

        return $restored;
    }

    // Секция говорила сама за себя — это её настоящее состояние
    if (!empty($variant_id)) {
        $this->saveDeliveryEcho([
            'variant_id' => $variant_id,
            'custom'     => $checkout_params['order']['details']['custom'] ?? [],
            'region'     => $this->getRegionFingerprint($checkout_params),
        ]);
    } elseif ($this->getDeliveryEcho() !== null) {
        // Покупатель сменил тип и ещё не выбрал вариант — прежний выбор больше не его
        $this->clearDeliveryEcho();
        shopPrefillPluginLog::debug('Delivery echo cleared: customer left shipping section empty');
    }

    return [];
}
```

Отпечаток — четыре скаляра из `order.region`, сравнение после `trim()`. `region` **никогда** не приходит секцией `clean` (проверено, см. «Что перепроверено», п. 4), так что сравнивать всегда есть с чем.

**B3. Два письма, а не одно.** Записи в `shop/checkout` **недостаточно** — `calculateAction()` строит `$input` из POST, сессию не читает. Восстановленное надо ещё и влить в живой `$data['input']`, как это уже делает payment-эхо ([CheckoutHooks:89-95](../wa-apps/shop/plugins/prefill/lib/classes/hooks/shopPrefillPluginCheckoutHooks.class.php#L89)):

```php
// handleCheckoutBeforeAuth(), рядом с syncPaymentEcho()
foreach ($this->session_storage->syncDeliveryEcho() as $section => $values) {
    if (isset($params['data']['input'])) {
        $params['data']['input'][$section] = shopPrefillPluginHelper::deepMergeArrays(
            $params['data']['input'][$section] ?? [],
            $values
        );
    }
}
```

Каждое письмо закрывает свой путь, и оба нужны:

| Путь | Откуда берётся `$input` | Что срабатывает |
|---|---|---|
| `POST /order/calculate/` | `waRequest::post()` ([:17](../wa-apps/shop/lib/actions/frontend/order/shopFrontendOrder.actions.php#L17)) | инъекция в `$data['input']` |
| Загрузка `/order/` | сессия ([`formVars():429`](../wa-apps/shop/lib/classes/checkout2/shopCheckoutViewHelper.class.php#L429)) | запись в сессию |
| `use_session_input` после `fast_render` | сессия ([:22](../wa-apps/shop/lib/actions/frontend/order/shopFrontendOrder.actions.php#L22)) | запись в сессию |

Побочно это чинит и «перезагрузка не помогает»: на загрузке страницы `$input` берётся из сессии, эхо успевает её долить.

**B4. Сброс.** `DELIVERY_ECHO_KEY` чистится там же, где сегодня `clearPaymentEcho()`: создание заказа, `clear_form`, отзыв согласия. Чистить только при непустом эхо (как в существующем коде) — лишняя запись в сессию поднимает `Set-Cookie: PHPSESSID` (P5, регресс issue-53).

### Правка C (🟠). Гард сворачивания должен знать про серверные ошибки

Сегодня [`ZenModeToggle.collapseGroup()`](../wa-apps/shop/plugins/prefill/js/modules/ZenModeToggle.js#L92) спрашивает только клиентскую валидацию своей группы:

```js
var hasErrors = this.validateSections(form, sections);   // только JS-валидаторы, только своя группа
```

Две дыры:

- **Серверные ошибки невидимы.** `ivan@test.123` проходит JS-регулярку и падает на `waEmailValidator`. Гард ошибок не видит → сворачивает **поверх живого сообщения об ошибке** (оно внутри формы, наш CSS его прячет) → `form.update()` → сервер отвечает ошибкой → Z1 разворачивает обратно. Покупатель видит мигание без объяснения. То же со всеми шестью ошибками из таблицы выше.
- **Про чужую группу не сказано ничего.** Ошибка в «Покупателе», покупатель сворачивает «Доставку» — гард смотрит только секции доставки, там чисто, сворачивает молча.

Правка минимальная: плагин уже знает обе вещи серверно (`getErrorStepId()` + `getRegularErrors()` в [`shopPrefillCheckoutState`](../wa-apps/shop/plugins/prefill/lib/classes/checkout/shopPrefillCheckoutState.class.php#L623), `getRegularErrors()` уже отфильтровывает маркер `fast_render`). Достаточно прокинуть в JS-инициализатор флаг «оформление сейчас заблокировано» + id группы с ошибкой, и в `collapseGroup()` показать **существующий** диалог (`showValidationErrorDialog`) с честной причиной вместо молчаливого сворачивания. Цена: один флаг в генерируемом инициализаторе, одна ветка в JS, одна строка локали.

**Направление «Изменить» — пересмотрено 24.08.2026 после прогона.** Планировалось не трогать: данные целы (правка B), покупатель увидит пустую секцию, после починки всё вернётся. Вживую это оказалось ровно той паникой «данные пропали», которой мы избегаем: клик по «Изменить» при активной ошибке разворачивает группу, где ядро не отрисовало **ни типов доставки, ни адресных полей** — вместо своей заполненной доставки покупатель видит пустоту. Плюс кука `expanded` залипает до конца сессии из-за действия, которое ничего не дало.

Поэтому гард поставлен на **оба** направления, одним и тем же флагом. Атрибут нужен в двух местах: на кнопке и на самой карточке-обёртке (`CollapseBlock.html` вешает `js-prefill-zen-toggle` на весь блок, клик по сводке тоже разворачивает).

## Как эхо соотносится со снапшотом

Да, по духу это снапшот — теневая копия, переживающая замену сессии. Отличия, которые делают его допустимым там, где снапшот был отвергнут:

| | Снапшот (снят 23.08.2026) | Эхо |
|---|---|---|
| Что хранит | весь `shop/checkout`, шесть секций | три ключа: `variant_id` + `custom` + отпечаток региона; отдельно `payment.id` + `custom` |
| Когда пишет | на каждом запросе | только когда секция говорила сама за себя |
| Когда восстанавливает | когда секция «не занята покупателем» (`canPrefillSection`) | только когда секция прислала **единственный** ключ `html` |
| Самоинвалидация | нет, жил до конца сессии | да: сменился регион → выброшено; секция сама сказала «пусто» → выброшено |
| Конфликт с P2 | был: возвращал стёртое покупателем | нет — см. ниже |

**Почему конфликта с P2 больше нет.** Секция, которая отрисовалась, всегда шлёт хотя бы одно своё поле: скрытый `shipping[type_id]` живёт в блоке типов и сериализуется даже пустым. Значит «покупатель очистил выбор» приезжает как `{type_id:'', html:'only'}` — два ключа, не «промолчала», эхо не восстанавливает, а очищается. Пустой POST из одного `html` бывает **только** когда секции на странице нет. То есть критерий — не «признак пустоты», а «признак отсутствия секции», и это разные вещи; снапшот их путал, эхо нет.

Проверено и на смене типа доставки: `Shipping.update()` шлёт свою секцию не-`clean` → `{type_id:'pickup', variant_id:'', html}` → секция говорила → эхо **очищается**, прежний вариант не воскресает.

## Что выяснилось при реализации 24.08.2026 — четвёртая ошибка плана

Первая реализация критерия (`array_keys($section) === ['html']`) в браузере **не сработала**: эхо доставки стиралось на каждом запросе, в логе `Delivery echo cleared: customer left shipping section empty`. Диагностический дамп секции показал причину:

```json
"shipping": {"service_agreement": "1", "html": "only"}
```

Секция `shipping` приходит **не пустой** даже когда её на странице нет. Поле `shipping[service_agreement]` рендерит **форма секции `region`** — [region.html:476-484](../wa-apps/shop/templates/actions/frontend/order/form/region.html#L476):

```smarty
<input type="hidden" name="shipping[service_agreement]" value="0">
<input class="wa-checkbox" type="checkbox" name="shipping[service_agreement]" value="1" ...>
```

А `region` короткое замыкание переживает — он делает работу в `prepare()`. Значит в любом магазине с включённым согласием на оказание услуг `order.shipping` **никогда** не приходит «только с `html`», и проверка по составу всех ключей всегда даёт ложное «секция говорила».

Это не тема и не сторонний плагин — это ядро, воспроизводится на любой инсталляции с `service_agreement` в настройках чекаута.

**Вывод:** проверять надо не «нет ключей, кроме `html`», а «нет ни одного **собственного** поля секции». Список собственных полей снят с шаблонов и шагов ядра (см. `SECTION_INPUT_FIELDS` в B1); чужие поля в пространстве имён секции он игнорирует по построению. Тезис «отрисованная секция всегда шлёт своё поле» при этом остаётся верным — ошибка была в том, что «своё» я подменил на «любое».

Закреплено регресс-проверкой в `SectionCheckerOwnershipVsDataTest` (блок 13).

**3. Клиентская починка: JS запоминает выбор в `localStorage`.** Гонки с перерисовкой секций, зависимость критичной для оформления функциональности от JS, третий источник состояния вне сессии.

**4. Детектор недоверия к рендеру, разворачивающий группу при чужой ошибке (правка A прошлых редакций).** Отброшен как лишний: с эхом сессия перестаёт врать, и **существующая** проверка `isGroupMinimumFilled()` сама даёт оба нужных поведения — выбор был → свёрнуто с правдивой сводкой; выбора не было → эхо пусто → развёрнуто, и пустая секция там уместна. Детектор был протезом под испорченную сессию. **5. Только правка C, без B.** Сообщение вместо потери — но потеря остаётся.

**6. Покрыть эхом `region.possible_address`.** Отклонено: ниша, последствие косметическое (дропдаун подсказок вернётся в исходное состояние), а объём эха заметно вырастет.

### F-10, ветки `admin_error` и `banned_error`: регресс тоже НЕ воспроизводится (05.09.2026)

ожидаемого `banned_error`; `is_company` того контакта не проверялся и не зафиксирован, поэтому
задним числом не подтвердить, но гипотеза объясняет наблюдение без противоречий).

Тот же цикл «сломал → починил» через реальный ввод в браузере (форма «Покупатель», поле email,

| Ветка | Контакт | `errors[0].id` (подтверждено отдельным `fetch()` с той же формой) | Лог на починке |
|---|---|---|---|
| `admin_error` | `PrefillF10Admin2`, `is_user=1`, `is_company=0` | `admin_error` | `Payment section restored from echo cache` (id: 16) + `Delivery section restored from echo cache` (variant_id: 43.NSK2:136:270) |
| `banned_error` | `PrefillF10Banned2`, `is_user=-1`, `is_company=0` | (текст ошибки идентичен `admin_error`/`forbidden_error` — общий `$error_message` в коде, `id` не виден в UI) | То же самое: оба `restored from echo cache` |

Оба случая — **регресс не воспроизводится**, идентично `forbidden_error`. Три из четырёх веток,
проходящих через `shopConfirmationChannel` (`forbidden_error`, `admin_error`, `banned_error`),
теперь подтверждённо не задеты регрессом; регрессирует только ветка 1 (`waEmailValidator`,
формат email) — она вызывается раньше и не использует `shopConfirmationChannel` вовсе. Гипотеза
(не проверявшаяся глубже, по правилу «баг документируем, причину не копаем»): различие может быть
не в типе ошибки, а в том, что именно отличается в сериализации формы между этими двумя кодовыми
путями — не разбиралось.

**Методическая находка.** В процессе теста один диагностический `fetch()` с намеренно минимальным
телом (только `auth[data]...`, без остальных секций) был отправлен напрямую на `/order/calculate/`
в обход реальной формы — это НЕ то же самое, что реальная короткая замыкание секции (там `shipping`
всё равно приходит с «пустыми своими полями», а не отсутствует целиком). Этот запрос временно увёл
`shipping`/`payment` в состояние «можно предзаполнять» (`canPrefillSection() = true`), что на
следующей загрузке страницы проявилось как обычное предзаполнение из истории, а не как регресс —
внешне похоже на «доставка потерялась», но причина другая и не относится к багу. Практический вывод:
для этого класса тестов не использовать синтетический `fetch()` с усечённым телом на реальной
сессии — только настоящий ввод в браузере (или `fetch()` с ПОЛНЫМ снимком формы). Диагностировать
через `errors[0].id` в JSON ответа можно, но только когда тело запроса — полный слепок настоящей
формы, а не ad-hoc минимальный набор полей.

### F-10, ветка «несовпадение типа покупателя»: структурно не подвержена регрессу (05.09.2026)

ветку структурно невосприимчивой к F-09/F-10, но по другой причине, чем `cart_invalid` (там другая
