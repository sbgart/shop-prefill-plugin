# Диалог потери оплаты не показывается при смене типа доставки, а приходит на следующем запросе

**Статус:** ✅ Найдено 04.10.2026 при прогоне 1.0.0, режим R; в тот же день исправлено и проверено вживую
**Приоритет:** 🟢 Мелочь — ничего не теряется и не врёт, срабатывает с задержкой в один запрос
**Сценарий:** F-42, конфигурация K1

## Что ожидалось

F-42: «Самовывоз + ЮKassa, переключить тип на «Почта» (ЮKassa для почты недоступна) → диалог «Нужно выбрать другую оплату», `kind: payment`, `lost: true`». [RULES.md P10](../concept/RULES.md): потеря сообщается в запросе, где выбор пропал.

## Что получилось

K1, количество 2, Самовывоз + способ 22, клик по типу «Почта»:

- запрос смены типа уходит с `payment[html]=only` и без `payment[id]` (перехват тела `calculate`);
- детектор: `kind: payment  lost: false  reason: step_skipped  echo_id: 22`, диалога нет, хотя список способов в ответе уже без 22 и оплата помечена как требующая выбора;
- следующий запрос (`form.update()`, уже с `payment[html]=1`): `lost: true  missing_in_response`, событие `prefill_payment_lost`, диалог показан.

Сам диалог корректен и разовый (после перезагрузки повторов нет). Гость при явном выборе варианта доставки (`post` + `36.parcel`) получает `lost: true` сразу.

## Причина (по коду ядра)

[shopCheckoutPaymentStep.class.php](../../../../../lib/classes/checkout2/shopCheckoutPaymentStep.class.php), конец `process()`: сначала `addRenderedHtml([... 'methods' => $methods])` (внутри него срабатывает хук `checkout_render_payment`, и список способов в `vars.payment.methods` есть), и только **после** этого, если `origin !== 'form'` и `input.payment.html === 'only'`, `unset($result['methods'])`.

Детектор потери выбирает решение в хуке `checkout_render_confirm`, который срабатывает позже, когда список уже вырезан (`getPaymentMethodIds()` → `null` → «шаг не считался»). То есть информация в запросе была, просто читается не в тот момент.

## Направление исправления

Снять список способов в хуке `checkout_render_payment` (он выполняется до `unset`) и передать идентификаторы хуку подтверждения через статическое поле. Статика нужна, потому что ядро пересоздаёт объект плагина на каждое событие (см. `CheckoutPageDetector::$checkout_hook_fired`). Около 15 строк и тест на «список виден в хуке оплаты и остаётся до хука подтверждения».

## Что сделано

Хук `checkout_render_payment` запоминает идентификаторы способов (`CheckoutState::rememberPaymentMethodIds()`, статика на запрос), пока ядро не вырезало `methods`; `getPaymentMethodIds()` читает сначала параметры своего хука, затем запомненное. Запоминание стоит за опцией `zen.lost_choice_notice` (по умолчанию выключена).

Проверено: `LostChoiceNoticeGateTest` (22 проверки, 6 мутантов убито); гость через curl (`qty 6`, самовывоз + 22 → почта с `html=only`): `payment: lost: true (missing_in_response)` в том же запросе, повтор — `already_notified`; браузер, K1: самовывоз + ЮKassa → «Почта» — один `calculate`, диалог «Нужно выбрать другую оплату» сразу.

## Область поражения

Покупатель, который меняет тип доставки при выбранной оплате, недоступной для нового типа. Оплата при этом сбрасывается и подсвечена, диалог всплывёт при следующем действии на форме, а не в момент смены. Неожиданное время, но не потеря данных.
