# session_is_alive не прокидывается в AJAX-рендере чекаута — риск перезаписи данных из localStorage

**Статус:** ✅ Закрыта 24.08.2026 как неприменимая — фиксить нечего на стороне плагина. Дефект в core (`session_is_alive` не долетает до `calculateAction()`) подтверждён вживую (curl + браузер), но описанный ниже сценарий его эксплуатации — нет. Разбор [issue-65](../codereview/issue-65-prefill-overrides-current-input.md) (ревизия 4, закрыта на день раньше, 23.08.2026) независимо показал, что `Form.prototype.reload()` — мёртвый код: единственный вызывающий подписан на событие `wa_auth_contact_logout`, которое нигде в проекте не генерируется (проверено grep'ом по всему `wa-apps/shop/`, включая легаси и минифицированные файлы — только `.on`/`.off`, ни одного `.trigger`). Смена региона/способа доставки идёт через `Section.update({reload:true})` → `Form.prototype.update()` — это **посекционный** JSON/HTML-пересчёт (`calculate()` с `response` не `html` для всей формы), который не пересоздаёт `Form` и не трогает `use_storage`/`storage("load")` — они срабатывают только внутри `initClass()`, вызываемого ровно один раз при конструировании `Form`: либо на первой полной загрузке страницы (`formVars()` — там флаг считается верно), либо в `Form.prototype.reload()` (недостижим). Живой браузерный тест это подтвердил: смена типа доставки (Курьер → Самовывоз) не изменила `window.waOrder.form.use_storage`, хотя AJAX-запрос ушёл — потому что новый `Form` не создавался. **Практический вывод: в текущей связке core+тема+плагин у дефекта нет действующего пути эксплуатации через обычные действия покупателя.** Это латентный баг core, а не активный риск для данных — важно только если апстрим когда-нибудь начнёт реально дёргать `Form.prototype.reload()` (например, если кнопка выхода станет слать `wa_auth_contact_logout` вместо `wa_order_reload_start`). Решение из раздела «Возможные решения» ниже не реализуется — патчить дохлый путь, который никто не вызывает, не имеет смысла (YAGNI); раздел «Куда возвращаться» описывает, при каком условии переоткрывать.

Возник как находка при обновлении shop-script в августе 2026: в рабочей копии был локальный патч core-файла, который апдейт бы затёр. Патч переносить нельзя — плагин ставится на чистые инсталляции shop-script, core трогать нельзя.

## Подтверждение дефекта (24.08.2026)

Сам дефект — реален и проверен независимо двумя способами:

1. **curl**, гостевая банка кук (см. CLAUDE.md): `POST /order/calculate/?response=html` с любыми полями → в ответе на месте `use_storage:` буквально вылезает xdebug-нотис:

   ```text
   Notice: Undefined index: session_is_alive in .../ee3f4642465fb801f337a5d068f38862371b85d0.file.FrontendOrderForm.html.php on line 351
   ```

2. **Тот же запрос из живой авторизованной сессии браузера** (`fetch('/order/calculate/?response=html', ...)` из консоли той же вкладки, где покупатель уже дошёл до чекаута с непустой сессией) — идентичный нотис. Значит `prepareFormVars()` действительно никогда не выставляет `session_is_alive`, независимо от реального состояния сессии — ни в гостевом, ни в авторизованном сценарии.

При этом реальный клик по смене типа доставки в браузере (Курьер → Самовывоз, тот же авторизованный сеанс) такого нотиса не производит и `window.waOrder.form.use_storage` не меняет — потому что этот клик не идёт через `response=html` для всей формы (см. статус выше).

## Контекст

В `wa-apps/shop/lib/actions/frontend/order/shopFrontendOrder.actions.php` (core Shop-Script, НЕ наш код) была обнаружена локальная правка в `calculateAction()`:

```php
$session_checkout = wa()->getStorage()->get('shop/checkout');
$view->assign((new shopCheckoutViewHelper())->prepareFormVars($data) + [
        'session_is_alive' => !empty($session_checkout['order']),
        ...
```

Эта строка отсутствует в апстриме Shop-Script. Без неё переменная `session_is_alive` в шаблон `FrontendOrderForm.html` не попадает вообще (Smarty трактует как `false`).

## Как используется session_is_alive

Двухуровневое хранилище данных чекаута (описано в [../concept/CONCEPT.md](../concept/CONCEPT.md), раздел «Механизм хранения данных»):

- **PHP-сессия** (`shop/checkout`) — основное хранилище, туда пишет и наш prefill (`SessionStorageProvider`).
- **localStorage** (`webasyst/shop/order/form`) — резервное хранилище в браузере, подгружается JS **только если сессия мертва**.

Переключатель — `session_is_alive`, который в `wa-apps/shop/templates/actions/frontend/FrontendOrderForm.html` идёт в инлайновый `<script>`:

```smarty
use_storage: {if $session_is_alive}false{else}true{/if},
```

и читается в `wa-apps/shop/js/frontend/order/form.js`:

```js
if (that.use_storage) { that.storage("load"); }
```

`storage("load")` при срабатывании берёт снэпшот из localStorage и целиком отправляет его в `that.calculate(form_data)` — т.е. **заменяет** текущее состояние формы, а не дополняет.

## В чём проблема (по анализу кода)

`session_is_alive` корректно вычисляется в апстриме только в `shopCheckoutViewHelper::formVars()` — используется при **первой полной загрузке страницы** чекаута.

Но `calculateAction()` — это JSON/HTML-эндпоинт `/order/calculate/`, который рендерит тот же `FrontendOrderForm.html` при:
1. fast_render follow-up сразу после первой загрузки страницы (`use_session_input=true`);
2. **любой структурной пересборке формы** через `Form.prototype.reload()` на клиенте — триггерится флагом `reload: true`, который проставляется при смене региона, способа доставки и т.п. (частое явление в обычном сценарии оформления заказа).

Без патча `session_is_alive` не передаётся в шаблон **вообще**, независимо от реального состояния сессии → `use_storage` всегда `true` на любом таком AJAX-рендере → `storage("load")` может сработать и затереть только что введённые (или предзаполненные плагином) данные устаревшим снэпшотом из localStorage.

Важный нюанс: `calculateAction()` в ветке без `use_session_input` **сохраняет** текущие данные формы в сессию ДО рендера ответа — значит после самого первого реального взаимодействия пользователя сессия физически не может быть «мертва» для всех последующих `reload()`-вызовов. То есть баг проявляется даже тогда, когда сессия объективно жива — просто флаг не долетает до шаблона.

## Воспроизведение (план теста, изначально написанный до проверки)

Шаг 3 плана ниже опирался на неверную посылку — «смена региона/способа доставки триггерит `reload: true` в `form.js`» смешивала посекционный `Section.update({reload:true})` с методом `Form.prototype.reload()`; это разные вещи, см. статус вверху и «Подтверждение дефекта». Оставлено как есть для истории и как основа воспроизведения, если условие из «Куда возвращаться» когда-нибудь наступит.

1. Открыть чекаут, ввести данные в поле, которое НЕ трогает наш prefill (например, комментарий к заказу), дать странице сохранить его в localStorage.
2. В DevTools → Application → Local Storage проверить ключ `webasyst/shop/order/form`.
3. Сменить регион/способ доставки (то, что триггерит `reload: true` в `form.js`) — **на деле не вызывает `Form.prototype.reload()`**, см. выше.
4. В Network найти POST на `/order/calculate/` с `response=html`, посмотреть значение `use_storage:` в инлайновом `<script>` ответа.
5. Проверить, откатились ли поля формы к старым значениям из localStorage после этого reload.

## Ожидаемое поведение

`use_storage` должен быть `false` в любом AJAX-рендере после того, как сессия уже содержит данные — localStorage должен подхватываться только один раз, когда PHP-сессия реально пуста/истекла.

## Фактическое поведение

Подтверждено 24.08.2026 (см. «Подтверждение дефекта» вверху): `use_storage` в HTML-ответе `calculateAction()` действительно всегда попадает под false-ветку `{if $session_is_alive}` (в дебаг-режиме — вообще PHP notice вместо значения), независимо от реального состояния сессии. Но живого пути, которым браузер запросил бы у `calculateAction()` именно `response=html` для всей формы вне первой загрузки страницы, в текущем core+теме+плагине нет — единственный такой вызов, `Form.prototype.reload()`, мёртвый код (см. issue-65).

## Возможные решения

Не реализуется — см. статус вверху. Решение ниже оставлено как история/на случай если условие из «Куда возвращаться» наступит:

Решение должно жить целиком в плагине, без правок core (ставится на чужие инсталляции):

**JS-патч в `frontendHead` (наш хук, уже используется для cookie гостя):** обернуть `window.waOrder.Form`, дождавшись его определения (form.js грузится раньше инлайн-скрипта шаблона). Для **любой пересборки формы, кроме самой первой на странице**, принудительно выставлять `use_storage: false` перед вызовом оригинального конструктора — потому что к моменту второй и последующих пересборок сессия чекаута гарантированно уже содержит данные (см. нюанс выше). Первую пересборку не трогаем — там либо сессия правда пуста (localStorage восстановление уместно), либо `formVars()` и так посчитал флаг верно.

## Куда возвращаться

Условие переоткрытия — не «после апдейта shop-script» вообще, а конкретно: апстрим начинает реально вызывать `Form.prototype.reload()` (например, событие `wa_auth_contact_logout` начинает где-то генерироваться, либо ядро добавляет новый вызывающий). Если это случится и проявится симптом (пропадающие поля формы при смене региона/доставки, старые данные из localStorage вылезают поверх новых) — начинать отсюда и реализовать JS-патч из «Возможные решения».
