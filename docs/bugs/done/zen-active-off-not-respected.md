# `zen.active = false` не отключает Zen-режим (F-16)

**Статус:** ЗАКРЫТО как ложное срабатывание 05.09.2026 — см. «Опровержение» ниже. Реальной проблемы
нет, `zen.active=false` работает штатно при правильной настройке.

## Воспроизведение (28.08.2026, прогон R, ФО-06, сценарий F-16, конфигурация K9)

1. В `shop_prefill_settings` добавлена строка `storefront_code='d2EtZGV2LmxvYy8q'` (`wa-dev.loc/*`),
   `name='active'`, `groups='["zen"]'`, `value='0'` — до этого override для `zen.active` на этой
   витрине не было, использовалось значение по умолчанию (`true`) из `storefront.settings.php`.
   Формат строки идентичен другим рабочим override-строкам `zen.active` в этой же таблице
   (например `id=41`, `groups=["zen"]`, для витрины `wa-dev.loc/shop/*`).
2. Свежая сессия (новый cookie jar, логин `admin`/`123`), товар в корзине, `GET /order/`.

**Ожидание (F-16, [TEST-PLAN.md](../tests/TEST-PLAN.md)):** ни одна группа не свёрнута,
`zenmode.css` не подключается.

**Факт:** группы `delivery` и `payment` по-прежнему рендерятся свёрнутыми
(`data-action="expand"`, есть кнопка «Изменить», сводка показана), `zenmode.css` по-прежнему
подключён (`<link>` в разметке). Поведение полностью совпадает с состоянием при
`zen.active` по умолчанию (`true`) — настройка `active=0` группы `zen` видимого эффекта не имеет.

Воспроизведено дважды подряд (два последовательных `GET /order/` в одной сессии) — не гонка загрузки.

## Не разбиралось

Читает ли `shouldCollapseGroup()` / выбор ассетов вообще leaf `zen.active`, или он подмешивается
в effective-settings иначе, чем остальные `zen.groups.*.enabled` (последние, судя по прежним
находкам этого прогона, применяются штатно — см. F-17 в TEST-PLAN.md, не проверялось отдельно
в этом прогоне).

## Уборка

Тестовая строка `id=326` удалена сразу после проверки — override для этой витрины снова отсутствует
(значение вернулось к дефолту `true` из кода, ничего восстанавливать не нужно).

## Опровержение (05.09.2026)

При работе над D-07 (ФО-04) выяснилось, что витрина `wa-dev.loc/*` (код `d2EtZGV2LmxvYy8q` —
тот же, что использовался здесь 28.08) **не имеет собственной строки `active` на верхнем уровне**
(`groups=null`) — а именно этот leaf проверяет `shopPrefillPluginStorefront::isActive()`
(`(bool) $this->getSettings()['active']`). Без него витрина по умолчанию **неактивна**
(см. CLAUDE.md плагина: «`active = false` — дефолт»), и `getEffectiveStorefront()` **всегда**
фоллбэчит на глобальную `*`, полностью игнорируя любые другие override-строки этой витрины —
включая ту единственную (`zen.active=0`), которую 28.08 создали для проверки F-16. Настройка
физически не могла сработать: код никогда не читал именно эту витрину.

Подробности механизма — [storefront-settings-orphaned-by-url-promotion.md](storefront-settings-orphaned-by-url-promotion.md).

**Повторная проверка (05.09.2026, правильно — через глобальную витрину `*`, `id=102`):**

1. `UPDATE shop_prefill_settings SET value='false' WHERE id=102` (`storefront_code='*'`, `name=active`, `groups=["zen"]`).
2. `/clear-cache`, свежая сессия, `GET /order/` (`user:1`, товар в корзине).
3. Результат: `zenmode.css` **не** подключён (`document.querySelector('link[href*=zenmode]')` → `null`),
   `document.querySelectorAll('[class*=prefill-zen]').length === 0` — Zen-режим полностью отключён,
   как и требует F-16.
4. Настройка возвращена в `true`, `/clear-cache` — повторная проверка подтвердила возврат
   (`zenmode.css` снова подключён, 12 элементов с классом `prefill-zen-*`).

**Вывод:** `zen.active=false` работает корректно. Находка 28.08 — ложноположительная, вызвана тем,
что override-строка была создана на витрине без собственного `active=true`, а не багом самой
Zen-логики. Открытых вопросов по этому сценарию не осталось.
