# Кэш сводки Zen показывает данные предыдущей личности после смены гость↔авторизован в той же сессии

**Статус:** ✅ Исправлено 07.09.2026 по [плану](../../plans/done/zen-summary-cache-identity-scope.md) — в записи кэша появился штамп владельца
(отпечаток источника), чужая запись читается как пустая. Проверено в браузере обоими прогонами
(репро больше не воспроизводится; кэш при этом продолжает работать для своей личности),
автотест `tests/ZenSummaryCacheIdentityTest.php` — 13 проверок.

## Воспроизведение (28.08.2026, прогон R, ФО-05)

1. Выйти из бэкенда (`?action=logout`) — сессия становится гостевой, но PHPSESSID **не меняется**
   (уже отмечено ранее в CLAUDE.md как грабли: логаут не создаёт новую сессию).
2. Гость оформляет заказ с доставкой в Москву, «Проспект Мира 1» (в этом прогоне — заказ #109,
   контакт 51, см. [TESTS.md ФО-04](../../tests/TESTS.md)).
3. Заново войти в бэкенд под тем же браузером (`admin`) — та же сессия, теперь `user:1`.
4. Открыть `/order/` (товар в корзине, `/prefill/clear-storage` вызван перед этим).

**Ожидание:** карточка «Доставка» в свёрнутом виде показывает данные **текущей** личности
(контакт 1, история — Новосибирск, ул. Дзержинского/Брестская пр-кт).

**Факт:** свёрнутая карточка показывает **«Москва, Проспект Мира 1»** — адрес гостя из шага 2,
хотя контакт сменился на 1. Лог подтверждает: `Zen summary for 'delivery' rendered from cache`.

При этом сам **живой источник данных корректен**: разворачивание карточки («Изменить») показывает
правильные поля формы — регион «Новосибирская область», город «Новосибирск». Расхождение — только
в закэшированной сводке для свёрнутого вида, не в реальных данных формы/сессии.

`shop_customer` контакта 1 не пострадал (`last_order_id=106`, не тронут), заказ #109 корректно
привязан к контакту 51 — путаницы в БД нет, только в отображении кэша сводки.

## Причина

`shopPrefillPluginZenSummaryCache` (`lib/classes/zenmode/shopPrefillPluginZenSummaryCache.class.php`)
хранит данные под ключом `shop/prefill_zen_summary` в `waSessionStorage` — то есть буквально
привязан к PHPSESSID, а не к личности (contact_id / гостевой токен). Подтверждено чтением кода,
без правок.

Единственное место, где кэш очищается — `shopPrefillPluginZenMode::resetState()`
(`clearCookies()` + `summary_cache->clear()`), а единственный вызов `resetState()` —
`shopPrefillPluginOrderHooks::handleOrderActionCreate()`, то есть **только при создании заказа**.
Ни логаут, ни логин под другим контактом, ни просто смена личности без заказа кэш не трогают —
а PHPSESSID при логауте/логине не меняется (грабли, отмеченные в CLAUDE.md).

`resolveSummaryData()` (`shopPrefillPluginZenMode.class.php`) на каждом рендере свёрнутой карточки
группы либо видит свежие данные в `$params` (`hasFreshData()`) и перезаписывает кэш, либо — если
`$params` пуст (fast_render на каждой загрузке `/order/`, короткое замыкание, либо группа просто
ещё не считалась в этом запросе) — молча подставляет то, что лежит в кэше, и пишет в лог
`Zen summary for '{group}' rendered from cache`. Эта проверка не смотрит, чья это личность.

## Подтверждённое репро (07.09.2026)

Заказ оформлять **не обязательно** — достаточно, чтобы гость хоть раз свернул карточку группы
с реальными данными:

1. Выйти из бэкенда (`?action=logout`) — сессия не меняется.
2. Гость: товар в корзину со страницы товара → `/order/` → выбрать тип доставки «Курьер»,
   вариант с СДЭК (регион по умолчанию витрины — Москва) → заполнить адрес и подъезд →
   нажать **«Свернуть»** у карточки «Доставка» вручную (авто-сворачивание не срабатывает,
   пока не сброшена кука `prefill_zen_delivery=expanded`, выставленная на первом пустом рендере).
   Карточка сворачивается и показывает «сдэк, Курьер • Бесплатно» — в этот момент
   `resolveSummaryData()` пишет эти данные в кэш. Заказ **не оформлялся**.
3. Войти в бэкенд под `admin` (контакт 1, та же сессия).
4. Открыть `/order/` (товар остался в корзине, заказ на шаге 2 не создавался).

**Факт:** карточка «Доставка» сразу показывает «сдэк, Курьер • Бесплатно» — выбор гостя.
Лог подтверждает: `2026-09-07 07:37:59 ... user:1 [DEBUG] Zen summary for 'delivery' rendered
from cache`, этому предшествует `[DEBUG] Prefill was evaluated but no params were filled
(empty final_params)`.

Реальная история контакта 1 (заказ #117, БД `shop_order_params`) — `shipping_name = "СДЭК (ПВЗ
Новосибирск, Вокзальная магистраль (NSK2))"`, `shipping_type = pickup`. То, что видно на экране —
не пикап в Новосибирске, а курьер в Москву, выбор гостя из шага 2.

Значит утечка шире, чем в исходном репро от 28.08: она не требует создания заказа вообще —
достаточно любой смены личности внутри одной незаменённой сессии между двумя рендерами,
один из которых застал `$params` пустыми.

## Как проверено после фикса (07.09.2026)

| Прогон | Что | Результат |
|---|---|---|
| A (репро выше) | Гость → Москва/СДЭК-курьер → «Свернуть» → логин `admin` → `/order/` | Карточка гостя не показана: у `admin` его собственные «Новосибирская область / Новосибирск». Единственный `rendered from cache` в интервале — в 08:37:40 **без** маркера `user:N`, то есть гость читал свой же кэш; у `user:1` обращения к кэшу нет |
| B (негативный) | Та же личность: `admin` выбрал ПВЗ NSK2, свернул карточку, перезагрузил `/order/` | `2026-09-07 08:39:40 … user:1 [DEBUG] Zen summary for 'delivery' rendered from cache`, карточка заполнена его же ПВЗ. Кэш не «починен выключением» |

Предупреждений `Failed resolving zen summary cache owner` в логе нет.

## Направление фикса (реализовано)

Ключ кэша должен зависеть от текущей личности, а не только от сессии — тогда смена личности
сама по себе делает запись в кэше нечитаемой (промах, а не чужие данные), без необходимости
ловить событие логина/логаута отдельным хуком. В `FillParamsProvider`/`CheckoutHooks` уже
считается «ключ источника» (source key) для того же различения гость/контакт — тот же ключ
(или его часть) стоит включить в ключ хранения `shop/prefill_zen_summary_<source_key>`
или в состав самого массива с проверкой владельца при чтении. Отдельный вызов `clear()` при
логине/логауте не нужен и был бы менее надёжен — событий смены личности в Webasyst несколько
(логин, логаут, `order_action.create` для гостя), и ловить их все по отдельности — это как раз
тот подход, который в `docs/bugs/zen-collapse-on-upstream-checkout-error.md` уже был отвергнут
для похожей проблемы в пользу структурного решения.
