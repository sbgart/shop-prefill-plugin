# В shop_prefill_settings есть строки с storefront_code = '-'

**Статус:** ❌ не баг, закрыто 07.09.2026. `-` — штатный код общеплагинных настроек, объявленный
в самом плагине. См. [«Разбор»](#разбор-07092026) в конце файла.

## Наблюдение

При проверке `active` перед сценарием A-02 (28.08.2026) обнаружены строки в
`shop_prefill_settings` с `storefront_code = '-'` — значение, не входящее в список известных
кодов витрин стенда (`*`, `d2EtZGV2LmxvYy8q`, `d2EtZGV2LmxvYy9zaG9wLyo=`, `d2EtZGV2LmxvYy9zaG9wLTEvKg==`):

```
storefront_code  name          groups         value
-                active        null           true
-                update_time   null           1787760106
-                updated_by    null           1
-                level         ["logging"]    debug
```

`update_time = 1787760106` → 2026-08-24 (проверить точно). `level = debug` — уровень логирования
для этой псевдо-витрины стоит на `debug`, при default `warning` (см. TEST-PLAN.md L06).

Не разбиралось: как эта строка появилась (ручное сохранение при нераспознанной витрине? тестовый
артефакт прошлой сессии?), влияет ли на `getEffectiveStorefront()` / SPA настроек, безопасно ли
удалить.

## Обновление (28.08.2026, прогон R, ФО-12, L-06)

Косвенное наблюдение в пользу того, что строка **действует**, а не мёртвая: весь
`wa-log/prefill.plugin.log` (с 19.08 по 28.08, ~104k строк) сплошь состоит из `[DEBUG]`-записей —
поведение, соответствующее именно `level=debug`, а не документированному умолчанию `warning`.
Не проверялось напрямую (не менялось значение, не смотрелся код чтения уровня) — только совпадение
по времени и по значению. Из-за этого L-06 (TEST-PLAN.md ФО-12) в этом прогоне не проверить в чистом
виде, пока эта строка не разобрана.

## Независимый повтор на чистой инсталляции (30.08.2026)

Воспроизведено на Docker-стенде под минимальную версию (`~/Project/shop10-docker`, чистая БД,
ни одного предыдущего сохранения). Единственное действие — сохранение вкладки «Guest» на
селекторе витрины **«General settings for all storefronts»** (`*`), витрина руками не
переключалась и не вводилась. Результат — та же строка-артефакт:

```
storefront_code  name    groups  value
-                active  null    true
```

Это исключает версию «тестовый артефакт прошлой сессии» и делает подозрение на нераспознанную
витрину маловероятным (витрина явно выбрана как `*`, ничего похожего на `-` не вводилось).
Похоже на детерминированный баг сохранения, а не разовую случайность — вероятный кандидат:
шапочный тумблер `active` (см. уже описанный дубль поля в
[duplicate-active-field-header-vs-tab.md](duplicate-active-field-header-vs-tab.md)) шлётся без
контекста витрины и падает в БД с фолбэк-кодом `-`. Не проверялось: воспроизводится ли без
клика по шапочному тумблеру вовсе.

## Третье независимое подтверждение (05.09.2026, K-10)

Сохранение вкладки «Отладка» → «Уровень логирования» (`shop_prefill[...][logging][level]`) при
выбранной глобальной витрине `*`, без единого клика по шапочному тумблеру `active`, тоже легло в
строку `storefront_code='-'` (id=115, `value` корректно обновился на выставленное значение). Это
ослабляет гипотезу «виноват именно шапочный тумблер `active`» — проблема шире и задевает как минимум
ещё одно поле формы (`logging.level`) на вкладке, где шапочного тумблера в кадре нет вовсе. Похоже на
что-то общее в пути сохранения формы настроек при витрине `*`, а не в конкретном поле.

## Разбор (07.09.2026)

Это не баг сохранения и не фолбэк-код нераспознанной витрины. `-` — **штатный код
общеплагинных настроек**, объявленный в самом плагине:

```php
class shopPrefillPluginSettingProvider extends shopPrefillPluginAbstractSettingProvider
{
    // Global settings use '-' as the storefront code
    private const CODE = '-';
```

В плагине два независимых слоя настроек, и они намеренно живут в одной таблице под разными кодами:

| Слой | Код | Конфиг умолчаний | Что там |
|---|---|---|---|
| Общеплагинные (не привязаны к витрине) | `-` | `lib/config/settings.php` | `active`, `logging.level`, `update_time`, `updated_by` |
| Настройки конкретной витрины | `checkout_storefront_id` | `lib/config/storefront.settings.php` | `active`, `prefill`, `styles`, `zen`, `update_time`, `updated_by` |
| Умолчания для всех витрин | `*` | `lib/config/storefront.settings.php` | то же, что у витрины |

`lib/config/settings.php` объявляет ровно те четыре ключа, что и наблюдались в базе — `active`,
`logging.level`, `update_time`, `updated_by`. Совпадение полное, ничего лишнего в строках `-` нет.

Это объясняет все три наблюдения выше без единой гипотезы о сбое:

- **Сохранение вкладки «Guest» при выбранной `*`** записало `-.active` — сработал общеплагинный
  killswitch из шапки, а не витринный тумблер.
- **`logging.level` при выбранной `*`** ушёл в `-`, потому что уровень логирования и есть
  общеплагинная настройка: он один на весь плагин, а не на витрину.
- **Весь лог в `[DEBUG]` при документированном умолчании `warning`** — следствие того, что
  `-.logging.level` действительно стоял на `debug`. Строка не мёртвая, она рабочая.

Независимо подтверждено в соседнем разборе: тумблер `active` в шапке настроек — это глобальный
killswitch плагина (`storefront_code = '-'`), а тумблер вкладки «Основные настройки» — настройка
конкретной витрины; см.
[settings-active-toggle-visual-state-desync.md](settings-active-toggle-visual-state-desync.md),
закрытый 06.09.2026 по той же причине.

Что действительно стоит улучшить (отдельно от этого файла) — два разных флага под одним именем
`active` и одинаковой иконкой в интерфейсе: см.
[duplicate-active-field-header-vs-tab.md](duplicate-active-field-header-vs-tab.md).
