# Debug-панель рендерится на любой странице, не только на чекауте, и без проверки `isAdmin()`

**Статус:** 🔍 Найдено 12.09.2026 при прогоне `/plugin-test prefill full`
**Приоритет:** 🟢 Мелочь (оба условия появления выключены по умолчанию)
**Сценарий:** обнаружено на шаге L2.2 (curl-проверка «0 ассетов на каталоге») — не входит явно ни в один
из L-01..L-03 в [TEST-PLAN.md](../tests/TEST-PLAN.md#фо-12-отладка), там ни одна строка не указывает
конкретную страницу и наличие/отсутствие `isAdmin()`.

## Что ожидалось

Комментарий в самом коде разделяет два разных охвата — ассеты только на чекауте, debug-панель отдельно
(`lib/classes/hooks/shopPrefillPluginFrontendHooks.class.php:70-71`):

```php
// Здесь остаются куки, remember-me, debug-панель и ассеты. Ассеты — только на
// странице оформления заказа: см. issue-64 и initializeFrontendAssets().
```

Формулировка предполагает осознанное решение, но нигде не зафиксировано явно, что панель обязана быть
видна **анониму на любой странице** — ни в `RULES.md`, ни в TEST-PLAN.md (L-03 описывает прогон «+
админ», не проверку прав).

## Что получилось

`handleFrontendHead()` (тот же файл, строки 96-104) гейтит `DialogTemplates` через
`$this->page_detector->isCheckoutPage()`, но вызов debug-панели строкой ниже — нет:

```php
if ($this->page_detector->isCheckoutPage()) {
    $head_html .= shopPrefillPluginViewProvider::render('checkout/DialogTemplates');
}

if ($this->is_debug_panel) {
    $head_html .= shopPrefillPluginDebug::renderDebugPanel();
}
```

`isDebugPanelEnabled()` (`lib/shopPrefill.plugin.php:105-114`) проверяет только глобальный
`waSystemConfig::isDebug()` и настройку витрины `debug_panel` — без `wa()->getUser()->isAdmin('shop')`.

Живой замер 12.09.2026 (анонимный `curl` без кук): при `debug=true` (глобально) и `debug_panel=true` у
витрины `<script src=".../prefill.debug.js">` и весь бутстрап панели присутствуют на `https://wa-dev.loc/`
(главная страница каталога, не чекаут). Панель тянет `collectCurrentState()`
(`lib/classes/debug/shopPrefillPluginDebug.class.php:114-146`): уровень логирования, эффективную витрину,
`source_key`/`applied_source` (хэши), дамп текущей сессии чекаута (`storage_dump`).

## Область поражения

Только когда **оба** флага включены одновременно: глобальный Webasyst `debug` (dev-флаг, не должен быть
включён в проде) и настройка плагина `debug_panel` (по умолчанию off). При обычной эксплуатации ни один
анонимный посетитель это не увидит. Данные в дампе — собственная сессия визитёра (`storage_dump` — его же
чекаут, не чужой), плюс внутренние технические подробности плагина (уровень логирования, ключи источника).
Межпользовательской утечки нет — сессии не пересекаются. Действующие эндпоинты панели
(`force-prefill`, `clear-storage`, `reset-and-refill`, `refresh-debug`) отдельно защищены CSRF +
`isAdmin('shop')` (см. L2.4 в TEST-PLAN.md) — сама разметка инертна без них.

## Рекомендация

1. Решить осознанно: если панель должна быть видна только на чекауте и/или только админу — обернуть вызов
   `renderDebugPanel()` тем же `isCheckoutPage()` и/или добавить проверку `isAdmin('shop')` в
   `isDebugPanelEnabled()`. Если текущее поведение — сознательный замысел (диагностика гео/кук на
   каталоге тоже нужна) — зафиксировать это явно в `RULES.md` и добавить сценарий в TEST-PLAN.md
   (`L-0x | debug on + debug_panel=on + аноним, страница каталога`), чтобы дыра в покрытии не повторилась.
2. Проверка после фикса (если решили ограничивать): `curl -sk https://wa-dev.loc/ | grep -c
   plugins/prefill` = 0 при `debug`+`debug_panel` включённых.

## Связанное

Побочно обнаружено вместе со stand-находкой: на момент прогона глобальный `debug` был случайно оставлен
включённым после прошлой проверки на PHP 8.4 ([pre-release-checklist.md](../tests/pre-release-checklist.md))
— выключен как часть исправления базовой линии перед этим прогоном.
