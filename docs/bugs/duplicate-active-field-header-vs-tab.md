# Дублирующееся поле `[active]` в шапке страницы настроек и во вкладке «Основные настройки» — тумблер в шапке молча перебивает выбор пользователя

**Статус:** 🔴 Подтверждено в браузере 24.08.2026, не исправлено
**Приоритет:** 🟠 важно до продажи — тихая потеря выбора администратора в настройках плагина, без ошибки и без индикации в UI
**Связано:** найдено при браузерной проверке батчинга сохранения ([issue-74#5](../codereview/issue-74-minor-findings-pass-2.md#5-сохранение-настроек--по-select--update-на-каждый-лист-дерева---✅-закрыто)); сама правка тут ни при чём — баг воспроизводится и на предыдущем коде, дерево `$settings` из POST этой правкой не менялось

## Симптом (подтверждено в браузере 24.08.2026)

Настройки плагина, витрина «Общие настройки для всех витрин» (`storefront_code = '-'`), вкладка «Основные настройки». Тумблер «Применять общие настройки для всех витрин» изначально включён (в БД `active` = `"true"`).

1. Выключил тумблер в панели «Основные настройки» — переключатель визуально встал в состояние «выключено».
2. Нажал «Сохранить» — тост «Сохранено», ошибок нет.
3. Прямой запрос к БД (`shop_prefill_settings`, `storefront_code='-'`, `name='active'`, `groups='null'`): значение осталось `"true"`. `update_time` при этом обновился — строка гарантированно была перезаписана этим же сохранением, просто не тем значением, которое выбрал пользователь.

Тумблер во вкладке визуально показывает «выключено», реальное состояние в БД — «включено». Несоответствие переживает перезагрузку страницы (сервер возвращает то же сохранённое `true`, так что при следующей отрисовке тумблер снова окажется включён — то есть даже видимость «получилось выключить» не сохраняется).

## Причина

Одно и то же имя формы `{$name_prefix}[active]` рендерится **дважды**, независимо друг от друга, в двух разных шаблонах одной страницы:

- `templates/actions/settings/blocks/Header.html:4,6` — маленький переключатель без подписи рядом с заголовком `<h1>` страницы, рендерится **всегда**, вне зависимости от выбранной вкладки или витрины (инклюдится один раз в начале `Settings.html`, а не внутри вкладок):
  ```html
  <input type="hidden" name="{$name_prefix}[active]" value="false">
  <span class="switch" data-type="switcher">
      <input type="checkbox" name="{$name_prefix}[active]" value="true" {if ifset($settings['active']) == 'true'}checked{/if}>
  </span>
  ```
- `templates/actions/settings/blocks/tabs/General.html:49-56` — тот же field-name, отрисован через `components/Field.html` → `components/controls/Switcher.html`, внутри вкладки «Основные настройки», с подписью «Применять общие настройки для всех витрин» (глобальная витрина) / «Использовать индивидуальные настройки» (`setting.active`, витрина с индивидуальными настройками) и с обработчиком `on_change="prefillUpdateStorefrontStatus"`, которого у Header.html-варианта нет.

Оба варианта — классическая пара `hidden + checkbox` с одинаковым `name`: `hidden` даёт значение по умолчанию для случая «чекбокс снят» (не попадает в POST сам по себе), `checkbox` перекрывает его на `true`, когда отмечен. При одинаковом `name` в одной `<form>` браузер отправляет все 4 инпута одним набором пар `key=value`; PHP (`waRequest::post()`/`$_POST`) для повторяющегося ключа оставляет **последнее** значение в порядке следования полей при разборе тела запроса — побеждает то поле, чьи `hidden`/`checkbox` идут последними.

Header.html рендерится безусловно и не синхронизируется с General.html ни при инициализации, ни через `on_change` (у него его просто нет) — его чекбокс отражает то, каким `active` пришёл с сервера на **момент открытия страницы**, и остаётся в этом состоянии, даже если пользователь переключил видимый тумблер во вкладке. В зафиксированном прогоне финальное значение победило именно от Header.html (сервер получил `active` не тем, что выставил пользователь в General.html) — то есть по факту эффективный порядок полей в форме на момент сабмита ставит инпуты Header.html **после** инпутов General.html. Чем именно это гарантируется (порядок инклюдов в `Settings.html`, монтирование вкладок через JS/SPA-компонент `prefill-storefront-select`, или что-то ещё) — не выяснялось, для фикса это не важно: сам факт дублирования имени — уже достаточная причина сломанного поведения, независимо от того, кто выигрывает гонку.

Header.html — общий для страницы блок (не завязан на вкладку/витрину), поэтому те же два поля с тем же именем накладываются на **любую** выбранную вкладку/витрину, у которой отрисован свой `[active]`, — то есть коллизия актуальна и для витринного `active` (подпись «Использовать индивидуальные настройки», `setting.active`), не только для глобального. Отдельно этот случай (сохранение витринного `active`) не перепроверялся тем же чистым до/после-запросом к БД — воспроизведение зафиксировано только для глобальной витрины, но код-путь идентичный.

## Почему не поймали раньше

У переключателя в Header.html нет подписи — это просто иконка-тумблер рядом с заголовком страницы. Пользователь, ожидаемо, взаимодействует с подписанным контролом во вкладке «Основные настройки», а не с безымянной иконкой в шапке, поэтому пропажу изменения естественно спишешь на «не сохранилось» или «глюк UI», а не на то, что где-то есть второй, никогда не тронутый пользователем чекбокс с тем же именем.

## Направление фикса

Прежде всего нужно решить, что такое переключатель в Header.html:

- **Если это задумывался как быстрый дубль того же `active`** (удобство — переключить прямо из шапки, не заходя во вкладку) — у него не должно быть собственного `name`, участвующего в сабмите формы. Синхронизировать визуально с полем в General.html через JS (общий `id`/слушатель `change` в обе стороны), а в форму отправлять только одно, настоящее поле.
- **Если это не связанный с `active` элемент** (например, задел под будущий общий статус плагина, скопированный по ошибке с тем же именем) — просто убрать оттуда `name="{$name_prefix}[active]"` у обоих инпутов Header.html либо удалить блок целиком, если он ничего не показывает пользователю осмысленного (подписи нет, назначение не описано ни в одном из соседних `docs/`).

В любом случае: в DOM на момент сабмита должна остаться только одна пара `hidden`+`checkbox` с именем `{$name_prefix}[active]` — сейчас их две, и какая победит, зависит от порядка полей в форме, а не от того, что выбрал администратор.

## Как воспроизвести

1. `wa-dev.loc/webasyst/shop/?action=plugins#/prefill` → витрина «Общие настройки для всех витрин» → вкладка «Основные настройки».
2. Через MCP `mariadb` (или напрямую) зафиксировать текущее значение: `SELECT value FROM shop_prefill_settings WHERE storefront_code='-' AND name='active' AND groups='null'`.
3. Переключить тумблер «Применять общие настройки для всех витрин» в противоположное состояние, нажать «Сохранить».
4. Повторить запрос из шага 2 — значение не изменилось, несмотря на «Сохранено» в UI.
