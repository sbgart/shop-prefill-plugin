# Zen сворачивает группы, которые ядро не обработало из-за ошибки на шаге выше

**Статус:** ✅ Закрыт 19.08.2026. Пункты 1–5 реализованы и проверены (браузер + гостевой прогон), пункт 7 (документация) сделан. Посев кэша из `FillParams` отклонён — см. «Отвергнутые варианты», п. 6
**Приоритет:** 🟠 важно до продажи — покупатель видит «готовую» доставку, которой в форме нет
**Сложность фикса:** 🔧 средний — трогает `ZenMode`, `ZenData` и `CheckoutHooks`
**Подготовка:** ✅ [issue-59](../codereview/issue-59-html-key-marks-section-filled.md) закрыта 19.08.2026 — `SECTION_DATA_FIELDS` готов, блокеров не осталось
**Связано:** [issue-75](../codereview/issue-75-zen-collapse-without-toggle-button.md), [issue-72](../codereview/issue-72-snapshot-overwritten-by-empty-branch.md), [issue-56](../codereview/done/issue-56-zen-summary-no-escaping.md)
**Правила:** [RULES.md](../concept/RULES.md) — R1–R4, Z1–Z5

## Симптом

Всё заполнено, покупатель правит email так, что тот не проходит серверную валидацию
(`waEmailValidator`, сообщение «Почта введена неправильно»). После ответа сервера:

- секция **Покупатель** разворачивается с ошибкой — верно;
- секция **Доставка** остаётся **свёрнутой**, но сводка наполовину пустая: вместо названия способа доставки — одинокая точка-разделитель, остаётся только адрес;
- секция **Оплата** пропадает со страницы целиком (`display: none`), вместе с ней исчезает и кнопка «Изменить» этой группы;
- «Стоимость доставки: бесплатно», «Итого 18 000 ₽» и активная кнопка «Подтвердить заказ» остаются на месте — форма выглядит готовой.

## Замеры (19.08.2026, воспроизведение в браузере)

При активной ошибке email:

```
region   -> inputs: 6   display: block     (данные есть)
shipping -> inputs: 0   display: block     (пусто)
details  -> inputs: 0   display: block     (пусто)
payment  -> inputs: 0   display: none      (секции нет вообще)
zen styles: delivery, payment              (обе группы свёрнуты)
```

После исправления email тем же `waOrder.form.update()`:

```
region: 6 | shipping: 2 | details: 2 | payment: 6 — все display: block
```

`wa-log/prefill.plugin.log` в том же запросе с ошибкой:

```
Section 'shipping' skipped: already filled
Section 'details'  skipped: already filled
Section 'payment'  skipped: already filled
Snapshot saved  sections: [auth, region, shipping, details, payment, confirm, response]
Prefill was evaluated but no params were filled (empty final_params)
```

**Данные в сессии целы.** Потерян только рендер.

## Тот же пустой рендер бывает и без ошибок: `fast_render`

**Первая загрузка `/order/` устроена ровно так же.** [`formVars()`](../../../../lib/classes/checkout2/shopCheckoutViewHelper.class.php#L432) ставит `fast_render = true`, а [`shopCheckoutShippingStep::process()`](../../../../lib/classes/checkout2/shopCheckoutShippingStep.class.php#L22-L27) на этот флаг немедленно выходит:

```php
} elseif (!empty($data['input']['fast_render'])) {
    $errors[] = ['fast_render' => true];
    return ['errors' => $errors];
}
```

`errors` непусты → `can_continue = false` → `error_step_id = 'shipping'` → details и payment короткозамыкаются тем же механизмом, что и при ошибке email. Ради этого `getRegularErrors()` и отфильтровывает маркер `['fast_render' => true]` — иначе он читался бы как ошибка валидации.

Замер серверного HTML первой отрисовки (fetch `/order/`, до того как JS сходил за догрузкой):

```
auth     inputs: 6    ← заполнено
region   inputs: 6    ← заполнено
shipping inputs: 0    ← пусто
details  inputs: 0    ← пусто
payment  inputs: 0    ← пусто
zen styles: delivery, payment   (обе группы свёрнуты)
```

Тот же DOM после того, как JS дослал `calculate` с `use_session_input=true`:

```
auth: 6 | region: 6 | shipping: 2 | details: 2 | payment: 6
```

То есть **на каждой загрузке чекаута группы delivery и payment проходят через состояние «данных нет»** — и это штатная работа ядра, а не сбой. Сейчас это незаметно: правило «нет ошибок → свернуть» сворачивает их и на первой отрисовке (сводка мигает пустой), а на второй они уже наполняются.

## Механизм

1. `shopCheckoutAuthStep::getConfirmationErrors()` ([shopCheckoutAuthStep.class.php:208-215](../../../../lib/classes/checkout2/shopCheckoutAuthStep.class.php#L208-L215)) прогоняет `waEmailValidator` → `errors[]` → `can_continue = false`.
2. В [`shopCheckoutStep::processAll()`](../../../../lib/classes/checkout2/shopCheckoutStep.class.php#L245-L280) выставляется `error_step_id = 'auth'`, и у **всех последующих шагов `process()` больше не вызывается** — только `prepare()`.
3. Базовый `prepare()` при выставленном `error_step_id` делает `addRenderedHtml([], ...)` — рендерит шаблон секции с пустым результатом. Поэтому shipping / details / payment приезжают пустыми.
   Исключение — `shopCheckoutRegionStep::prepare()`: он делает всю работу в `prepare()`, поэтому регион рендерится нормально. Отсюда «половина сводки».
4. В [form.js](../../../../js/frontend/order/form.js#L2013) флаг `reload` каждой секции после любого апдейта сбрасывается обратно в `true`, поэтому на следующем `update()` все секции запрашивают свой `[html]` и получают пустой.
5. Наш [`shouldCollapseGroup()`](../../lib/classes/zenmode/shopPrefillPluginZenMode.class.php#L131-L147) решает сворачивать по правилу «в группе нет ошибок». Ошибка лежит в `auth`, значит в `delivery` и `payment` «ошибок нет» — и группы сворачиваются.

**Корень:** мы читаем молчание как «всё хорошо». У группы ниже упавшего шага ошибок нет не потому, что там порядок, а потому что её **вообще не валидировали**. Состояний три, а правило знает два.

## Наблюдение по куке

[`syncCollapseCookieState()`](../../lib/classes/zenmode/shopPrefillPluginZenMode.class.php#L384-L399) пишет `prefill_zen_{group}=expanded` при любом разворачивании, включая системное. Проверено: после починки email группа «Покупатель» осталась развёрнутой.

Это **не баг, а намеренное поведение** — иначе секция схлопывалась бы под руками у покупателя, который её как раз правит. Но с новым правилом сворачивания оно даёт побочный эффект на пустых группах, разбор — в пункте 6 плана.

## Целевое поведение

Причина всех трёх симптомов одна: **Zen спрашивает `$params` о том, чего `$params` не знает.**

`$params` описывает *текущий запрос*, а не состояние заказа. Он пуст всегда, когда конвейер шагов замкнуло — при ошибке выше по цепочке и при `fast_render` на каждой загрузке страницы. Значит вопрос «есть ли данные у группы» вообще нельзя задавать `$params`.

Но у плагина уже есть надёжный источник этого знания — сессия `shop/checkout`. Prefill читает её на каждом запросе и печатает результат в лог тем же `SectionChecker`, который нам и нужен:

```
Section 'shipping' skipped: already filled
Section 'payment'  skipped: already filled
```

Это работало корректно даже в тот момент, когда доставка на экране была пуста.

> **Зачем вообще нужен снапшот** — уточнение 19.08.2026, прежняя формулировка в [issue-72](../codereview/issue-72-snapshot-overwritten-by-empty-branch.md) («покупатель случайно очистил секцию — снапшот вернёт что было») сбивает с толку.
>
> Сессия чекаута не аддитивна: [`calculateAction()`](../../../../lib/actions/frontend/order/shopFrontendOrder.actions.php#L35-L38) кладёт `$session_checkout['order'] = $input` — **целиком заменяет** блок содержимым POST. А POST после короткозамкнутого рендера обеднён: секции приехали пустыми, браузер сериализовал пустоту и отправил обратно. Снапшот — теневая копия, переживающая такую перезапись.
>
> То есть он чинит **машинную** потерю данных, а не отменяет осознанную правку покупателя. Осознанную правку защищает `html` в ключевых полях (пункт 6), и эти два механизма не конфликтуют, а дополняют друг друга.

Правила, которые здесь применяются, живут в [concept/RULES.md](../concept/RULES.md): R1–R3 (рендер и состояние), Z1–Z4 (дзен-режим).

### Разделение источников

| Вопрос | Источник | Почему |
|---|---|---|
| **Сворачивать ли группу?** | сессия `shop/checkout` через `SectionChecker` | всегда достоверна, не зависит от короткого замыкания |
| **Есть ли ошибки в группе?** | `$params` | ошибки существуют только в рамках запроса |
| **Что показать в сводке?** | `$params`, иначе кэш | названия тарифов, цены и логотипы даёт только рендер |

Третья строка — единственная, где `$params` незаменим: сессия хранит **идентификаторы** (`shipping.type_id`, `payment.id`, поля адреса), а сводке нужны **названия**: «Бесплатная доставка курьером», «Бесплатно», логотип плагина. Их вычисляют плагины доставки и оплаты внутри `process()`, и при коротком замыкании их просто нет.

Отсюда решение: кэшировать последний удачный набор данных сводки и брать его, когда `$params` пуст.

## План правки

### 1. Решение о сворачивании — из сессии

`shopPrefillPluginZenMode` получает доступ к `getCheckoutParams()` и `SectionChecker` (оба уже есть у `SessionStorageProvider`, инжектится как остальные зависимости) и считает `isGroupFilled($group)` по списку **`SECTION_DATA_FIELDS`** — без служебного `html`, см. пункт 6.

Чтения сессии дешёвые: `waStorage` держит массив в памяти запроса.

> Понятие «короткого замыкания» при этом **исчезает из кода целиком**. Не нужны ни порядок шагов, ни `isSectionShortCircuited()`, ни `isFastRender()` — мы просто перестаём задавать `$params` вопрос, на который он не умеет отвечать.

### 2. Кэш данных сводки

`shopPrefillPluginZenData::extractSummaryData()` уже возвращает плоский массив скаляров под шаблон. Его и кэшируем в сессии (`shop/prefill_zen_summary/{group}`):

- в `$params` есть данные группы → рендерим из них и **записываем** массив в кэш;
- в `$params` данных нет → рендерим из кэша.

Кэшируем **массив, а не HTML**: смена шаблона или настроек витрины применяется сразу, в сессии не лежит разметка, и открытый [issue-56](../codereview/done/issue-56-zen-summary-no-escaping.md) про экранирование не расползается в хранилище.

Устаревание не опасно: кэш подставляется только когда в текущем рендере данных нет, а решение сворачивать в этот момент уже принято по сессии. Если покупатель очистил доставку — сессия скажет «пусто», группа развернётся, и кэш не понадобится.

**Первая отрисовка первого визита** — единственная оставшаяся дырка: кэш ещё пуст, `$params` пуст из-за `fast_render`. Планировался посев кэша из самого prefill — **отклонён**, разбор в «Отвергнутых вариантах», п. 6.

Со второй отрисовки и дальше мигание пустой сводкой не воспроизводится: кэш уже заполнен реальным рендером.

### 3. Минимум группы — только то, что переживает короткое замыкание

Проверять «все секции группы заполнены» нельзя. Замер 19.08.2026 показал, почему.

**Что происходит с сессией при коротком замыкании.** Сломал email и сделал подряд несколько `update`:

| Момент | `shipping` | `details` |
|---|---|---|
| до поломки | `type_id`, `variant_id` | `shipping_address.street` |
| сразу после | `type_id`, `variant_id` | `street` |
| после ещё двух `update` | `type_id`, `variant_id` | **`{"html":"only"}` — улица потеряна** |

Причина асимметрии: `Shipping.getData()` и `Payment.getData()` держат выбор в состоянии JS-контроллера и отправляют его даже при пустом DOM, а `Details.getData()` сериализует только форму — а форма после короткозамкнутого рендера пуста. Живая иллюстрация правила N1.

Ядро при этом адрес не теряет: `shopCheckoutDetailsStep::prepare()` хранит его отдельно в `details_address` и подставляет в форму. Проверено — после перезагрузки сводка показывала «Москва, ул Гостевая, д 1, кв 11», хотя в сессии у `details` не было ничего, кроме `html`.

**Вывод: `details.street` в минимум группы не входит.** Его теряет механика ядра, а не покупатель, — значит как признак «доставка выбрана» он ложный.

| Группа | Минимум |
|---|---|
| `customer` | `auth`: email, телефон или имя |
| `delivery` | **`shipping.type_id`** — и только он |
| `payment` | `payment.id` |

Три приятных следствия:

- **самовывоз без адресных полей больше не особый случай** — минимум выполняется по `type_id`, конфиг читать не нужно;
- `region` не нужен (ядро не даёт ему опустеть);
- пункт про `config['shipping']['used']` тоже отпадает. При выключенной доставке ядро выбрасывает вывод хука `checkout_render_details` целиком, вместе с CSS (issue-75), так что группа и сегодня не сворачивается. Разницы быть не должно — подтвердить в браузере, сценарий 5 в проверках.

### 4. Правило сворачивания

```
свернуть = группа включена
        И нет ошибок в группе       (из $params, как сейчас)
        И минимум группы заполнен   (из сессии, таблица в пункте 3)
        И cookie != 'expanded'
```

Порядок условий на результат не влияет — все три ветки дают «не сворачивать», а `syncCollapseCookieState()` в этом случае и так пишет `expanded`.

### 5. Кука — оставляем как есть, и это не опечатка

Прошлая редакция предлагала для причины «нет данных» **не писать** куку. Это давало схлопывание под руками: гость выбирает «Курьер» → `type_id` появляется в сессии → минимум выполнен → группа закрывается, пока он ещё выбирает вариант и вводит адрес.

Правильно ровно наоборот: ветка «нет данных» пишет `expanded`, так же как ветка ошибок. Тогда:

- гость открыл чекаут, доставка пуста → развернули, кука `expanded`;
- выбрал «Курьер» → минимум выполнен, но кука `expanded` → **группа остаётся открытой**, сколько бы `calculate` ни прошло;
- нажал «Свернуть» → JS удаляет куку → следующий рендер: минимум есть, ошибок нет, куки нет → сворачиваем.

То есть **`syncCollapseCookieState()` не меняется вообще**. Меняется только `shouldCollapseGroup()` — одним условием:

```php
if ($state->hasGroupErrors($group)) {        // Z1 — как сейчас
    return false;
}
if (!$this->isGroupMinimumFilled($group)) {  // Z2 — новое
    return false;
}
if ($cookie_state === 'expanded') {          // как сейчас
    return false;
}
return true;
```

Трёхзначная кука (`collapsed` отдельным состоянием) не нужна: раз ветка «нет данных» пишет `expanded`, отсутствие куки однозначно значит «сворачивать можно».

**Почему это не залипнет после ошибки валидации.** Опасение было такое: короткое замыкание опустошает группу → Z2 разворачивает → пишет `expanded` → после починки группа не свернётся никогда. Не сработает, потому что минимум delivery — это `type_id`, а он короткое замыкание переживает (замер в пункте 3). Ровно поэтому минимум и должен состоять только из устойчивых полей.

Существующее залипание при ошибках не трогаем — оно сделано намеренно, чтобы секция не схлопывалась под руками у того, кто её правит.

| Причина разворота | Кука |
|---|---|
| Клик «Изменить» | `expanded` |
| Ошибки в группе | `expanded` |
| Минимум не заполнен | `expanded` |

Известный предел: гость без истории получил `expanded`, потом залогинился в той же сессии и у prefill появились данные — группа не свернётся, пока он сам не нажмёт «Свернуть». Кука сессионная и гасится в `clearCookies()` при оформлении заказа, так что живёт это недолго.

## Отвергнутые варианты

**1. Детектировать короткое замыкание по `error_step_id` и порядку шагов.** Первая редакция этого плана. Работает, но требует знания порядка шагов, отдельной обработки `fast_render` и адаптера «снапшот → формат `$params`» для сводки. Пункт 1 достигает того же результата, не вводя ни одного нового понятия.

**2. Не выводить блок Zen, когда в `$params` нет данных группы.** Три строки кода. Но тогда на каждой загрузке страницы доставка сначала рисуется развёрнутой и пустой, а после догрузки схлопывается — скачок вёрстки на каждом визите. Хуже, чем сейчас.

**3. Чинить на клиенте: JS видит свёрнутую группу без полей и разворачивает её.** Гонки с перерисовкой секций ядром, зависимость от работоспособности JS в вещи, влияющей на возможность оформить заказ. Отказ.

**4. Фолбэк блока delivery на `checkout_render_shipping` (как обещано в ZEN-MODE.md).** Не нужен. Список шагов в [`getCheckoutSteps()`](../../../../lib/classes/checkout2/shopCheckoutConfig.class.php#L410-L435) захардкожен и безусловен — все шесть создаются всегда, настройки на состав не влияют. Хук `checkout_render_details` срабатывает либо через [`prepareFormVars()`](../../../../lib/classes/checkout2/shopCheckoutViewHelper.class.php#L465-L477) (безусловно по всем шагам, на рендерах `response=html`), либо через [`addRenderedHtml()`](../../../../lib/classes/checkout2/shopCheckoutStep.class.php#L360) (посекционно, если клиент запросил `[html]`). Эмпирически подтверждено: в замерах выше `details` отрендерился пустым, но тег `prefill-zen-styles-delivery` оказался внутри `.wa-step-details-section`.

Задумывался фолбэк на самом деле против другого: ядро **выбрасывает** вывод хука при `$details.disabled` или если кастомная тема потеряла `{foreach $event_hook.details}`. Это разобрано и закрыто в [issue-75](../codereview/issue-75-zen-collapse-without-toggle-button.md) — CSS теперь едет вместе с кнопкой. Плюс построить фолбэк и нельзя: в момент `checkout_render_shipping` неизвестно, отрендерится ли `details` дальше.

**5. Мешать ядру замыкать конвейер (подкладывать данные в `$data`, гасить `error_step_id`).** Это борьба с задокументированным поведением ядра на чужих инсталляциях. Проглотит настоящие ошибки валидации. Отказ.

**6. Посев кэша сводки из `FillParams` при первом предзаполнении.** Закрыл бы последнюю дырку — пустую сводку в первой отрисовке первого визита. Отклонён 19.08.2026 после разбора:

- окно жизни проблемы — **один запрос**: дальше приходит первый `calculate`, секции перерисовываются, и работает реальный кэш;
- цену (`shipping_rate`), срок, адрес ПВЗ, описание оплаты и логотипы посеять нельзя в принципе — их считает плагин доставки от корзины, в прошлом заказе их нет. Дефолтный шаблон доставки в это окно дал бы «**Название** • » с висящим разделителем;
- `FillParams::getPaymentName()` в проде был всегда `null` (сеттер не вызывался ниоткуда, кроме теста), хотя `payment_name` в `shop_order_params` лежит — то есть посев группы payment потребовал бы ещё и правки провайдера. **Обновление 19.08.2026:** провайдер починен в [issue-83](../codereview/done/issue-83-fillparams-payment-fields-never-set.md), `payment_name` и `payment_plugin` теперь заполняются. Этот довод против варианта 6 отпал; остальные (цена, срок, логотипы, окно в один запрос) в силе.

Цена — маппер, метод кэша, проводка в хук, тесты — против одного кадра. Не окупается.

## Как воспроизвести

Браузерная валидация `type="email"` не пускает запрос на сервер, поэтому руками словить сложно — нужен адрес, проходящий проверку браузера, но не `waEmailValidator`. Детерминированно:

```js
var i = document.querySelector('input[name="auth[data][email]"]');
i.type = 'text';
i.value = 'broken.address.without.at';
i.classList.remove('wa-error');
window.waOrder.form.update({});
```

Вернуть обратно: `i.type='email'; i.value='<валидный>'; window.waOrder.form.update({});` — состояние восстанавливается полностью, следов в БД не остаётся.

**Стенд для гостевых сценариев (4, 4a, 4b, 7).** Выход из бэкенда сессию чекаута не обнуляет, а файлы PHP-сессий недоступны — поэтому «чистый гость» делается curl-ом с пустой банкой кук:

```bash
J=guest.jar; rm -f $J
curl -sk -c $J -b $J https://wa-dev.loc/ -o /dev/null
curl -sk -c $J -b $J -X POST https://wa-dev.loc/cart/add/ -d 'product_id=847&sku_id=2268&quantity=1'
curl -sk -c $J -b $J -D headers.txt https://wa-dev.loc/order/ -o first-paint.html
```

Плюс метода: `Set-Cookie` видно напрямую (браузерные инструменты его не отдают), а состояние группы читается из HTML — наличие `id="prefill-zen-styles-{group}"` и класс кнопки (`prefill-zen-collapse` = «Свернуть», развёрнуто; `prefill-zen-expand` = «Изменить», свёрнуто). Дальше сценарий крутится через `POST /order/calculate/`: id типов доставки — `todoor` / `pickup` / `post`, вариант — `{shipping_id}.{rate_id}` (напр. `33.courier`), html секций запрашивается параметрами `{section}[html]=1`.
