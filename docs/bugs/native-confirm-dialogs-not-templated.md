# Диалоги подтверждения используют нативный `window.confirm()`, не шаблон плагина

**Статус:** исправлено 06.09.2026.

## Наблюдение (05.09.2026, прогон R, ФО-12, K-11)

При проверке кнопки «Очистить» (сброс `wa-log/prefill.plugin.log`) на вкладке «Отладка» админки
обнаружилось, что подтверждение — не собственный диалог плагина (`SaveScopeDialog` и подобные,
объявленные в `<template>` по конвенции CLAUDE.md), а нативный `window.confirm()` браузера.

Текст диалога сам по себе корректно локализован (`msgstr` в `.po`, читается через `$_()`/`config.messages`)
— это не рецидив уже закрытого [debug-panel-hardcoded-russian-strings.md](debug-panel-hardcoded-russian-strings.md)
(там речь была именно о нелокализованном тексте, эта проблема снята). Проблема именно в способе
показа: нативный диалог, а не шаблонный.

Найдено пять таких мест:

| Файл | Строка | Действие | Ключ локализации |
|---|---|---|---|
| `js/prefill.settings.js` | 539 | Сброс кастомного CSS к оригиналу | `dialog.css_reset.confirm` |
| `js/prefill.settings.js` | 798 | Очистить лог (`?module=prefillPluginSettingsClearLog`) | `msgClearConfirm` (аналогичный ключ) |
| `js/prefill.debug.js` | 212 | Плавающая панель: «Применить Prefill» (`force-prefill`) | `message('refill_confirm')` |
| `js/prefill.debug.js` | 214 | Плавающая панель: «Очистить и заполнить» (`reset-and-refill`) | `message('refill_confirm')` |
| `js/prefill.debug.js` | 216 | Плавающая панель: «Очистить сессию» (`clear-storage`) | `message('clear_confirm')` |

## Практическое следствие

Нативный диалог блокирует обработку `Input.dispatchMouseEvent`/скриншотов у CDP-based браузерных
инструментов автоматизации без выделенного JS-dialog-хендлера (в отличие от шаблонных диалогов
плагина, кликабельных как любой другой DOM-элемент) — обнаружено вживую **дважды подряд** при
проверке K-11/L-05: клик по «Очистить» (лог) и отдельно клик по «Применить Prefill» (`force-prefill`
на плавающей панели) оба подвесили вкладку до ручного подтверждения диалога человеком. Для
человека-пользователя функционально работает нормально, разница — в тестируемости и в
согласованности с собственной конвенцией проекта («не собирать HTML в JS», диалоги — через
`<template>`).

## Рекомендация (что переделать)

Не использовать `window.confirm()`/`window.alert()` в этом проекте вообще — ни в новом коде, ни при
доработке существующего. Вместо: свой шаблонный диалог подтверждения (по образцу `SaveScopeDialog.html`
из плагина `prefill` — `<template id="...">` + клонирование + подстановка текста через `textContent`,
как того и требует правило проекта «не собирать HTML в JS»). Разумный план:
1. Завести один переиспользуемый компонент-диалог подтверждения (шаблон + небольшой JS-хелпер,
   принимающий текст и колбэк на подтверждение) — не пять разных мест, а одна точка.
2. Перевести все пять мест из таблицы выше на него.
3. Заодно закрывает и тестируемость: шаблонный диалог — обычный DOM-элемент, кликабельный без
   специального dialog-хендлера в инструментах автоматизации.

## Не разбиралось

- Есть ли другие места в проекте с той же схемой за пределами перечисленных пяти.

## Решение (06.09.2026)

Не единый компонент на оба контекста — они живут в разных JS-средах, а не потому, что
поленились обобщить:

- **Настройки (`prefill.settings.js`, 2 места — CSS reset, очистка лога).** Контекст — бэкенд
  SPA, jQuery и `wa-content/js/dialog/dialog.js` уже подключены (использовались для
  `SaveScopeDialog`, issue-78). Добавлена `prefillConfirm(message)` — тот же `$.waDialog` +
  `<template>`-клонирование, что и у `SaveScopeDialog`. Шаблон —
  `templates/actions/settings/blocks/ConfirmDialog.html`
  (`#prefill-confirm-dialog-template`), подключён в `Settings.html`. Новые ключи локали:
  `dialog.confirm.ok`, `dialog.confirm.cancel`.
- **Плавающая панель (`prefill.debug.js`, 3 места — force-prefill, reset-refill,
  clear-storage).** Контекст другой: панель рендерится на любой странице (включая витрину),
  без гарантии jQuery — весь файл написан на чистом JS. Использован нативный `<dialog>`
  (`showModal()`/`close()`), а не `$.waDialog`. Разметка — `#prefill-debug-confirm` в
  `templates/debug/DebugStack.html`, вложена внутрь `<aside id="prefill-debug-stack">` (не
  рядом), чтобы унаследовать CSS-переменные темы (`--pd-*`) и `data-color-scheme` без
  повторной синхронизации — top-layer промоушен `showModal()` не рвёт обычное CSS-наследование
  по DOM-дереву, только stacking/overflow. Хелпер — `showConfirm(text)` в `prefill.debug.js`,
  `mutate()` теперь асинхронный (`Promise`). Новые ключи локали: `debug.confirm_ok`,
  `debug.confirm_cancel` (переданы во `window.PrefillDebugConfig.messages` из
  `shopPrefillPluginDebug::renderDebugPanel()`).

Оба места по-прежнему проверены вживую (браузер, K-11-подобный сценарий: клик по «Применить
Prefill» на плавающей панели и по «Очистить» лога в настройках) — вкладка не подвисает,
`Отмена`/крестик/Esc не выполняют действие, `Подтвердить` выполняет.

**Тёмная тема бэкенда** (`html[data-theme="dark"]`, переменные — `wa-content/css/wa/wa-2.0.css`):
у `$.waDialog`-диалога настроек (`.prefill-confirm-dialog`) фон и тень были захардкожены в
ядровом `wa-content/js/dialog/dialog.css` (`.wa-dialog-body{background:#fff}`) — сам компонент
`$.waDialog`/`wa-dialog` под тёмную тему не адаптирован (в отличие от более нового
`.dialog`/`.dialog-body` оттуда же, который уже на переменных). Плагин это не чинит глобально
(файл ядра, `wa-content/`, трогать нельзя) — вместо этого в `css/prefill.settings.css` добавлено
точечное переопределение только для `.prefill-confirm-dialog` под `html[data-theme="dark"]`,
теми же переменными, что использует актуальный `.dialog-body` (`--background-color-blank`,
`--dialog-background-color`, `--dialog-shadow-color`, `--text-color`). Проверено вживую в
тёмной теме бэкенда. Плавающей панели это не касалось — она с самого начала использует
собственную систему цветов (`--pd-*`, `data-color-scheme`) в `css/prefill.debug.css`, а не
`$.waDialog`, и её `<dialog>` уже наследует эти переменные, будучи вложенным в `.pd-panel`.
