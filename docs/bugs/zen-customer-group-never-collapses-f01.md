# Группа «Покупатель» (customer) не сворачивается в Zen-режиме на первом кадре

**Статус:** факт, не разобран.

## Воспроизведение (28.08.2026, прогон R, ФО-06, сценарий F-01)

1. Полностью свежая PHP-сессия (новый cookie jar, логин `admin`/`123` через `POST /webasyst/`, без
   переиспользования старых кук).
2. Контакт 1 (авторизованный покупатель) имеет полную историю заказов и все поля профиля заполнены:
   `firstname="Admin"`, `lastname="Admin"`, `phone="+7 (923) 111-22-33"`,
   `email="artem.shamberger@gmail.com"` — все непустые, `zen.active=true` (значение по умолчанию,
   переопределений в `shop_prefill_settings` нет).
3. Товар добавлен в корзину (`POST /cart/add/`), `GET /order/`.

**Ожидание (правило Z2, [TEST-PLAN.md](../tests/TEST-PLAN.md) F-01):** группы `customer`, `delivery`,
`payment` свёрнуты с первого кадра — все поля заполнены, свёртывать есть что.

**Факт:** группы `delivery` и `payment` свёрнуты корректно (`data-action="expand"`, показана сводка).
Группа `customer` — **не свёрнута**: рендерится с кнопкой «Свернуть» (`data-action="collapse"`),
то есть в развёрнутом виде, хотя все поля секции заполнены и данные не пустые.

Воспроизведено дважды подряд на двух независимых свежих сессиях (два разных cookie jar, два новых
логина) — не разовая гонка.

## Уточнение механизма (05.09.2026, повторная проверка на независимой свежей сессии)

Проверено ещё раз с нуля: новый cookie jar (`curl`), логин `admin`/`123` через `POST /webasyst/`,
`POST /cart/add/`, `GET /order/` — без какого-либо переиспользования браузерных кук. Результат
идентичен 28.08: в ответе есть `data-group="delivery" data-action="expand"` и
`data-group="payment" data-action="expand"` (обе свёрнуты), но никакого `data-group="customer"` —
группа `customer` не свёрнута. Повторный `GET /order/` в той же сессии (второй запрос, куки те же)
— то же самое, `customer` по-прежнему не сворачивается.

По логу (`wa-log/prefill.plugin.log`) на **первом** запросе этой свежей сессии видна строка:

```text
[DEBUG] Zen group 'customer' expanded: nothing to summarize yet
```

— то есть `isGroupMinimumFilled('customer', ...)` вернул `false` на первом кадре, хотя у контакта
(Admin, id=1) все поля профиля заполнены: проверка читает **параметры сессии чекаута**, а не
данные контакта напрямую, и на первый вызов эти параметры в сессии ещё не готовы (когда именно они
появляются в сессии для `delivery`/`payment` — не проверялось; сама секция при этом уже показывает
предзаполненные Имя/Фамилию/Телефон/Email на этом же первом кадре, то есть предзаполнение полей
формы и это конкретное условие сворачивания читают, по-видимому, разные источники).

Второй запрос той же сессии в лог **не** пишет `Zen group 'customer' expanded: ...` вообще (ни
одна из двух debug-веток `shouldCollapseGroup()` не сработала) — то есть решение принято по кука-ветке
(`shouldCollapseGroup()`, строка ~197: `if ($cookie_state === 'expanded') return false;`) без
захода в проверку данных. Причина — `syncCollapseCookieState()` (строка ~494): при **любом**
`is_collapsed === false`, независимо от причины, всегда проставляет `prefill_zen_customer=expanded`
на ответе. Один-единственный неудачный первый кадр (гонка «сессия ещё не прогрета») сам записывает
куку, которая на всех последующих запросах той же сессии **безусловно** удерживает группу
развёрнутой — механизм не различает «покупатель сам развернул блок руками» (штатное поведение,
см. F-03) и «сервер решил не сворачивать, потому что на тот момент не было данных».

Отдельно проверено: в уже «тёплой» браузерной сессии (много часов, десятки предыдущих запросов и
несколько реальных заказов в этой же PHP-сессии за сегодня — параметры чекаута в сессии заведомо
давно записаны) ручная очистка **только** куки `prefill_zen_customer` (`document.cookie = '...; expires=...'`)
и обновление страницы **дают корректно свёрнутую группу `customer`** — сама логика проверки
`isGroupMinimumFilled`/сворачивания для customer, если её не подставлять куки-веткой, работает
верно. Это не отменяет находку: в реальном сценарии (новый визит, новая сессия) кука выставляется
сама на первом же кадре и дальше липнет постоянно — баг воспроизводится каждый раз именно там, где
это важнее всего (первый заход покупателя).

## Не разбиралось

- Почему поле формы (Имя/Фамилия/...) на первом кадре уже предзаполнено, а
  `isGroupMinimumFilled('customer')` в этот же момент читает сессию как пустую — то есть какой
  именно источник использует предзаполнение полей и почему он недоступен (или ещё не записан) в
  момент проверки `shouldCollapseGroup()`.
- Совпадает ли момент появления данных в сессии для `customer` с моментом для `delivery`/`payment`,
  или у auth-секции просто самая ранняя точка проверки в общем рендер-пайплайне.
