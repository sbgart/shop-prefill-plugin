# Раннее предзаполнение на страницах витрины (`on_entry`)

**Статус:** вырезано из v1.0 18.08.2026 в рамках [issue-63](../codereview/issue-63-guest-hash-lookup-full-scan.md). Возвращать только по реальному запросу покупателя плагина.

Здесь сохранён и разбор того, почему функция была удалена, и готовый дизайн на случай возврата — чтобы не проходить исследование заново.

## Что это было

Настройка витрины `prefill.on_entry` (по умолчанию `true`). При включении `frontendHead()` вызывал `preFillCheckoutParams()` на **каждой** странице витрины — главной, категории, карточке товара, поиске, — чтобы checkout-сессия была заполнена ещё до того, как покупатель дойдёт до оформления.

Текст хинта в админке обещал: «Если включено, предзаполнение запускается при открытии страниц витрины. Если выключено — при открытии корзины. Полезно, когда цена в корзине зависит от способа доставки.»

Удалённые точки:

- `'on_entry' => ['value' => true, ...]` в `lib/config/storefront.settings.php`
- ветка `if ($this->storefront_settings['prefill']['on_entry'])` в `lib/classes/hooks/shopPrefillPluginFrontendHooks.class.php`
- переключатель в `templates/actions/settings/blocks/tabs/General.html`
- строки локали `setting.prefill.on_entry` и `hint.prefill.on_entry` в обоих языках

## Почему вырезано

Три независимых факта, каждый проверен по коду ядра.

### 1. Обещание про «цену в корзине» закрыто и без настройки

Корзина в checkout2 — это `/order/`, где `checkout_before_auth` срабатывает уже при отрисовке формы: `shopCheckoutViewHelper::formVars()` зовёт `shopCheckoutStep::processAll('form', ...)` (`wa-apps/shop/lib/classes/checkout2/shopCheckoutViewHelper.class.php:436`), а `processAll()` эмитит `checkout_before_<step>` (`wa-apps/shop/lib/classes/checkout2/shopCheckoutStep.class.php:243`). То есть форма приходит предзаполненной на первой же загрузке независимо от `on_entry`.

### 2. Обещание про «цены в каталоге» не выполнялось физически

`frontend_head` вызывается из лэйаута (`wa-apps/shop/lib/layouts/shopFrontend.layout.php:36-39`), то есть **после** того, как storefront-контроллер собрал `$content` и цены. Запись в сессию из этого хука не могла повлиять на текущую страницу — только на следующий запрос.

### 3. В стоковом Shop-Script предзаполненные секции вне чекаута не читает никто

Все чтения `shop/checkout` в ядре вне `checkout2/` касаются только ключей **верхнего уровня**, которых плагин не пишет:

| Место | Читает |
|---|---|
| `lib/classes/shopDiscounts.class.php:350` | `coupon_code` |
| `lib/actions/frontend/shopFrontendShipping.controller.php:118` | `coupon_code` |
| `lib/classes/shopAffiliate.class.php:258` | `use_affiliate` |

Плагин пишет в `['order'][<секция>]`. Пересечения нет. Мини-корзина считается через `shopCart::total()` → `shopDiscounts::calculate()`, куда уходит массив только из `currency` / `total` / `items` — способ доставки туда не попадает в принципе.

Установленные сторонние плагины проверены отдельно: `cityselect` в `shopCityselectHelper::setCity()` сам **пишет** `order.region` и `order.details.shipping_address.zip` при выборе города (то есть он писатель, а не потребитель предзаполнения), `bnpblocks` работает в чекаут-контексте и сам зовёт `processAll()`. Ни один не читает предзаполненные секции ради цены на каталоге.

### 4. Побочный вред

Запись сессии с каталожной страницы поднимала `session_is_alive` (`wa-apps/shop/lib/classes/checkout2/shopCheckoutViewHelper.class.php:439`), из-за чего Shop-Script считал checkout-сессию живой и не восстанавливал более свежую незавершённую форму из `localStorage`. С вырезанным `on_entry` этот конфликт исчезает сам.

**Итог:** функция не давала ничего из обещанного, но приносила полный проход по источнику данных на каждой странице каталога и глушила штатное восстановление формы.

## Когда возвращать

Единственный реальный сценарий: у покупателя плагина стоит сторонний плагин цен/скидок/доставки, который читает `shop/checkout['order']` на страницах каталога и меняет цену. Признак — жалоба вида «цена в каталоге не учитывает мою прошлую доставку».

Проверка перед возвратом:

```bash
grep -rn "shop/checkout" wa-apps/shop/plugins/ | grep -v "/prefill/"
```

Если потребитель действительно нашёлся — возвращать по дизайну ниже, а **не** в `frontend_head`: там оно не работает (см. п. 2).

## Дизайн на случай возврата

### Хук: `controller_before.*`

До запуска storefront-контроллера Shop-Script эмитит динамическое событие:

```php
// wa-apps/shop/lib/classes/shopFrontController.class.php:18-19
$handled = wa('shop')->event('controller_before.'.$class, $evt_params);
if ($handled) {
    return;
}
```

Проверено: маска `controller_before.*` поддерживается. `waEvent::getRegex()` превращает её в `/controller_before\..*/` (`wa-system/event/waEvent.class.php:789-791`), `isMask()` возвращает `true` (`:809-816`), после чего обработчик регистрируется в wildcard-корзине `self::$handlers['shop']['*']` и на каждом событии фильтруется через `isValidEventName()`. Перечислять главную, категорию, поиск и карточку по отдельности не нужно.

Накладные расходы приемлемы: регекс проверяется в `runPlugins()` на строке 221 — **до** `new $class(...)` на строке 239, поэтому объект плагина на чужих событиях не создаётся, платим одним `preg_match` на событие shop.

Порядок рендера при таком хуке:

```text
HTTP-запрос страницы витрины
  ↓
shopFrontController определил контроллер
  ↓
controller_before.*  ← здесь предзаполняем сессию
  ↓
storefront controller/action → цены и скидки читают уже обновлённую сессию
  ↓
layout → frontend_head → куки, remember-me, ассеты, debug
```

### ⚠️ Ловушка: обработчик обязан вернуть литеральный `null`

`shopFrontController` трактует непустой результат как «контроллер уже отработал» и **не рендерит страницу вообще**. В результат события попадает всё, что не `null`:

```php
// wa-system/event/waEvent.class.php:247
if ($plugin_result !== null) {
    $result[$result_key.'-plugin'] = $plugin_result;
```

Соседний хук плагина `handleFrontendHead()` возвращает `''` (пустую строку), и написать `return '';` по аналогии — самое естественное движение. Но `''` не `null`: он попадёт в массив, `$handled` станет истинным и витрина отдаст пустую страницу. Это надо вынести в PHPDoc обработчика и покрыть тестом.

### Гейты контекста

`controller_before.*` шире `frontend_head` — он срабатывает и для JSON/AJAX frontend-контроллеров. Обработчик продолжает работу только когда выполнено всё:

- `wa()->getEnv() === 'frontend'`
- плагин и effective storefront-настройка активны
- `prefill.on_entry === true`
- `$params['controller'] instanceof waViewController`
- запрос — обычный HTML-рендер витрины, не JSON-эндпоинт

Для checkout `calculate`/`create`, AJAX-эндпоинтов самого плагина и прочих JSON-контроллеров — ранний выход. Чекаут-путь остаётся за `checkout_before_auth`.

### Взаимодействие с маркером источника

Механика маркера описана в [issue-63](../codereview/issue-63-guest-hash-lookup-full-scan.md) и при возврате `on_entry` не меняется, но два правила становятся критичными:

1. **Маркер гейтит только обращение к БД, а не весь `preFillCheckoutParams()`.** Восстановление из снапшота обязано отрабатывать на каждом запросе — оно живёт в сессии и стоит ноль запросов.
2. **Для гостя без token-cookie маркер не пишется.** Иначе на каждой каталожной странице анониму и боту стартует PHP-сессия и уходит `Set-Cookie: PHPSESSID` — это ломает инвариант [issue-53](../codereview/issue-53-empty-prefill-writes-session.md). Отсутствие куки и так проверяется за ноль запросов, состояние для этого не нужно.

### Что остаётся принятым компромиссом

- При включённом `on_entry` заполнение новой сессии снова поднимет `session_is_alive` и подавит восстановление незавершённой формы из `localStorage`. Это цена функции, а не отдельный баг.
- `calculate` во время `on_entry` не запускается: полный checkout pipeline дёргает плагины доставки и оплаты и может заметно замедлить первое открытие каталога. В сессию переносится значение из прошлого заказа, а его применимость проверяет потребитель. Prefill не создаёт экземпляр отключённого плагина доставки только потому, что его ID сохранён в старом заказе.
- Full-page cache, отдающий HTML без запуска storefront-контроллера, нового состояния сессии не увидит — это внешнее ограничение кэша.

### План возврата

1. Вернуть `prefill.on_entry` в `lib/config/storefront.settings.php` со значением `false` по умолчанию.
2. Вернуть переключатель и строки локали; в хинте честно описать компромисс — функция нужна магазинам, где цены вне чекаута зависят от прошлого заказа, и добавляет работу на первом запросе новой сессии.
3. Зарегистрировать `controller_before.*` в `lib/config/plugin.php`, добавить гейты, обработчик всегда возвращает `null`.
4. Переиспользовать ленивый loader и маркер источника из issue-63 — новой логики предзаполнения писать не нужно.
5. Тесты: возврат `null` не ломает рендер; JSON-контроллер не запускает prefill; при `on_entry = true` потребитель сессии видит данные при расчёте цены первой страницы; при `on_entry = false` каталог не делает ни одного запроса к заказам.
