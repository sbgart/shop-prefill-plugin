# Актуализация дебаг-панели Prefill

Статус: реализовано 2026-09-05; статические проверки и основной гостевой сценарий в Chrome пройдены.
Дата: 2026-09-05.

## Реализованный транспорт AJAX trace

Render-хуки добавляют в собственный HTML скрытые `<template class="js-prefill-debug-carrier">`
со структурированными событиями текущего PHP-запроса. `MutationObserver` панели переносит
содержимое шаблона в историю страницы, группируя по `request_id` и сохраняя не более десяти
запросов. Механизм не перехватывает глобальные `fetch`/XHR, не меняет JSON-контракт ядра и
не пишет trace в checkout-сессию или БД. `refresh-debug` остаётся отдельным снимком текущего
состояния и не изображает новый checkout trace.

## Фактический результат

- Старая сводка по несуществующим `sections_*_status`, `BEFORE/AFTER` и `called_hooks` удалена.
- Панель показывает реальные события Prefill, payment/delivery echo, Zen и render-хуков. События
  группируются по PHP-запросам и ограничиваются десятью запросами на странице.
- Обычный рендер и `refresh-debug` больше не читают историю заказов. Для этого есть отдельный
  GET endpoint `prefill/debug-source`; его результат прямо подписан как диагностическое чтение.
- `ToggleZen` удалён вместе с маршрутом: панель больше не меняет настройку эффективной витрины.
- Изменяющие команды принимают только POST при глобальном debug, правах администратора Shop-Script
  и совпадающем CSRF-токене cookie/POST. Гостю эти кнопки не выводятся.
- Видимые строки перенесены в `shop_prefill` ru_RU/en_US; JS не содержит кириллицы и не собирает
  HTML через `innerHTML`.
- Интерфейс переведён на компактные карточки и семантические цветовые токены. Светлая/тёмная схема
  выбирается автоматически по состоянию темы Shop-Script и обновляется при её переключении.

## Подтверждённая исходная ситуация

1. `DebugStatusPanel.html` показывает `active` и `zen.active`, но не фактическое решение по секциям и группам.
2. Единственный актуальный вызов `addDebugEntry()` находится в `renderSectionErrorsAndDebug()`. Он передаёт данные render-хука и ошибки, но не `sections_prefill_status` / `sections_filled_status`. Таблица `Prefill Decision`, обработка `BEFORE/AFTER` и массив `called_hooks` остались от прежней реализации.
3. `refreshDebug()` заменяет три верхних блока. История render-хуков не обновляется и не помечается как старый запрос.
4. `collectDebugData()` самостоятельно вызывает `getFillParams()` и считает заказы. Поэтому просмотр диагностики загружает источник даже там, где рабочий checkout его лениво пропустил.
5. `ToggleZen` сохраняет `zen.active` эффективной витрины, включая глобальную `*`, а JS только обновляет панель.
6. Есть русский текст и HTML в JS/PHP, повторяющиеся дампы и вывод `print_r` без явного HTML-экранирования.
7. `isDebugPanelEnabled()` проверяет глобальный debug и `prefill.debug_panel`, без `isAdmin('shop')`. Команды очистки/заполнения/ToggleZen требуют debug и администратора. Не считать всю панель административной по предположению.

Эти факты повторно сверить перед правками: соседняя работа может изменить код.

## 1. Определить контракт диагностических данных

Основные файлы: `lib/classes/debug/shopPrefillPluginDebug.class.php`, `lib/classes/hooks/shopPrefillPluginCheckoutHooks.class.php`, `lib/classes/hooks/shopPrefillPluginFrontendHooks.class.php`, `lib/classes/sessionstorage/shopPrefillPluginSessionStorageProvider.class.php`, `lib/classes/zenmode/shopPrefillPluginZenMode.class.php`, актуальные `SectionChecker` и `CheckoutState`.

Ввести структурированную запись запроса вместо разбора строки заголовка регулярным выражением:

- `request_id`, время, тип запроса и последовательный номер события;
- этап: вход в checkout-хук, применение prefill, payment echo, delivery echo, render конкретной секции;
- контекст: текущая и эффективная витрина, fallback на `*`, настройки, режим гость/авторизован, состояние согласия;
- решения prefill по секциям и Zen по группам;
- изменения данных по путям и раскрываемый снимок конкретного этапа;
- результат/ошибки, а также явный признак, если этап не наблюдался.

Договориться в коде о трёх состояниях: значение известно, значение не вычислялось, чтение завершилось ошибкой. Не заменять последние два состояния на `false`, «нет заказов» или «пусто».

Собирать данные только при включённой панели. Коллектор должен переживать пересоздание экземпляра плагина внутри одного PHP-запроса, но не смешивать разные запросы. Не добавлять постоянные диагностические записи в БД или checkout-сессию. Ограничить размер снимков и число событий; усечение явно обозначать.

## 2. Записывать реальные решения Prefill и эхо-кэшей

В существующих местах принятия решений записывать причину и фактический результат. Не вычислять после рендера предположение о том, что «должно было» произойти.

Для Prefill фиксировать:

- доступность секции по текущим правилам `SectionChecker`, включая ограничения владения данными;
- источник отсутствует / уже обработан / реально загружен;
- ID заказа, только если он известен из реально загруженного источника;
- данных нет / данные применены / повторная обработка запроса пропущена;
- какие поля изменились в сессии и какие попали в живой `$params['data']['input']`.

Для payment и delivery echo отдельно фиксировать сохранение, восстановление, очистку или пропуск и причину. В сводке показывать доступные идентификаторы доставки, тарифа, пункта и оплаты. Не называть восстановление из эхо-кэша предзаполнением из заказа.

Убрать обязательные `getFillParams()` и подсчёт заказов из обычного открытия/обновления панели. Добавить отдельное действие «Загрузить данные источника» для чтения истории по явному запросу. Его результат подписать как диагностическое чтение, а не как источник, применённый checkout. Оно не должно сбрасывать маркер, применять данные или менять форму.

## 3. Записывать реальные решения Zen

Для `customer`, `delivery`, `payment` показывать:

- общую настройку Zen и настройку группы;
- состояние cookie группы;
- достаточность данных для сводки;
- ошибки группы, отложенные ошибки и `error_step_id`, когда доступны;
- был ли шаг обработан, пропущен конвейером либо выключен;
- фактическое решение и причину: свернуть, оставить открытым, не выводить;
- наличие сводки в ответе; состояние DOM указывать отдельно и только если оно реально измерено клиентом.

Решение брать из рабочей ветки Zen. Если для объяснения нужен общий evaluator, существующий метод должен использовать его результат, а не оставаться второй независимой реализацией правил. Не исправлять известное расхождение `zen.active` с поведением под видом диагностики.

## 4. Обеспечить актуальность при AJAX

До выбора транспорта проследить реальные ответы calculate/create и доступные plugin hooks, затем записать выбранный способ в этом документе. Использовать plugin-owned механизм передачи диагностического payload с тем же checkout-ответом, не менять ядро и не вмешиваться в обработку формы.

Обязательный результат:

- начальная загрузка и последующие calculate обновляют панель данными соответствующего запроса;
- запросы имеют ID, история хранится только на странице, максимум 10 запросов;
- новый ответ не смешивает старые ошибки/решения с новой сессией;
- отдельный `refresh-debug` помечается как чтение текущего состояния, а не новый checkout trace;
- если финальный результат или отдельный этап недоступен через существующие hooks, показывать «не наблюдалось», не выдавать последний render-hook за завершение всего конвейера;
- отсутствие диагностики в ответе и ошибка её загрузки не ломают checkout;
- учесть конкурентные AJAX-ответы: сохранять связь с запросом и не выдавать поздно пришедший старый ответ за новейший.

Не использовать глобальный перехват всех `fetch`/XHR страницы. Не вставлять диагностический HTML в контракт JSON ядра случайным `echo`.

## 5. Перестроить интерфейс

Файлы: `templates/debug/*.html`, `js/prefill.debug.js`, `css/prefill.debug.css`.

Порядок блоков:

1. **Контекст:** витрина → эффективная витрина, настройки, пользователь/гость, согласие, выбранный запрос и время.
2. **Предзаполнение:** компактная таблица секция → решение → причина → изменённые поля.
3. **Zen:** группа → фактическое состояние → причина.
4. **Доставка и оплата:** выбранные идентификаторы и события эхо-кэшей.
5. **Запросы и ошибки:** последовательность этапов и различия данных; полные дампы под раскрытием.
6. **Действия:** обновление состояния, явное чтение источника, очистка, повторное заполнение и настройки.

Удалить прежнюю таблицу `Cfg && Data && !Fill`, неиспользуемые поля `sections_*_status`, обработку `BEFORE/AFTER`, `called_hooks` и связанный мёртвый CSS после проверки всех ссылок. Новую историю строить по структурированным событиям.

Переименовать `Session Storage` в «PHP-сессия shop/checkout». Не отображать наличие ключа как доказательство заполненности или валидности.

Убрать постоянные успешные `alert()`, использовать статус внутри панели. Разметку, включая состояния загрузки/ошибки, вынести в Smarty-шаблоны; JS использует clone/DOM API и `textContent`. Заменить позиционные `nth-child` селекторы устойчивыми ID/data-атрибутами, inline onclick — обработчиками событий. Сохранять раскрытые блоки и прокрутку при обновлении.

Локализовать видимый текст PHP/Smarty/JS для ru_RU/en_US, включая подсказки и ошибки. Идентификаторы классов, секций и технические значения переводить не нужно.

## 7. Проверка и критерии приёмки

Перед изменениями зафиксировать поведение в реальном Chrome; после — выполнить ту же матрицу. Не создавать заказ без необходимости: для create-проверки использовать существующий тестовый сценарий и не запускать реальные платежи.

| Сценарий | Что подтвердить |
| --- | --- |
| Глобальный debug выключен / настройка панели выключена | Панель и сбор событий выключены, diagnostic endpoints недоступны |
| Гость без источника | Нет ложного «источник применён», автоматическое открытие панели не читает историю |
| Гость с историей, согласие в разных состояниях | Показанные условия совпадают с фактическими правилами, мутации недоступны гостю |
| Авторизованный пользователь с заказом | Реальный источник/ID, заполненные поля и причины пропуска совпадают с запросом и сессией |
| Повторный calculate | Маркер обработанного источника виден, панель не вызывает дополнительную загрузку истории |
| Смена доставки/региона и ошибка предыдущего шага | Prefill и echo различимы, идентификаторы соответствуют фактическим данным |
| Zen: ручное раскрытие, пустая группа, ошибки, выключенная группа | Причины отражают исполненную ветку, не желаемое поведение |
| Неактивная текущая витрина с fallback | Видно использование `*`, панель не меняет сохранённые настройки |
| Несколько AJAX-запросов и ручное обновление | ID/время и происхождение каждого блока корректны, история ограничена |
| Служебные действия администратором | Серверные ограничения действуют, результат соответствует подписи |
| Данные с HTML-символами и строкой `<script>` | Отображаются как текст, ничего не исполняется |
| ru_RU/en_US, узкий экран, раскрытые дампы | Переводы, читаемость и сохранение состояния работают |

Проверить PHP lint изменённых файлов, JS syntax check и `git diff --check`. Для выделенной логики решений/диффа допустимы небольшие содержательные проверки без внедрения нового тестового фреймворка; они не заменяют браузерную проверку.

Сравнить бизнес-результат checkout с включённой и выключенной панелью. Подтвердить по логам/счётчикам вызовов, что автоматический сбор не вызывает `getFillParams()` и запросы истории дополнительно к рабочему потоку. Проверить отсутствие ошибок JS/PHP.
