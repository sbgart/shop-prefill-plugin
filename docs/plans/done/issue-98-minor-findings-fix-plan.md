## 2. Нет индекса по `storefront_code`

**Файл:** `lib/config/db.php`

Проверено по истории: в [issue-57#4](../codereview/issue-57-minor-robustness-findings.md) (закрыт
21.08.2026, статус «⛔ не делаем») уже обсуждали индекс на этой таблице — но другой. Там отклонили
составной `UNIQUE (storefront_code, name, groups(191))` с переходом `set()`/`setBulk()` на
`INSERT ... ON DUPLICATE KEY UPDATE`. Причины отказа к нашему предложению не переносятся:

- префикс `groups(191)` не влезает в лимит ключа MyISAM (1000 байт: `303 + 152 + 576 ≈ 1031`) — у
  нас индекс только по `storefront_code` (`varchar(100)` в utf8mb3 ≤ 300 байт), с большим запасом;
- `UNIQUE` без правки записи превращает мягкую гонку (лишняя строка, сама схлопывается) в жёсткую
  (`waDbException`, 500 посреди сохранения формы) — обычный неуникальный индекс семантику записи не
  меняет вообще, `set()`/`setBulk()` не трогаются;
- префиксный индекс на `groups` ловит ложные совпадения (значения расходятся только в хвосте) — не
  про `groups`, эта часть не применима.

Единственное, что действительно переносится: правка `db.php` не доедет до уже установленных копий
(`CREATE TABLE IF NOT EXISTS` при `install()`). Для нас это не блокер — релиза не было, других
установок кроме локального стенда нет.

Добавить `'storefront_code' => 'storefront_code'` в `:keys`. Миграция не нужна — новые установки
получат правильную схему из `db.php` сразу. На локальном стенде таблица уже создана без индекса,
поэтому отдельно накатить `ALTER TABLE shop_prefill_settings ADD INDEX storefront_code
(storefront_code)` через MySQL MCP, чтобы код и стенд не расходились. Комментарий в `setBulk()`
(`lib/models/shopPrefillPluginSettings.model.php:45-46`) про отказ от `UNIQUE`/`ON DUPLICATE KEY`
остаётся верным — не трогать, он не про этот индекс.

**Риск:** низкий. **Объём:** минимальный (1 строка + один ALTER на стенде).

**Сделано 11.09.2026:** `db.php` дополнен, `ALTER TABLE ... ADD INDEX storefront_code
(storefront_code)` накатан на стенд через `mysql` CLI (MCP `execute` не пропускает `ALTER`).
Проверено: `information_schema.statistics` показывает новый неуникальный индекс, все 242 строки на
месте, 19 автотестов зелёные, сохранение формы настроек (`Основные настройки` → переключить и
сохранить тумблер) прошло без ошибок — `setBulk()` записал/перезаписал строки штатно, PHP-лог не
вырос ни на строку. `debug_panel` для всех трёх витрин не затронут.

## 3. `rememberMe()` без `cookie_domain` ядра — ЛОЖНАЯ НАХОДКА, закрыто без фикса

**Статус:** ❌ не баг. Предпосылка issue-98 («ядро в тех же местах берёт домен из конфига
авторизации») не подтвердилась при проверке 11.09.2026.

Прежде чем чинить, поискал в `docs/` прошлые обсуждения `cookie_domain`/`rememberMe` — ничего, кроме
самого issue-98. Дальше разобрал вопрос по коду ядра и живым тестом:

- `grep -rln "cookie_domain" wa-system/ wa-apps/ wa-config/` (кроме самого плагина) находит **только
  два файла**: `wa-system/auth/waAuth.class.php` (где ключ читается: строки 527, 740, 892, 947, 985)
  и `wa-system/storage/waSessionStorage.class.php` (это `session_cookie_domain` — из
  `session_get_cookie_params()`/php.ini, к `auth_token` отношения не имеет). **Ничто во всей
  установке никогда не кладёт `cookie_domain` в опции `waAuth`.**
- `waDomainAuthConfig` — класс, на который ссылается issue-98 и который плагин уже использует в
  `isDomainRememberMeEnabled()`. Прочитан целиком (1205 строк, `wa-system/config/waDomainAuthConfig.class.php`):
  метода `getAuth()` там нет, ни одного cookie-геттера нет. Только `getRememberMe()`/`setRememberMe()`
  (bool-флаг) и настройки формы входа/регистрации.
- `wa-config/auth.php` (реальный конфиг на стенде) — структура без ключа `cookie_domain` вообще
  (`auth`, `fields`, `params`, `route_url`, `app`, `rememberme`, `login_caption`, ...).
- Живая проверка: CLI-бутстрап `wa()`, `ReflectionProperty` на `$options` живого `wa()->getAuth()` —
  результат `{cookie_expire, is_user, login_field_ids}`. Ключа `cookie_domain` нет, значит
  `ifset($this->options['cookie_domain'], '')` в самом ядре тоже всегда резолвится в `''`.

**Вывод:** предложенный в issue-98 фикс («взять домен из того же источника, что и ядро») скопировал
бы пустую строку в пустую строку — no-op. Плагин уже ведёт себя идентично ядру, расхождения нет.
Описанное следствие (покупатель на соседнем поддомене остаётся гостем) реально, но это ограничение
самого Webasyst в мультидоменной установке — ядро тоже не делится `auth_token` между поддоменами
ни в одном известном пути, а не специфичный баг плагина.

**Решение (подтверждено пользователем 11.09.2026):** закрыть без фикса, код `rememberMe()` не трогать.
Если когда-нибудь понадобится реальное кросс-поддоменное SSO (сценарий `wa-dev.loc` +
`shop-1.wa-dev.loc`) — это отдельная новая фича плагина (явная настройка «домен cookie для remember
me», admin заполняет сам, зная свои домены), а не копирование несуществующего значения из ядра.

## 4. `prefill/logs` без метода/CSRF — план шире находки issue

**Статус:** ✅ реализовано 11.09.2026.

Перед реализацией искал прошлые обсуждения CSRF в проекте — нашёлся прямо релевантный
[issue-79](../codereview/issue-79-issue-52-csrf-half-done.md) (открыта, статус «сознательно
отложено» от 21.08.2026), но он про **другой** набор эндпоинтов: публичные `consent`,
`apply-delivery`, `fill-checkout-params`, доступные гостю. Там решили не добавлять токен именно
потому, что это требовало бы правок JS ради риска без эксплойта. Отложенное решение не
противоречит этому пункту — здесь четыре debug-эндпоинта, доступные только `isAdmin('shop')` при
включённом debug, из них три уже используют CSRF-токен (готовый механизм, не новый), четвёртый
(`Logs`) просто не был к нему подключён при копипасте.

**Файлы:** `lib/actions/frontend/*.controller.php` (4 шт.), `js/modules/Logger.js`

`_csrf` — не самопальная защита, это встроенный механизм ядра (`waAuthUser.class.php:106-107` в
`wa-system`, куку `_csrf` ставит фреймворк каждому визитёру, читаема из JS). Три соседних
дебаг-эндпоинта её уже проверяют, `js/prefill.debug.js` (панель админа) её и отправляет через свой
`mutate()`. А вот `Logger.js` (модуль, вызывающий `prefill/logs`) через `HttpClient.post()` **вообще
не прикладывает `_csrf`** — значит, если просто добавить проверку на сервере по образцу трёх соседей,
легитимные логи из `Logger` начнут получать `Access denied`.

План:
- вынести общий `isAllowed()` в новый базовый класс
  `lib/classes/frontend/shopPrefillPluginFrontendDebugBaseController.class.php` (по образцу уже
  существующего `shopPrefillPluginSettingsBaseController`), убрать три копии из
  `ClearStorage`/`ForcePrefill`/`ResetAndRefill`, подключить к нему `Logs`;
- в `Logs` добавить чтение `message` как `waRequest::TYPE_STRING` и вырезание переводов строк;
- в `Logger.js` добавить чтение куки `_csrf` (маленький `getCookie()`, как в `prefill.debug.js`) и
  передавать его в `httpClient.post('prefill/logs', {message, type, _csrf})` — иначе фикс сломает
  логирование с фронтенда.

**Риск:** средний — трогает и PHP, и JS, нужна ручная проверка в браузере (логи из чекаута по-прежнему
долетают при включённом debug).
**Объём:** средний.

**Сделано 11.09.2026:** добавлен `lib/classes/frontend/shopPrefillPluginFrontendDebugBaseController.class.php`
(по образцу `shopPrefillPluginSettingsBaseController` — `final execute()` с проверкой, `abstract
handle()`), `ClearStorage`/`ForcePrefill`/`ResetAndRefill` переведены на него без изменения
поведения (дословная копия `isAllowed()` удалена трижды). `Logs` подключён к тому же базовому
классу; `message` теперь читается как `waRequest::TYPE_STRING_TRIM` и чистится от `\r`/`\n`.
`Logger.js` — добавлен приватный статический `_getCsrfCookie()` (та же идиома, что в
`prefill.debug.js`) и отправка `_csrf` в теле POST.

Проверено: `php -l` на все 5 файлов чисто, 19 автотестов зелёные. Живьём в браузере (admin,
debug + debug_panel включены): реальный автоматический лог инициализации фронтенда
(`PrefillFrontendController initialized.`) дошёл до `wa-log/prefill.plugin.log` через
пропатченный `Logger.js` без правок урла — подтверждает, что фикс не сломал легитимный путь.
Ручной POST с `_csrf` — `200 {status:"ok"}`; без `_csrf` — `200 {status:"fail", errors:"Access
denied"}`, одинаково для всех четырёх эндпоинтов (`clear-storage`, `force-prefill`,
`reset-and-refill`, `logs`). `message[]=x` (бывший «Array to string conversion») — тихо
превратилось в пустую строку, PHP error log чист. Перевод строки в `message` — записался одной
строкой лога, подделать соседнюю запись не вышло. Кнопки debug-панели (`Очистить сессию`,
`Применить Prefill`, `Очистить и заполнить`) отработали как раньше — `Обработанный источник` в
панели переключился `user:1` → `—` после очистки, запросы вернули `200` без ошибок в PHP-логе.

## 6. `collectUniqueDeliveryOrderIds()` без потолка — ОТКЛОНЕНО

смысловой ошибкой: покупатель, полсотни раз подряд заказавший одним способом, терял редкий второй
адрес — он просто не попадал в окно `LIMIT 50`, а дедупликация схлопывала все пятьдесят одинаковых
заказов в одну карточку, оставляя четыре слота из пяти пустыми. Фикс 19.08.2026 заменил потолок по
заказам на добор страницами (`50 → 100 → 200 → 400`, `HISTORY_PAGE_MAX`) **до набора нужного числа
вариантов или конца истории** — специально чтобы редкий вариант из глубины истории не терялся.

`HISTORY_SCAN_MAX` из issue-98 — это тот же потолок по заказам под новым именем. Добавлять его —
значит откатить issue-68 и вернуть тот же баг с потерей редкого адреса, просто на большем окне (500
вместо 50). Путь срабатывает только по явному клику на «Мои варианты», не на каждой странице чекаута
(это отдельно подтверждено в issue-68 и не оспаривается issue-98) — стоимость без потолка признана
приемлемой уже тогда.

**Решение:** пункт закрыт как отклонённый, в реализацию не идёт.

Простые одноэлементные контейнеры без вложенной структуры (state-строки лога — пусто/загрузка/
ошибка, ошибка CSS-редактора) собраны через `document.createElement` без шаблона — правило не про
структуру, а про экранирование, а `textContent` не нуждается в нём вовсе.

Опциональные части (дата и meta-строка лог-записи, context-блок, desc/ex-head/ex/ex-code тултипа)
удаляются из клона через `.remove()`, если данных нет, а не оставляются пустыми — иначе flex-gap
и margin у пустого элемента добавили бы лишний отступ, которого не было в строковой версии
(проверено по CSS `.prefill-log-entry__rail`/`__meta`/`__context`, все с `gap`/`margin`). Meta-строка
(IP · user · JS-тег) собирается как раньше — раздельные узлы с разделителем `·` только между
реально присутствующими частями, а не `join()` по строке.

Тултип переменной (`prefill-var-tooltip`) — самое интересное место: `waTooltip`/Tippy.js принимает
`content` как DOM `Element` напрямую (`wa-content/js/tippy/wa.tooltip.js`:
`l(e.content)?(M(t,""),t.appendChild(e.content))`), без `allowHTML` и любого экранирования —
функция теперь возвращает не HTML-строку, а собранный `<div>`. `prefillEscapeHtml` не используется
нигде и удалён полностью, как и было целью правила.

`renderPreview()`: ошибка от сервера (`errors.join("\n")`) раньше уходила в `.replace(/\n/g,
'<br />')` перед вставкой через `.html()`; теперь `\n` остаётся в `textContent`, а перенос строк
рисует CSS `white-space: pre-line` на новом классе `.prefill-ct-preview-error__detail` — визуально
идентично, без единого тега в JS.
