# План: разворот, который не состоялся, ничего не ломает и не молчит

**Статус:** согласован с владельцем 20.09.2026, к реализации не приступали.

## Что чиним

| Находка | Симптом |
|---|---|
| 🔴 [zen-block-vanishes-on-stale-blocked-flag](../bugs/zen-block-vanishes-on-stale-blocked-flag.md) | Блок свёрнут, почта сломана, клик «Изменить» → блок исчезает с экрана целиком |
| Хвост F-36 в [zen-blocked-dialog-on-incomplete-step](../bugs/zen-blocked-dialog-on-incomplete-step.md) | Клик «Свернуть» при серверной ошибке → сервер не свернул, реакции нет |

**Причина одна:** клик решает, что делать, по разметке предыдущего рендера, а последствия не проверяет. Признаки ставит сервер, и к моменту клика они устаревают: уход из поля пересчёта с отрисовкой не вызывает.

## Правило (решение владельца)

1. Блок был **свёрнут**, разворот не состоялся → остаётся свёрнутым, плагин показывает предупреждение.
2. Блок был **развёрнут** → остаётся развёрнутым и пропадает вместе со скрытой секцией. Это поведение ядра ([payment.html:12](../../../../templates/actions-legacy/frontend/order/form/payment.html#L12)), плагин в него не вмешивается.

Узнать об отказе можно только после пересчёта: `test@mail..ru` клиентская проверка ядра пропускает, поломку видит только сервер.

## Часть 1: разворот — просьба, а не приказ

Сервер не отличает «попросил только что» от «было развёрнуто всё это время»: кука одна и та же. Разделяем значения.

| Значение | Пишет | Смысл |
|---|---|---|
| `expanding` | клиент по клику «Изменить» | просьба, одноразовая |
| `expanded` | сервер в `sync()` | состояние |

Просьбу сервер гасит на ближайшем рендере группы: развернул — переписал в `expanded`, отказал — снял куку. До следующего запроса она не доживает.

**Правки:**

- `ZenLatch` — константа `REQUESTED`, метод `isExpandRequested()`, `isExpanded()` признаёт оба значения;
- `ZenModeToggle.expandGroup()` — пишет `expanding`;
- `shouldCollapseGroup()` — ветка **перед** проверкой защёлки:

```php
if ($this->latch->isExpandRequested($group) && $state->getBlockingGroupFor($group) !== null) {
    // Просят развернуть, а шаг группы не считался: под скрытой секцией нет ни полей,
    // ни списков. Оставляем свёрнутым — сводка с данными покупателя никуда не денется.
    return true; // reason: 'expand_refused_blocked'
}
```

**Почему по `getBlockingGroupFor()`, а не по «шаг не считался»:** `isStepSkipped()` истинно и при `fast_render`, то есть на каждой загрузке `/order/` — отказ получал бы каждый клик.

**Почему перед защёлкой:** `isExpanded()` признаёт `expanding` и объявила бы группу развёрнутой раньше, чем мы успеем отказать.

## Часть 2: реакция на ответ сервера

Одна проверка после `form.update()` вместо `warnIfNothingToSummarize()` — она в неё входит.

| Клик | После обновления | Реакция |
|---|---|---|
| «Свернуть» | свернулась | ничего |
| «Свернуть» | развёрнута, есть `data-nothing-to-summarize` | диалог «нечего сворачивать» |
| «Свернуть» | развёрнута, признака нет | прокрутка к подсказке + общий диалог (F-36) |
| «Изменить» | развернулась | ничего |
| «Изменить» | осталась свёрнутой, есть `data-blocked-by` | прокрутка к блокирующей группе + общий диалог (F-37) |

Диалог во всех случаях один — тот же, что сегодня у оплаты, заблокированной невыбранным вариантом доставки. Там же клиент стирает свою метку `expanding` на случай, если ядро не перерисовало секцию-носителя.

Попутно: `User collapsed the ... group` пишется до пересчёта и лжёт, когда сервер не свернул. Запись о результате переезжает в эту же проверку.

**Проверено в ядре:**

- `update()` возвращает промис и до возврата навешивает перерисовку всех секций ([form.js:4057](../../../../js/frontend/order/form.js#L4057)) — наш обработчик видит свежую разметку; промиса нет → проверка молча не выполняется;
- `renderError()` ([form.js:3954](../../../../js/frontend/order/form.js#L3954)) только добавляет подсказку и не стирает чужую → серверная «Почта введена неправильно» переживёт наш вызов валидации, текст диалога останется правдой.

## Отвергнуто

1. **Показывать заблокированную развёрнутую группу сводкой** — блок, который сам сворачивается и сам разворачивается обратно, это магия (решение владельца).
2. **Хранить просьбу до лучших времён** — покупатель чинит почту и получает внезапно развернувшийся блок.
3. **Снять куку и обновить форму ещё раз** — второй запрос и мигание блока; отказ на сервере даёт то же без мигания.
4. **Спрашивать сервер перед кликом** — лишний запрос на каждый разворот.
5. **Снимать скрытие ядра для развёрнутой группы** — под ним пусто, это отвергнутый в B2b вариант.

## Риски

1. `isExpanded()` забудет `expanding` → разворот сломается совсем. Громко, ловится первым кликом и тестом.
2. Ветка встанет после защёлки → всё как сейчас, но тихо. Ловится F-37.
3. Условие съедет на `isStepSkipped` → отказ на каждый клик после загрузки страницы. Отдельный сценарий прогона.
4. Метка переживёт рендер → разворот сработает с опозданием. Подстраховано стиранием в части 2.
5. Ложный диалог от части 2 при чужом `data-blocked-by` в разметке. Ловится обходом здорового чекаута.
6. `warnIfNothingToSummarize()` надо заменить, а не поставить рядом, иначе два диалога на клик.

## Не чиним (осознанно)

- Группа, развёрнутая до поломки, пропадает с экрана — поведение платформы, 🔴 после правки сужается до него и переезжает в «известные особенности».
- Клиент по-прежнему судит по снимку сервера: лечим последствие, снимок устаревает всегда.

## Тесты

- `tests/ZenExpandRequestTest.php` — протокол куки и приоритет веток: `expanding` + блокировка → свёрнуто несмотря на защёлку; `expanding` без блокировки → разворот; `expanded` + блокировка → разворот сохраняется (случай 2 правила). Инстанс без конструктора через reflection, защёлка — наследник с подменённым чтением куки (образец — `ZenGroupCarrierTest`). Мутации: перенести ветку под защёлку; забыть `expanding` в `isExpanded()`.
- Клиентская часть автотестами не покрывается — сценарии F-36, F-37 и обход здорового чекаута без диалогов.
