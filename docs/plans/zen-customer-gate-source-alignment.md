# План: гейт группы `customer` спрашивает источник сводки, а не сессию

**Создан:** 08.09.2026
**Источник:** [f01 — группа «Покупатель» не сворачивается](../bugs/zen-customer-group-never-collapses-f01.md) — найдено 28.08.2026 при прогоне R (ФО-06), корень найден 08.09.2026
**Уточняет правило:** Z2 в [RULES.md](../concept/RULES.md), с оговоркой к R3
**Статус:** ✅ Реализовано и полностью проверено 08.09.2026 (этапы 1-5). Три прогона из раздела «Проверка» пройдены дважды — curl-ом и в живом браузере, результаты обоих — в файле бага; автотест `tests/ZenCustomerGateSourceTest.php`, 13 проверок; все 18 тестов плагина зелёные.

## Зачем

`shouldCollapseGroup('customer')` спрашивает `isGroupMinimumFilled()`, а тот — параметры сессии
чекаута: `order.auth.data.{firstname|phone|email}`
([SectionChecker:237](../../lib/classes/sections/shopPrefillPluginSectionChecker.class.php)).
Для **авторизованного** покупателя этих данных в сессии нет и не будет: предзаполнение auth-секцию
для него сознательно не пишет —
[SessionStorageProvider:627-630](../../lib/classes/sessionstorage/shopPrefillPluginSessionStorageProvider.class.php):

```php
// Для авторизованных пользователей auth данные берутся из контакта автоматически
if ($this->isUserAuthenticated()) {
    return;
}
```

В сессию `order.auth.data.*` попадает только из POST браузера (`calculateAction()` пишет POST
целиком), то есть **после** первого серверного рендера. Гейт отказывает всегда на первом кадре.

Сводка при этом читает совсем другое — `$state`, то есть `vars.auth.fields.*.value`
([CheckoutState:37-70](../../lib/classes/checkout/shopPrefillCheckoutState.class.php)), — и на том
же кадре он заполнен.

**Это не гонка.** Замер 08.09.2026: холодная curl-банка, авторизованный admin, `GET /order/`,
затем второй `GET /order/` в той же сессии с удалённой из банки кукой-защёлкой (чтобы снова
попасть в проверку данных):

```text
GET#1:  customer:collapse  delivery:expand  payment:expand
GET#2:  customer:collapse  delivery:expand  payment:expand
[DEBUG] Zen group 'customer' expanded: nothing to summarize yet   ← и на GET#2 тоже
```

Сессия не «прогревается». В HTML того же ответа поля заполнены реальными значениями:

```html
<input name="auth[data][firstname]" ... value="Admin">
<input name="auth[data][phone]"     ... value="+7 (923) 111-22-33">
<input name="auth[data][email]"     ... value="artem.shamberger@gmail.com">
```

(в браузере: `valueLen` 5/5/18/26 при `placeholderLen` 0/0/16/0 — значения, не плейсхолдеры).

Сворачивать было что, сводка отрисовалась бы верно — гейт спрашивает источник, который для этой
группы пуст by design.

### Откуда взялась проверка (история, 08.09.2026)

Дефект — регресс от 20.08.2026, и это меняет соблазнительный вывод «проверку добавили зря, снять её».

До `0fc4ab7` (20.08) в `shouldCollapseGroup()` проверки данных не было вовсе:

```php
if (! $this->isGroupEnabled($group))   return false;
if ($cookie_state === 'expanded')      return false;
if ($state->hasGroupErrors($group))    return false;
return true;   // всё, сворачиваем
```

Группа `customer` у авторизованного сворачивалась на первом кадре всегда, сводка бралась из
`$state` и была верна — поэтому f01 до 20.08 не существовал. Но свёрнутой оказывалась и группа
**гостя с пустой формой**: блок обещал «здесь всё готово», а за ним не было ничего. Против этого
19.08 (`4bfb0ac`) и написано Z2, а 20.08 (`0fc4ab7`) оно реализовано через `isGroupMinimumFilled()`.

То есть изменение 20.08 починило гостя и сломало авторизованного — единственной причиной стал
выбор сессии как прокси для «есть ли данные». Возврат к состоянию «до 20.08» вернул бы дефект Z2:

| | до 20.08 | сейчас | по этому плану |
|---|---|---|---|
| Авторизованный, полный профиль | свёрнут ✓ | развёрнут ✗ | свёрнут ✓ |
| Гость, пустая форма | свёрнут ✗ (пустое обещание) | развёрнут ✓ | развёрнут ✓ |

Оба столбца сходятся только в третьем варианте: `vars.auth.fields` у гостя пуст, у авторизованного
заполнен. Поэтому фикс — исправление источника проверки, а не её снятие.

## Решение

Для группы `customer` минимум считать по `$state` — тем же геттерам, из которых строится сводка, —
а не по сессии. `delivery` и `payment` не трогать.

```
shouldCollapseGroup('customer', $state)
  ├─ кука expanded?          → развернуть (Z4, без изменений)
  ├─ ошибки в группе?        → развернуть (Z1, без изменений)
  ├─ шаг auth не отработал?  → фоллбэк на сессию (B2a)
  └─ есть непустое среди firstname / phone / email в $state → свернуть
```

**Ветки по авторизации нет вовсе** — один предикат даёт верный ответ всем. Замерено 08.09.2026:

| Кто | `vars.auth.fields` | Предикат | Сегодня |
|---|---|---|---|
| Гость | поля есть, значения `''` | не заполнено → развёрнут | так же ✓ |
| Авторизованный | значения из контакта | заполнено → **свёрнут** | развёрнут ✗ |
| Стёр поле в форме | значение `''` | не заполнено → развёрнут | зависит от сессии |
| Короткое замыкание на `shipping` | значения на месте | решение не скачет | — |

Главное достоинство: гейт и сводка читают **один и тот же массив**. Расхождение между «свёрнуто»
и «в сводке пусто» становится структурно невозможным, а не «починенным» — сегодня их держат в
согласии два независимых источника, и они разошлись.

### Почему это не нарушение R2/R3

R3 разрешает брать из `$params` «отображаемые значения», и сводка уже берёт их именно так —
`$state->getFirstName()` и соседи. Спорно было одно: может ли отображаемое значение **решать**.

Рационал R3 — «`$params` пуст для секций ниже упавшего шага и при `fast_render`» — к этой точке
не применим по построению:

- `auth` — первый шаг чекаута, ниже упавшего он не бывает;
- `fast_render` выходит на `shipping`, то есть после `auth`;
- решение принимается в `handleCheckoutRenderAuth()` — хуке **внутри рендера самого шага**.
  Сработал хук → шаг отработал.

Проверено на коротком замыкании (`error_step_id = shipping`): в ответе `vars.auth.fields` полон.

R2 говорит про **состояние заказа**. «Есть ли что показать в сводке» — не состояние заказа, а
свойство рендера. Уточнение к Z2 это и фиксирует: предикат «нет данных» спрашивает источник
сводки, потому что именно правдивость сводки Z2 и защищает.

### Что фикс не трогает

- **Z4 (защёлка) не меняется.** Кука пишется и читается как сейчас; область её действия — отдельная
  задача, [zen-collapse-latch-outlives-php-session.md](../bugs/zen-collapse-latch-outlives-php-session.md).
- **`delivery` и `payment` остаются на сессии и эхо-кэше** — у них `$params` действительно пустеет
  (Z5, P9), и для них R3 работает ровно как написан.
- **R4 в силе:** кэш сводки по-прежнему только показывает. Предикат читает **свежий** `$state`,
  к кэшу не обращается — иначе устаревшие данные начали бы управлять формой.
- **Предзаполнение не трогаем.** Ранний `return` в `prepareAuthSectionParams()` остаётся: писать в
  сессию заказа ради решения об отрисовке — лечение симптома побочным эффектом (см. отвергнутый
  вариант 1).

### Тонкости, каждая ловится тестом

1. **Три поля, не четыре.** Минимум остаётся на `firstname`/`phone`/`email` — как в
   `SECTION_DATA_FIELDS['auth']` сегодня. `lastname` и `company` в сводке участвуют
   (`PRESENCE_FIELDS`, шаблон), но в минимум не входят и сейчас; расширять набор в этой задаче не
   нужно — это меняло бы семантику Z4 отдельно от исправления источника.
2. **Фоллбэк, а не «пусто».** `isStepSkipped('auth')` = `vars.auth === []` — шаг не отработал.
   Это неопределённость, а не пустота: по B2a отступаем на существующую проверку по сессии, а не
   объявляем «данных нет». На хуке `checkout_render_auth` случай недостижим, но гард обязателен —
   `shouldCollapseGroup()` публичный.
3. **Источник ровно один.** Когда шаг `auth` отработал, `$state` авторитетен и сессия **не**
   опрашивается. Опрашивать оба — вернуть два источника, ради устранения которых фикс и делается.

## Проверка

Три прогона, все обязательны:

- **Репро f01, curl.** Холодная банка → логин `admin` → товар в корзину → `GET /order/`:
  `data-group="customer" data-action="expand"` (свёрнут), в логе нет `nothing to summarize yet`.
  Внимание к методике: атрибуты у `customer` разнесены переводом строки — однострочный grep их не
  видит, смотреть `data-action`, а не наличие `data-group`.
- **Негативный, гость.** Чистая гостевая банка → `GET /order/`: группа развёрнута, в логе
  `nothing to summarize yet`, атрибут `data-nothing-to-summarize` на месте (не сломать фикс
  [соседнего бага](../bugs/zen-collapse-noop-when-section-empty.md)).
- **Негативный, Z4 посреди ввода.** Гость вводит имя → группа **не** схлопывается под руками
  (держит защёлка). Без этой проверки легко «починить» f01, сломав Z4.

Плюс существующие 14 автотестов и `ZenGroupCarrierTest`.

## Отвергнутые варианты

**1. Писать auth в сессию и для авторизованных** (убрать ранний `return` в
`prepareAuthSectionParams()`). Тогда существующий гейт работает без правок и R2 остаётся буквально
верным. Отвергнуто: это правка **пайплайна заказа** ради решения об отрисовке. `shop/checkout` —
то, из чего собирается заказ; цена ошибки максимальная из трёх вариантов, а выигрыш только в том,
что не нужно уточнять формулировку правила.

**2. Гейт читает контакт.** Ветка «авторизован → минимум по контакту». Отвергнуто: заводит
**третий** источник и с ним новый класс расхождений. Покупатель стёр телефон в форме — контакт
по-прежнему говорит «заполнено», сводка отрисует пустоту, прямое нарушение Z2. Лечится
обязательной проверкой `isSectionOwnedByCustomer()` перед обращением к контакту — две ветки и два
инварианта там, где у варианта из «Решения» ноль.

**3. Отложить решение до калькуляции, которая принесла данные.** Проверено вживую 08.09.2026 и
отвергнуто по трём независимым причинам:

- на загрузке `/order/` уходит **одна** автоматическая калькуляция, и `auth` она не несёт: в логе
  всех запросов визита `Section 'auth' can be prefilled`, а не `skipped: belongs to customer`;
- калькуляции с auth — только от взаимодействия (тоггл Zen, `onRegionChange`, `cartWatcher`,
  шаг доставки). Позитивный контроль: клик по тогглу → сразу `skipped: belongs to customer`;
- решающее — автоматическая калькуляция **не перерисовывает секцию `auth`**: zen-решения для
  `customer` в логе на ней нет вовсе, хук не сработал. Даже передумай сервер, обновлённый блок
  доставить некуда.

Механизм ядра, который выглядит как спасение, но им не является: `form.js` после каждого
пересчёта сохраняет всю форму в `localStorage` (`webasyst/shop/order/form`, там есть
`auth[data][*]` и `auth[html]`) и на инициализации воспроизводит её калькуляцией. Но
воспроизведение под флагом `use_storage: {if $session_is_alive}false{else}true{/if}` — только при
**мёртвой** сессии чекаута, а предзаполнение плагина отрабатывает в `checkout_before_auth`, то
есть до расчёта флага, и делает сессию живой. Замер: свежая PHP-сессия, снимок в `localStorage` на
месте → `customer` всё равно развёрнут, второго решения в логе нет.

## Смежное, вне этой задачи

- **Область действия защёлки** — [zen-collapse-latch-outlives-php-session.md](../bugs/zen-collapse-latch-outlives-php-session.md).
  Делать **после** этого фикса, отдельной правкой и отдельным прогоном: иначе не отличить, какой из
  двух дал результат. После f01 у авторизованного покупателя промах перестаёт возникать вовсе, так
  что защёлке будет нечего продлевать — но гостевой сценарий она закрывает независимо.
- **`use_storage` гасится собственной записью плагина** (см. отвергнутый вариант 3). Для f01 это не
  корень, но следствие шире: у витрин с prefill восстановление формы ядром из `localStorage`
  практически не работает никогда. В [issue-65](../codereview/issue-65-prefill-overrides-current-input.md)
  разобран «случай 11» — влияние на предзаполнение, — но не то, что флаг оказывается выключен
  всегда. Отдельной задачей, не здесь.
- **Витрина, где обязательное поле auth пусто у контакта.** Предикат срабатывает по любому одному
  полю, поэтому группа свернётся, а пустое обязательное поле спрячется до первого «Подтвердить
  заказ» (дальше сработает Z1 и развернёт группу с ошибкой). Тот же риск есть у варианта 2.
  `vars.auth.fields[*]['required']` лежит рядом со значением, то есть ужесточить предикат до «все
  обязательные заполнены» технически можно — но это меняет Z4 отдельно от исправления источника,
  поэтому не здесь. Проверить на стенде с `order_without_auth = false`.
