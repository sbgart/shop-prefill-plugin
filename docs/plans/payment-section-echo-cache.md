## Зачем

После снятия снапшота владение секцией `payment` держится только на `html` ([SectionChecker.class.php:48-55](../../lib/classes/sections/shopPrefillPluginSectionChecker.class.php#L48-L55)). Это верно останавливает предзаполнение из истории заказов, но как побочный эффект убрало и то, что снапшот когда-то чинил бесплатно: способ оплаты больше не переживает смену типа/варианта доставки.

Подтверждено в браузере 22.08.2026 на контакте Ивана (`user:1`), способ оплаты T-Касса уже выбран:

- Перехвачен реальный `XMLHttpRequest.send()` на `/order/calculate/` при клике по другому варианту доставки. Тело запроса: `shipping[variant_id]=33.courier`, `payment[html]=only` — **ключа `payment[id]` в POST нет вообще**, не пустая строка, а отсутствует;
- Секция «Оплата» в DOM тут же развернулась и показала все 6 способов без единого отмеченного;
- Лог плагина подтвердил решение: `Section 'payment' skipped: belongs to customer` → `Prefill was evaluated but no params were filled` — код работает ровно как спроектирован, просто спроектирован без памяти о том, что было мгновение назад.

Причина — в ядре, не в POST-е плагина. Оба места, где `payment` умышленно исключается из списка секций, отправляемых с реальными значениями:

```js
// Shipping.prototype.update — form.js:2003-2015, дёргается и при смене типа (form.js:1584),
// и при смене варианта (form.js:1640) — оба через that.update({reload:true})
that.scope.update({ sections: ["auth", "region", "shipping", "details", "confirm"] })

// onRegionChange — form.js:3600-3609
that.getFormData({ sections: ["auth", "region", "details", "confirm"] })
```

Других мест, где `getFormData()` получает явный список `sections`, в `form.js` нет — grep по всему файлу даёт ровно эти два совпадения. Значит `payment[html]==='only'` без данных возникает **только** от этих двух причин (плюс `that.disabled` — секция, которую сам виджет считает неактивной, см. ниже) — не от произвольной путаницы.

## Как отличаем «сбросило само» от «он сам очистил»

Ядро различает это самостоятельно, на уровне протокола, и плагин может просто прочитать различие:

```js
// Payment.prototype.getData — form.js:2637-2665
if (that.disabled) {
    result.push({name: "payment[html]", value: "only"});      // виджет неактивен
} else if (options.clean) {
    result.push({name: "payment[html]", value: "only"});      // секцию не спрашивали
} else {
    result = that.$form.serializeArray();                      // спросили — вот реальные поля
    if (!options.only_api && that.reload) {
        result.push({name: "payment[html]", value: 1});
    }
    ...
}
```

`html === 'only'` — секция сегодня не отправляла собственных полей, пустота ничего не говорит о намерении покупателя. Любое другое состояние (`html` отсутствует, `html === 1`, реальные поля в `serializeArray()`) — секция **говорила сама за себя** в этом запросе, и если результат пуст — это осознанный пустой выбор, трогать нельзя (P2, тест «ЩИТ ОТ РЕГРЕССА» в `SectionCheckerOwnershipVsDataTest.php`, блок 4).

Это уже используемое в проекте разделение — тесты сегодняшнего дня различают `['html' => 'only']` и `['html' => 1]` как разные фикстуры (блоки 2 и 5 того же файла). Новое здесь — только то, что мы читаем это различие ещё в одном месте.

## Согласование с B2a и отклонённым «мини-снапшотом»

Прямая цитата [B2a](../concept/RULES.md):

> Восстанавливать эти данные записью в `shop/checkout` — лечить симптом: правильный ответ на «не знаю» — развернуть, а не додумать.

И из «Отклонённые варианты» плана снятия снапшота:

> **Мини-снапшот на `shipping.type_id` и `payment.id`.** Устаревшие данные снова начинают решать: после смены региона старый `type_id` может быть недоступен, и свёрнутая группа соврёт (Z2). Тот же дефект, что у идеи «кэшировать вердикт». Отвергнут.

Это тот же класс риска, и делать вид, что его нет, было бы нечестно. Разница, ради которой этот план вообще существует:

1. **B2a — про «не знаю».** Здесь мы не гадаем: `html === 'only'` — не эвристика, а прямое следствие ровно двух перечисленных выше мест в ядре. Это проверяемый факт о текущем запросе, а не догадка о состоянии заказа.
2. **Самоинвалидация, которой не было у отклонённого варианта.** Кэш живёт, пока секция сама не заговорит и не скажет иное — в том числе пустотой. Как только `payment` придёт не-`only` и пусто (покупатель реально открыл секцию и ничего не выбрал), кэш чистится в том же запросе. Восстановленное значение не может пережить решение покупателя — именно этого не хватало «мини-снапшоту».
3. **Только `payment`, не `shipping`.** Риск из отклонённого варианта («старый `type_id` недоступен после смены региона») касался обеих секций. Для `shipping` он не снимается тем же трюком: у смены региона нет отдельного «настоящий/служебный» сигнала лучше того же `html`, а смена региона — редкое осознанное действие, и уже подтверждено в браузере (Этап 3 плана снятия снапшота), что честный сброс `shipping` там — верное поведение, не баг. Для `payment` источник боли другой: покупатель листает варианты **той же** доставки, ничего не решая заново, а секция оплаты дёргается на каждый клик.
4. **Остаточный риск не закрыт этим планом целиком, а сужен.** «Устаревшее значение может быть недоступно под новый выбор» — не снимается пунктами 1-3, потому что они про **когда** восстанавливать, а не про **валиден ли** восстановленный `id` под новую доставку. Это ровно то, ради чего ниже отдельный Этап 0 — без него читающая часть кэша не включается.

Правило записывается как **P9** — узкое, проверяемое исключение из B2a, а не отмена его логики. Формулировка — в Этапе 6.

## Дизайн

Один новый ключ сессии, по образцу уже существующих (`SOURCE_KEY`, `PENDING_AUTH_KEY` в [SessionStorageProvider.class.php:14-21](../../lib/classes/sessionstorage/shopPrefillPluginSessionStorageProvider.class.php#L14-L21)):

```php
private const PAYMENT_ECHO_KEY = 'shop/prefill_payment_echo';
```

Хранит весь «лист» секции без `html` — `id` и, если есть, `custom` ([SessionStorageProvider.class.php:399-404](../../lib/classes/sessionstorage/shopPrefillPluginSessionStorageProvider.class.php#L399-L404) показывает, что у `payment` оба поля, не только `id`).

Алгоритм на каждый `checkout_before_auth` (псевдокод, метод условно `syncPaymentEcho()`):

```
$payment = $checkout_params['order']['payment'] ?? [];
$html    = $payment['html'] ?? null;
$id      = $payment['id']   ?? null;

если группа payment выключена в настройках (isGroupEnabledForSection('payment') === false):
    ничего не делаем — мерчант явно отключил plugin-логику для этой группы

если html === 'only':
    если $id пуст:
        читаем эхо-кэш
        если в кэше есть значение — сливаем его в order.payment (id + custom, html остаётся 'only'),
        setCheckoutParams(), возвращаем восстановленный кусок для текущего рендера, логируем restore
    (если id почему-то не пуст при html==='only' — по протоколу ядра так не бывает; не трогаем)
иначе (html отсутствует, === 1, или пришли реальные поля — секция говорила сама):
    если $id не пуст — пишем эхо-кэш = текущие payment.id (+ custom), это подтверждённый выбор
    если $id пуст — чистим эхо-кэш: покупатель сам оставил секцию пустой
```

**Куда встраивается.** Не через `applyPrefill()` — `payment` там никогда не попадёт в `$available` (владение = `html`, а `html` держится вечно после первого рендера), и это правильно, трогать этот путь не нужно. Отдельный вызов из [`CheckoutHooks::handleCheckoutBeforeAuth()`](../../lib/classes/hooks/shopPrefillPluginCheckoutHooks.class.php#L57-L83), рядом с существующим вызовом `preFillCheckoutParamsFromSource()`, а не внутри него. Никакой проверки совместимости перед восстановлением не требуется (см. «Довешено 22.08.2026» выше) — подставляем безусловно, дальше решает ядро на `/order/create/`, как решало бы и без плагина.

**Отражение в текущий рендер.** Восстановленные данные нужно не только сохранить в сессию, но и подставить в `$params['data']['input']['payment']` **этого же запроса** — иначе `checkout_render_payment` в этом же цикле нарисует пустую секцию, хотя в сессии уже есть значение (ровно тот разнобой, который тестировался и был честным в Этапе 3 плана снятия снапшота, но здесь стал бы просто новым багом).

Готовый путь для этого есть — `shopPrefillCheckoutState::applyPrefillInput()` ([shopPrefillCheckoutState.class.php:813-825](../../lib/classes/checkout/shopPrefillCheckoutState.class.php#L813-L825)) делает ровно такой merge. **Но переиспользовать его не стоит**: он попутно выставляет `$this->is_prefilled = true`, а этот флаг уже отмечен как ненадёжный (план снятия снапшота, Этап 5: «починить врущий флаг `is_prefilled`»). Подмешивать в него ещё и «восстановлено эхом» — не то же самое, что «предзаполнено из истории заказов», и без явного решения только усложнит будущий фикс. Проще слить `deepMergeArrays()` напрямую в `handleCheckoutBeforeAuth()`, в обход `applyPrefillInput()`, до отдельного решения по Этапу 5 того плана.

**Где чистится кэш целиком** (не только «одиночная» чистка при пустой отправке из алгоритма выше):
- при создании заказа — [`OrderHooks::handleOrderActionCreate()`](../../lib/classes/hooks/shopPrefillPluginOrderHooks.class.php#L44), рядом с уже существующим `$this->zen_mode->resetState()` (строка 72) и `clearSourceMarker()`;
- при явной очистке формы — [`FrontendConsent`, case `clear_form`](../../lib/actions/frontend/shopPrefillPluginFrontendConsent.controller.php#L53-L58), рядом с `wa()->getStorage()->remove('shop/checkout')`.

Оба места — там же, где сегодня чистится всё остальное состояние чекаута; отдельного нового жизненного цикла не заводим.

## Этапы

### Этап 0. Проверить, что делает ядро с «устаревшим» `payment.id` — ✅ выполнено 22.08.2026

Проверено гостевой сессией через `curl` с чистой банкой кук (см. CLAUDE.md) напрямую на `/order/calculate/`, без браузера и без кэша — товар 914/2408, регион Москва (`rus`/`77`).

**Нашлась настоящая, не выдуманная несовместимость** на этой инсталляции: способ оплаты `22` (ЮKassa) в `data.payment.methods["22"].options.shipping_type = {pickup, todoor}` — **без `post`**. Остальные пять способов доступны во всех трёх типах. Это конфигурация самих платёжных плагинов (`shop_payment_plugin.options`), не что-то специально подстроенное для теста.

Три прогона одним и тем же гостем подряд:

1. `todoor/33.courier` + `payment[id]=22` → принято чисто: `selected_method_id: 22`, ошибок нет.
2. `todoor/34.delivery` (**другой вариант того же типа**, целевой сценарий этого плана) + `payment[id]=22`, как если бы это сделал будущий кэш → принято чисто: `22` всё ещё есть в `methods`, `selected_method_id: 22`, ошибок нет. Именно ради этого случая план и затевался — работает.
3. `post/36.parcel` (**тип, где `22` недоступен**) + `payment[id]=22`, эмуляция эха при несовместимости → `error_step_id: payment`, `errors: [{payment[id]: "Выберите способ оплаты"}]`, `22` **отсутствует** в `data.payment.methods`, но `selected_method_id` всё равно эхом вернул `22` — сырое значение из POST, без проверки.

**Довешено 22.08.2026 — проверка ошибочного вывода выше.** Первая версия этого раздела утверждала, что несовместимый `payment[id]` даёт покупателю *видимую* ошибку хуже сегодняшнего состояния — это оказалось неверно, поймано вопросом «а зачем нам вообще гадать совместимость, пусть ядро само решает». Перепроверено прицельно на двух вещах, которые раньше не смотрел:

1. **Сам HTML секции** (`data.payment.html`, то самое, чем `Shipping.prototype.render()` заменяет DOM) — в несовместимом случае это чистый список способов оплаты **без единого отмеченного и без текста ошибки внутри** (`checked count: 0`, поиск «шибк»/«не выбран» — ничего). `errors`/`error_step_id` — отдельная структура верхнего уровня, в саму секцию не подмешивается.
2. **Полная перезагрузка страницы** в этом состоянии (не AJAX, реальный `GET /order/`, Иван, `user:1`) — секция «Оплата» рендерится ровно как сегодня без кэша: список способов, ничего не выбрано, никакой ошибки на экране. Визуально неотличимо от обычного «покупатель ещё не выбрал».
3. **`POST /order/create/`** с тем же несовместимым `payment[id]=22` при `post`-доставке — `order_id` нет, ответ `error_step_id: payment`, `"Выберите способ оплаты"`. Заказ не создаётся, покупателя корректно тормозят на финальном шаге — **тем же самым текстом**, что он увидел бы, вообще ничего не выбрав.

**Значит `errors`/`error_step_id` — это сигнал для шага «Подтвердить заказ», а не для рядового пересчёта.** На обычной перерисовке секции (в том числе при смене доставки) он никак не проявляется — ни в подменяемом HTML, ни визуально. Слепое эхо несовместимого `id` неотличимо от сегодняшнего «просто пусто»: и то и другое рендерится одинаково нейтрально, и в обоих случаях `/order/create/` одинаково не даст оформить заказ без осознанного выбора.

**Исправленный вывод: гадать совместимость самим не нужно вообще.** Подставляем кэш безусловно; если он всё ещё подходит — ядро принимает и Zen сворачивает; если не подходит — ядро тихо не подставляет выбор (как сегодня без кэша), а на попытке оформить заказ настоящая, честная валидация уже стоит на месте и не зависит от плагина. Раздел «Этап 0b» ниже — по той же причине не нужен, оставлен зачёркнутым для истории решения, а не как открытая задача.

### ~~Этап 0b. Где технически проверять совместимость~~ — снят 22.08.2026, был основан на неверной посылке

Оставлено как есть, зачёркнуто, а не удалено — сам ход рассуждения был обоснованным на момент написания и может пригодиться, если когда-нибудь понадобится **реальная** проверка совместимости для другого сценария. Но применительно к этому плану — не нужен: как показал раздел «Довешено 22.08.2026» выше, ядро само является достаточным и единственно верным судьёй совместимости на шаге `/order/create/`, а на рядовом пересчёте вопрос вообще не встаёт (несовместимое эхо рендерится так же нейтрально, как и отсутствие эха). Специально проверять что-либо в `checkout_before_auth` до восстановления — не нужно.

Список актуально доступных методов (`data.payment.methods`, с которым сверялся Этап 0) — это `$params['vars']['payment']['methods']` в терминах плагина (тем же путём уже читают `shopPrefillCheckoutState::getPaymentMethodName()/getPaymentLogoUrl()`, [shopPrefillCheckoutState.class.php:522,541,581](../../lib/classes/checkout/shopPrefillCheckoutState.class.php#L522)). Ядро вычисляет его **во время обработки шага `payment`** в `processAll()` — то есть он существует к моменту хука `checkout_render_payment`, но не раньше.

А `CheckoutHooks::handleCheckoutBeforeAuth()` — единственное место, где восстановление может повлиять на **сам выбор** (записать `payment.id` в `$params['data']['input']` до того, как ядро отрисует радиокнопки) — срабатывает **перед обработкой шага `auth`**, то есть до шагов `shipping` и `payment` в этом же запросе. На этой стадии `vars.payment.methods` ещё не существует.

Получается разрыв: точка с данными о совместимости (`checkout_render_payment`) технически **не может** повлиять на уже отрисованную ядром разметку способов оплаты — хук в этой точке только добавляет HTML **в конец** секции (блок Zen Mode), он не участвует в рендере самих radio-кнопок. Точка, которая может повлиять на выбор (`checkout_before_auth`), не знает, что ещё доступно.

Старый (снапшот-эры) префилл этой проблемы не имел: `shipping` и `payment` восстанавливались **из одного и того же исторического заказа одновременно**, поэтому пара была по построению совместима — валидировать было нечего. Эхо-кэш восстанавливает `payment` отдельно от **свежего** выбора `shipping`, поэтому совместимость пары никем не гарантирована, и это первый случай в проекте, где она реально нужна.

Рабочая гипотеза (не проверена вживую, проверить первым делом в Этапе 2): `shopPrefillPluginPluginsProvider::getPaymentMethods()` ([shopPrefillPluginPluginsProvider.class.php:32-44](../../lib/classes/fillparams/shopPrefillPluginPluginsProvider.class.php#L32-L44)) читает **статическую конфигурацию** инстансов способов оплаты (`shop_payment_plugin`), включая `options.shipping_type`, — то же самое поле, что и в `vars.payment.methods[id].options.shipping_type`, только не привязанное к текущему рендеру. Если это так, доступность можно проверить **в `checkout_before_auth`**, не дожидаясь рендера: взять `shipping[type_id]` из текущего запроса (он там уже есть — это ровно то, что поменял покупатель) и свериться со статическим `shipping_type` кэшированного способа оплаты, без обращения к вычисляемым на рендере `vars`.

Если гипотеза не подтвердится — придётся либо отказаться от точного восстановления в тот же рендер (и решать проблему на уровне «предложить заново после следующего пересчёта», что хуже и, вероятно, не стоит усилий), либо искать другую точку данных. Это главный технический риск плана — весомее, чем то, что описывалось на момент написания черновика.

### Этап 1. `SectionChecker::isSectionMechanicallyClean()`

Новый public-метод, узкий и pure (та же категория, что весь остальной класс — легко покрывается юнит-тестом без Webasyst):

```php
public function isSectionMechanicallyClean(string $section_id, array $checkout_params): bool
{
    return ($checkout_params['order'][$section_id]['html'] ?? null) === 'only';
}
```

Тест — новый блок в `tests/SectionCheckerOwnershipVsDataTest.php` (или отдельный файл, если авторы посчитают тему обособленной): `html==='only'` → true, `html===1` → false, `html` отсутствует → false, для всех шести секций (метод общий, используем сейчас только для `payment`).

### Этап 2. Эхо-кэш в `SessionStorageProvider`

### Этап 8. Проверить в браузере

Повторить ровно сегодняшний сценарий (контакт с выбранными доставкой и оплатой, смена варианта доставки в пределах того же типа) и убедиться, что:

1. способ оплаты остаётся выбранным и секция не разворачивается после смены варианта;
2. смена **типа** доставки на тот, где прежний способ оплаты недоступен (см. Этап 0) — ведёт себя так, как решено по итогам Этапа 0 (честно сбрасывается либо валидно подставляется, но не протаскивает недопустимое значение до заказа);
3. покупатель, реально открывший секцию оплаты и оставивший её пустой (клик по «Изменить» → ничего не выбрано → смена доставки ещё раз) — оплата **не** восстанавливается, кэш не воскрешает то, что покупатель сам отверг;
4. создание заказа очищает кэш — следующий заказ того же браузера не подхватывает чужой старый способ оплаты;
5. `clear_form` (если доступна кнопка в UI/debug-панели) тоже чистит кэш.

## Открытые вопросы

- Название ключа/методов — рабочее, не финальное («эхо» выбрано, чтобы не путать со снятым снапшотом; можно предложить другое).
- ~~Реакция на «недоступный восстановленный способ оплаты»~~ — закрыто Этапом 0: код не нужен, ядро само фильтрует на рендере и блокирует на `/order/create/`.
- Стоит ли когда-нибудь распространить тот же механизм на `shipping.type_id` при смене региона — сейчас сознательно нет (см. «Согласование», пункт 3), но если пользователи будут жаловаться на аналогичный эффект при смене региона, пересмотреть отдельно, не задним числом здесь.

## Чего этот план не касается

- Залипающая кука `prefill_zen_payment=expanded` (`ZenMode::syncCollapseCookieState()`, [ZenMode.class.php:440-447](../../lib/classes/zenmode/shopPrefillPluginZenMode.class.php#L440-L447)) — отдельный, уже обсуждённый и намеренно принятый как есть механизм (Z4). Этот план решает проблему на уровне данных (способ оплаты не теряется вовсе), поэтому куке в сценарии из «Зачем» и не придётся залипать — но это следствие, не цель, и если эхо-кэш не покроет какой-то другой сценарий, залипание там всё ещё возможно.
- Аналогичное поведение `shipping`/`region` — см. «Согласование», пункт 3, и «Открытые вопросы».
- issue-81 (уровень логирования не инициализировался в собственных эндпоинтах плагина) — не связано с этим планом по существу, исправлено отдельно 22.08.2026 в тот же день, см. [TODO.md](../TODO.md).
