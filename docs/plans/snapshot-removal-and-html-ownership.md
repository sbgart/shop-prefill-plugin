# План: снятие снапшота и владение по `html`

**Создан:** 22.08.2026
**Источник:** итог разбора [issue-65](../codereview/issue-65-prefill-overrides-current-input.md), раздел «Целевая архитектура»
**Правило-основание:** [B2a](../concept/RULES.md) — при неопределённости отдаём стоковый чекаут
**Статус:** 🟡 этапы 0-3 закоммичены 23.08.2026, этап 5 исправлен той же датой. Не сделано: этап 4 (маркер источника, необязателен, отложен), полный список «Что проверить в браузере после» (проверены только сценарии 2-4, не проверены 1, 6-10)

## Зачем

Разбор issue-65 показал три вещи, которые вместе делают текущую конструкцию избыточной:

1. **Сценарий issue-65 недостижим.** Владение держится на `html`, а он приходит в 100% реальных POST-ов: единственный путь без него — `Form.prototype.reload()`, который никто не вызывает (событие `wa_auth_contact_logout` не генерируется нигде в проекте).
2. **Содержательные поля в `SECTION_OWNERSHIP_FIELDS` — артефакт снапшота.** Владение гейтит и восстановление тоже, поэтому `shipping`/`payment` намеренно лишены `html` — иначе снапшот не смог бы их вернуть. Без снапшота список схлопывается до `['html']` у всех шести секций.
3. **Единственный потребитель снапшота — Zen Mode**, и то косвенно: он читает сессию, а снапшот держит её полной. Для предзаполнения снапшот не нужен (браузер дошлёт из DOM), для создания заказа тоже (`createAction()` работает с POST).

Плюс продуктовое решение: плагин предзаполняет **при входе на чекаут либо по явной просьбе** и ничего не пишет, пока покупатель взаимодействует с формой. Снапшот противоречит ему буквально — восстановление это запись в `shop/checkout` во время взаимодействия.

## Что получается

| Сейчас | После |
|---|---|
| Владение = ключевое поле + `html`, списки различаются по секциям | Владение = `html`, одинаково у всех шести |
| Снапшот: теневая копия всего чекаута, запись при каждом запросе | Нет |
| Восстановление данных при вымывании сессии | Нет — группа разворачивается (B2a) |
| Маркер источника гейтит поход в БД | Не нужен: `html` и есть признак «здесь уже были» |
| cityselect блокирует предзаполнение региона | Предзаполнение перекрывает cityselect |

Логика становится однопроходной: вход на `/order/` → сессия пуста, `html` нет → предзаполняем всё → готово. Любой следующий запрос → `html` есть → не делаем ничего.

## Побочный эффект: Zen Mode станет разворачивать группы чаще

### Старый баг не вернётся

Проверено: `GROUP_MINIMUM_SECTIONS['delivery'] = ['shipping']`, проверяется через `isSectionFilled()` (список DATA = `type_id`). Прежний баг — «группа свёрнута, хотя доставка не выбрана» — требовал сворачивания при пустой секции. Снятие снапшота делает сессию **беднее**, то есть `isGroupMinimumFilled()` возвращает `false` **чаще**, и группа разворачивается **чаще**. Движение строго в безопасную сторону, вернуться этот баг по данному пути не может.

### Окно вреда узкое — уточнено 22.08.2026

Первая редакция плана называла смену города частой и делала из этого блокирующий риск. Неверно, поправка принята:

- `region_change` уходит из [`onChange()`](../../../../js/frontend/order/form.js#L657), а тот срабатывает, **только когда покупатель реально правит** поле региона (страна/область/город/индекс), значение непустое и прошло валидацию. Плюс `setCity()` у cityselect, если его диалог показан на самой странице чекаута;
- у вернувшегося покупателя с предзаполненным адресом не срабатывает ни то, ни другое — в целевом потоке это **ноль раз за сессию**;
- **вымывание вредит только если доставка уже была выбрана.** У гостя, впервые вводящего адрес, `shipping` ещё пуст: терять нечего, и группа в этот момент и должна быть развёрнута.

Опасное окно сужается до одного сценария: вернувшийся покупатель, у которого всё предзаполнено и свёрнуто, **меняет адрес доставки**. И в нём разворот — правильное поведение по B2a: город сменился, доставка пересчитывается, прежний вариант может быть недоступен.

Принудительная синхронизация кук cityselect/bodysite окно не возвращает: мы пишем куки **серверно, из PHP**, JS-события при этом не возникает → `region_change` не стреляет → сессия не вымывается.

### Остаточный пункт: залипающая кука авто-разворота

Не блокер, решается отдельно от снапшота. [`syncCollapseCookieState()`](../../lib/classes/zenmode/shopPrefillPluginZenMode.class.php#L440) пишет куку **серверно при каждом рендере**:

```php
if ($is_collapsed) { $this->response->setCookie(self::COOKIE_PREFIX.$group, '', -1, '/'); }
else               { $this->response->setCookie(self::COOKIE_PREFIX.$group, 'expanded', 0, '/'); }
```

А чтение на [строке 162](../../lib/classes/zenmode/shopPrefillPluginZenMode.class.php#L162) форсирует развёрнутое: `if ($cookie_state === 'expanded') { return false; }`.

Следствие: в описанном выше сценарии группа развернётся и **останется развёрнутой до конца сессии**, даже когда покупатель заново выберет доставку. Это косметика, а не потеря данных, и кнопка сворачивания у него есть (Z3).

**Решено 22.08.2026: принимаем как есть.** Залипание — не дефект, а прямое следствие Z4, и правило подтверждено в исходной формулировке: развёрнутая группа сворачивается только по воле покупателя либо когда он ушёл из корзины.

Оба момента сброса уже реализованы, добавлять ничего не нужно:

- **новый заказ** — [`OrderHooks::handleOrderActionCreate()`](../../lib/classes/hooks/shopPrefillPluginOrderHooks.class.php#L72) зовёт `$this->zen_mode->resetState()`, который чистит куки групп и кэш сводки;
- **закрытие браузера** — кука сессионная (`setCookie(..., 'expanded', 0, '/')`, `expires = 0`).

Отклонённые варианты и почему:

- **Куку писать только по явному действию, авто-решение считать заново каждый запрос.** Тогда группа схлопнулась бы обратно сразу после выбора доставки — то есть закрылась бы под руками покупателя, что Z4 прямо запрещает. Отвергнут.
- **Мини-снапшот на `shipping.type_id` и `payment.id`.** Устаревшие данные снова начинают решать: после смены региона старый `type_id` может быть недоступен, и свёрнутая группа соврёт (Z2). Тот же дефект, что у идеи «кэшировать вердикт». Отвергнут.

## Предостережение для смежной задачи: принудительная синхронизация кук

Не входит в этот план, но решение принято в одном обсуждении, поэтому фиксируется здесь. Плагины региона, с которыми предстоит дружить: **cityselect** (стоит на деве) и два от **bodysite** — «SEO-регионы» и «Информация о доставке и оплате».

Замысел — перекрывать их данные нашими, потому что прошлый заказ достовернее автоопределения (VPN), и не давать им перезатирать наш регион. Для вымывания сессии это безопасно (серверная запись кук не порождает `region_change`), но есть **своя** опасность, никак со снапшотом не связанная:

- у cityselect есть `detectRedirect()` — переход между витринами по городу. Если наш город из прошлого заказа попадает под правило редиректа, покупателя может выбросить на другую витрину **посреди оформления заказа**;
- у «SEO-регионов» регион управляет URL, каноникалами и контентом, то есть принудительная смена — это уже не только чекаут, а SEO-поведение страниц.

Обе интеграции делать с явной проверкой «не приведёт ли это к редиректу» и тестировать до релиза.
