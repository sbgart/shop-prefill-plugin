# Issue 63 — Поиск заказов гостя сканирует `shop_order_params` на каждой странице витрины

**Статус:** ⬜ Открыта, решение согласовано 17.08.2026
**Приоритет:** 🔴 Высокий (деградация магазина под нагрузкой, проявится только у покупателя плагина)
**Сложность фикса:** 🔨 Средний (меняется схема хранения связи «гость → заказ» и порядок работы хуков)
**Файлы:**
`lib/classes/orders/shopPrefillPluginOrderProvider.class.php` (`getLastOrderIdByGuestHash`, `getAllOrderIdsByGuestHash`, `getLastOrderIdByContactId`, `getOrderComment`, `getContactIdFromOrder`),
`lib/classes/fillparams/shopPrefillPluginGuestHashStorage.class.php`,
`lib/classes/fillparams/shopPrefillPluginFillParamsProvider.class.php`,
`lib/classes/hooks/shopPrefillPluginFrontendHooks.class.php`, `…CheckoutHooks…`, `…OrderHooks…`,
`lib/classes/sessionstorage/shopPrefillPluginSessionStorageProvider.class.php` (+ новый класс гейта)

## Проблема

Гостевой сценарий ищет заказ по значению параметра:

```php
"SELECT order_id FROM shop_order_params
 WHERE name = s:name AND value = s:hash
 ORDER BY order_id DESC
 LIMIT 1"
```

Индексы таблицы (`wa-apps/shop/lib/config/db.php:560`):

```php
':keys' => array(
    'PRIMARY' => array('order_id', 'name'),
    'name'    => 'name',
),
```

По `value` индекса нет. MySQL возьмёт индекс `name` и переберёт **все** строки `name='prefill_guest_hash'` — то есть по одной на каждый гостевой заказ за всю историю магазина, — а затем отсортирует их filesort'ом.

`shop_order_params` — одна из самых больших таблиц Shop-Script. На локальной базе 2403 строки параметров на 87 заказов (~28 строк на заказ); на магазине с 50 000 гостевых заказов запрос перебирает 50 000 строк.

### Скан — только часть счёта

Один вызов `getFillParams()` для гостя — это не один запрос, а цепочка:

| # | Запрос | Индекс |
|---|--------|--------|
| 1 | `shop_order_params WHERE name=… AND value=…` | **полный перебор + filesort** |
| 2 | `getOrderParams(order_id)` | PK |
| 3 | `getOrderComment(order_id)` → `shop_order` | PK |
| 4 | `getContactIdFromOrder(order_id)` → `shop_order` | PK, **тот же заказ, второй раз** |
| 5 | `new waContact()` + `getAuthData()` | ещё один-два |

Для авторизованного скана нет (`shop_order.contact_id` проиндексирован), но запросы 2–5 те же — то есть 5–6 запросов на каждый хит витрины у любого посетителя.

## Где это выполняется

1. `shopPrefillPlugin::frontendHead()` → `FrontendHooks::handleFrontendHead()` → `getFillParams()`. Хук `frontend_head` срабатывает на **каждой** странице витрины — главная, категория, карточка товара, поиск.
2. `checkoutBeforeAuth` → тот же путь, на **каждом** AJAX `calculate`/`create` (а их за одно оформление десятки).
3. `getFillParamsCollection()` (диалог «Мои варианты») — уже без `LIMIT 1`, то есть выбирает **все** строки, см. [issue-68](issue-68-params-choice-collection-n-plus-1.md).

Дополнительно: в `handleFrontendHead()` результат `getFillParams()` нужен только внутри `if (on_entry)` и в debug-панели — при `on_entry = false` все эти запросы выполняются вхолостую.

И главное — **результат почти всегда выбрасывается**. `preFillCheckoutParams()` заполняет только пустые секции, а проверка `canPrefillSection()` работает по текущей сессии и данных заказа не требует. В логе это видно прямо: `Section 'shipping' skipped: already filled` … `no params were filled`. Порядок действий обратный правильному: сначала поход в БД, потом вопрос «а нужно ли было».

## Последствия

- Рост нагрузки на БД пропорционально числу заказов магазина: чем успешнее магазин, тем хуже работает плагин.
- На локальной разработке и у первых покупателей невидимо (сотни заказов), выстреливает у крупного клиента — худший сценарий для платного плагина.
- Больше всего страдает самый массовый сегмент: гость без единого заказа платит полным сканом за каждую просмотренную страницу, а найти для него нечего по определению.

## Решение

Пять слоёв, каждый работает независимо; порядок = порядок внедрения.

### 1. Указатель вместо поиска по значению

Кука гостя хранит не только hash, но и id последних заказов — одной кукой, чтобы части не рассинхронизировались:

```
prefill_guest = <hash>.<id1,id2,…,idN>     // httponly, secure, 1 год, N ≈ 10
```

Чтение: `order_id` из куки → `shop_order_params` по PK → сверка `prefill_guest_hash` из параметров заказа с hash из куки через `hash_equals()`. Подделка `order_id` в куке ничего не даёт: без hash заказ не отдаётся. Запись id — там же, где сейчас пишется hash (`OrderHooks::saveGuestHash()`), с той же проверкой согласия.

Полный скан исчезает совсем. **Своя таблица не нужна** (в прошлой редакции этого файла предлагалась `shop_prefill_guest_order`): связь всё равно живёт ровно до потери куки, потому что hash тоже в куке, — серверный реестр не даёт ничего сверх указателя. Записи `prefill_guest_hash` в `shop_order_params` остаются: теперь это не индекс для поиска, а токен владения.

**Миграция не нужна** — релиза не было; на локалке достаточно один раз пересоздать куку.

### 2. Ранний выход, когда источника заведомо нет

- **Гость:** в куке нет ни одного `order_id` → заказов нет (id туда пишет только `order_action.create`) → выходим **без единого запроса**, в этот визит и во все последующие. Это отсекает основную массу трафика.
- **Авторизованный:** `shop_customer` (PK = `contact_id`, поля `last_order_id`, `number_of_orders`, поддерживается ядром в `shopCustomerModel::updateFromNewOrder()`, [db.php:201](../../../../lib/config/db.php)) — один запрос по первичному ключу отвечает сразу и «есть ли заказы», и «какой последний». Нет строки → выходим. Заменяет `getLastOrderIdByContactId()` с его `ORDER BY id DESC`.

  Сверено на локальной базе: `last_order_id` совпадает с `MAX(shop_order.id)` по контакту во всех строках `shop_customer`.

### 3. Маркер источника в сессии

Рядом с `shop/checkout` и `shop/prefill_snapshot` появляется третья запись:

```php
'shop/prefill_source' => ['key' => 'guest:<hash>', 'order_id' => 10087, 'ts' => 1755400000]
```

`key` — отпечаток источника: `user:<contact_id>` или `guest:<hash>`; вычисляется из сессии и куки, **без запросов к БД**. Совпал с маркером — в БД не идём вообще: данные уже предзаполнены в `shop/checkout`.

Маркер ставится **и когда источник оказался пустым** — иначе секция, которую нечем заполнить (у прошлого заказа не было комментария или способа оплаты), тянула бы запрос на каждом хите вечно.

Сброс:
- `order_action.create` — оформлен заказ, источник изменился;
- смена авторизации — ключ содержит `contact_id`/hash, промахивается сам;
- TTL 30 минут — страховка на случай правки заказа админом в бэкенде;
- контроллеры явных действий покупателя (выбор варианта в диалоге, force prefill, apply delivery) гейт обходят: `order_id` приходит из запроса, после применения они обновляют маркер.

Персональных данных в маркере нет — только ключ, id и время.

### 4. Гейт «нечего заполнять»

Инвертировать порядок в `preFillCheckoutParams()`: сначала посчитать список предзаполняемых секций по сессии и снапшоту, и только если он непуст — обратиться к провайдеру. Технически — принимать не готовый `FillParams`, а ленивый источник (callable / `FillParamsSource`). На чекауте это основной фильтр: `calculate` летит на каждое изменение поля, а заполнять там почти всегда нечего.

### 5. Схлопывание запросов и мемоизация

- `getOrderComment()` + `getContactIdFromOrder()` + чтение заказа → один `SELECT id, contact_id, comment FROM shop_order WHERE …`.
- Статический кэш контакта в `ContactProvider` (в диалоге «Мои варианты» `contact_id` у всех заказов один и тот же).
- Мемоизация `getFillParams()` — **статическая**, а не в поле объекта: `waEvent` пересоздаёт плагин на каждый хук, см. [issue-73](issue-73-stale-plugin-singleton.md).
- Лимиты для коллекции — см. [issue-68](issue-68-params-choice-collection-n-plus-1.md).

## Безопасность

1. **Хеш гостя обязан стать криптостойким.** Сейчас `GuestHashStorage:85`:

   ```php
   $unique_id = 'guest_' . uniqid('', true) . '_' . microtime(true);
   $guest_hash = hash('sha256', $unique_id);
   ```

   Энтропии здесь ровно столько, сколько в моменте создания куки: `uniqid()` и `microtime()` — это время. SHA-256 от предсказуемого входа предсказуем.

   Пока поиск шёл по значению, hash надо было угадывать вслепую. В схеме с указателем защита от чтения чужого заказа держится **только** на hash, а `order_id` — маленькое последовательное число, которое перебирается тривиально. Значит: `bin2hex(random_bytes(32))`. Замена бесплатна — релиза не было.

2. Сверка токена — `hash_equals()`, не `==`.
3. Кука: `httponly` уже есть, `secure` захардкожен в `false` с TODO — закрыть здесь же (пересекается с [issue-57](issue-57-minor-robustness-findings.md)).
4. Согласие: нет consent → ни hash в заказ, ни id в куку. Логика не меняется.

## Отклонённые варианты (и почему)

- **Своя таблица `shop_prefill_guest_order`** — см. §1: не даёт ничего сверх указателя в куке, зато требует миграции и обслуживания.
- **Данные в localStorage браузера.** Ломает `on_entry`: предзаполнение применяется на сервере до рендера, а данные из localStorage доедут в лучшем случае следующим запросом — первая страница покажет цены без учёта выбранной доставки. Плюс это недоверенный источник (в чекаут-сессию нельзя писать без сверки с БД, а сверка — это тот самый запрос), плюс адрес и телефон в localStorage читает любой сторонний скрипт на витрине.
- **Файловый кэш (`waCache`) поверх сессии.** Экономит 2 запроса по PK раз в 30 минут на посетителя (сессия Webasyst живёт `session_timeout = 1800`), а платим персональными данными на диске, отдельной инвалидацией и вторым источником правды. Добавляется поверх за полчаса, если замеры после внедрения покажут необходимость.
- **Подписанная кука со снимком данных (HMAC).** Единственная схема с нулём запросов между сессиями, но 1–2 КБ персональных данных летят с каждым HTTP-запросом, нужен секрет и его ротация, а правки заказа в бэкенде покупатель не увидит до следующего заказа.

## Решённые развилки

- **`on_entry` остаётся на всех страницах витрины, а не только на корзине/чекауте.** Цена товара зависит от выбранного способа доставки и оплаты (скидка за самовывоз и т.п.), поэтому сессия должна быть предзаполнена до рендера каталога. После §2–§3 это стоит один поход в БД на визит, а не запрос на каждой странице.
- **В сессию пишем весь набор секций**, а не только ценообразующие `region`/`shipping`: на цену влияет в том числе способ оплаты.
- **Ассеты — отдельная история.** Гейт по контексту (CSS/JS только на корзине и чекауте) остаётся за [issue-64](issue-64-assets-loaded-on-every-page.md); предзаполнение сессии он не затрагивает.

## Итог

| Кто | Сейчас | После |
|---|---|---|
| Гость без истории (основной трафик) | 5–6 запросов со сканом на каждой странице | **0, всегда** |
| Гость с историей | 5–6 со сканом на каждой странице | 2 по PK на визит, дальше 0 |
| Авторизованный без заказов | 5–6 на каждой странице | 1 по PK на визит, дальше 0 |
| Авторизованный с заказами | 5–6 на каждой странице | 2–3 на визит, дальше 0 |
| Каждый `calculate` на чекауте | 5–6 | 0 |

## Тесты

1. Новый посетитель без куки: пройти по каталогу — в логе плагина ни одного обращения к заказам.
2. Гость с заказом: первая страница визита — один поход в БД, последующие страницы и `calculate` — ни одного.
3. Гость оформляет второй заказ: маркер сброшен, предзаполнение подхватило новый адрес.
4. Подмена `order_id` в куке на чужой заказ → предзаполнения нет (сверка hash).
5. Авторизованный без заказов: один запрос к `shop_customer` за визит.
6. «Мои варианты» у гостя с 3+ разными адресами: карточки на месте (список id из куки, не один заказ).
7. Скидка за самовывоз: цены в каталоге на первой же странице визита учитывают доставку и оплату из прошлого заказа.
8. Регресс issue-65 — в свежей сессии, см. выше.
