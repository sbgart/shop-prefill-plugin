# Issue 51 — Плагин молча выдаёт постоянную cookie авторизации `auth_token` на 90 дней

**Статус:** ✅ Готово
**Приоритет:** 🔴 Высокий (безопасность / претензии магазинов)
**Сложность фикса:** 🔧 Средний
**Файлы:** `lib/classes/user/shopPrefillPluginUserProvider.class.php` (`rememberMe`, `getAuthToken`), `lib/classes/hooks/shopPrefillPluginFrontendHooks.class.php` (`handleRememberMeCookie`)

## Проблема

На каждом хите `frontend_head` для авторизованного покупателя плагин ставит cookie `auth_token`:

```php
$hash = md5($this->getCreateDatetime() . $this->getLogin() . $this->getPassword());
return substr($hash, 0, 15) . $this->getId() . substr($hash, -15);
```

Это **точная копия** `waAuth::getToken()` — то есть валидный токен «запомнить меня» фреймворка, по которому `waAuth` автоматически авторизует посетителя.

Настройка `prefill.remember_me.active` включена по умолчанию (`storefront.settings.php`), TTL — 90 дней.

Что здесь не так:

1. **Игнорируется политика фреймворка.** `waAuth` ставит `auth_token` только если `$this->auth_config->getRememberMe()` и пользователь сам отметил «запомнить меня». Плагин выдаёт токен всем и всегда, фактически отменяя настройку магазина и выбор покупателя.
2. **Общие компьютеры.** Покупатель, вошедший «на один раз», остаётся залогинен 90 дней после закрытия браузера.
3. **`secure = false`.** На HTTPS-магазине токен уходит и по обычному HTTP (см. [issue-57](issue-57-minor-robustness-findings.md)).
4. Токен строится из хеша пароля контакта — читать `password` контакта ради этого нежелательно.

Для магазина это выглядит как «плагин предзаполнения самовольно продлевает сессии покупателей» — риск претензий и отказа в публикации.

## Рекомендация

Минимум:
- уважать `waAuthConfig::getRememberMe()` и cookie `remember` (продлевать токен, только если он уже был выдан фреймворком);
- по умолчанию выключить `prefill.remember_me.active`, а в описании настройки явно объяснить, что она делает;
- `secure` выставлять по `waRequest::isHttps()`.

Лучше: отказаться от собственной генерации токена и продлевать уже существующую cookie фреймворка, не создавая её.

## Что сделано

При разборе выяснилось, что «просто продлевать существующую cookie» на витрине недостаточно: при оформлении заказа фреймворк её не выдаёт вовсе. `shopConfirmationChannel::authorize()` зовёт `auth(['id' => $contact_id])` без ключа `remember`, а галочки «Запомнить меня» в диалоге подтверждения кода нет — покупатель авторизуется только на текущую сессию. Поэтому сценарии разведены:

- **Покупатель сам отметил «Запомнить меня»** — плагин только продлевает уже выданный токен. Признак согласия — наличие cookie `auth_token`; кука `remember` для этого не годится, `waAuth::_remember()` пишет в неё `0` и отказавшимся, и тем, кому галочку не показывали.
- **Авторизация при оформлении заказа** — токен выдаёт плагин, но только по новой настройке `prefill.remember_me.on_order` (по умолчанию выключена). Факт «выбора не было» фиксируется меткой в сессии на `order_action.create` (до `postConfirm()`) и потребляется на следующей загрузке страницы — постфактум по cookie этот случай неотличим от явного отказа.

Также:

- токен считает `waAuth::getToken()` — своя md5-формула и прямое чтение `password` контакта убраны;
- `secure` выставляется по `waRequest::isHttps()` (закрывает [issue-57](issue-57-minor-robustness-findings.md));
- cookie `remember` больше не ставится: она лишь предотмечает галочку в форме логина, а выбора покупатель мог не делать;
- добавлена проверка `waDomainAuthConfig::getRememberMe()` — без неё `waAuth::_authByCookie()` вообще не читает `auth_token`, то есть токен был бы бесполезен;
- `expires` по умолчанию `0` — стандартный срок Webasyst (30 дней), кастомный срок задаётся админом;
- в настройках плагина показывается статус обеих внешних зависимостей (`rememberme` домена и `order_without_auth` магазина) со ссылками на нужные страницы.
