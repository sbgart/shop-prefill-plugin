## Кратко

Плагин сначала загружает прошлый заказ, а потом выясняет, нужен ли он был. Для гостя загрузка начинается с неиндексированного поиска по `shop_order_params.value`, поэтому каждый запрос перебирает все гостевые заказы магазина.

Решение — четыре независимых правила:

1. **Предзаполнение уходит с каталога.** Настройка `on_entry` вырезается, `frontend_head` перестаёт трогать источник. Предзаполнение живёт только на чекаут-пути.
2. **Гостевой идентификатор переезжает в индексируемую колонку `name`.** В куке — случайный bearer-token, в БД — производный от него lookup id.
3. **Кука выдаётся только после первого завершённого заказа.** Нет куки — нет истории — ноль запросов.
4. **Маркер источника в сессии + ленивая загрузка.** Источник читается не чаще одного раза на пару «витрина + личность» за сессию.

Отдельная таблица, список `order_id` в куке, индекс в таблице ядра, свой TTL-кэш и `hash_equals` не нужны.

Дизайн вырезанного `on_entry` сохранён в [todo/on-entry-early-prefill.md](../todo/on-entry-early-prefill.md) — с обоснованием удаления и планом возврата, если у покупателя плагина найдётся сторонний потребитель сессии на каталоге.

## Проблема

### 1. Неиндексированный гостевой поиск

```sql
SELECT order_id FROM shop_order_params
WHERE name = 'prefill_guest_hash' AND value = :guest_hash
ORDER BY order_id DESC LIMIT 1
```

Индексы таблицы (`wa-apps/shop/lib/config/db.php:560-569`):

```php
':keys' => array(
    'PRIMARY' => array('order_id', 'name'),
    'name'    => 'name',
),
```

По `value` индекса нет. СУБД отбирает по индексу `name` **все** строки `prefill_guest_hash` — по одной на каждый гостевой заказ за всю историю магазина — и сравнивает `value` уже постфильтром. На магазине с 50 000 гостевых заказов это 50 000 строк на каждый запрос, включая запросы посетителей, у которых заказов не было никогда.

### 2. Один `getFillParams()` — это цепочка запросов

| # | Запрос | Индекс |
|---|--------|--------|
| 1 | `shop_order_params WHERE name=… AND value=…` | **перебор + filesort** |
| 2 | `getOrderParams(order_id)` | PK |
| 3 | `getOrderComment(order_id)` → `shop_order` | PK |
| 4 | `getContactIdFromOrder(order_id)` → `shop_order` | PK, **та же строка, второй раз** |
| 5 | `waContact` + `getAuthData()` | ещё 1-3 |

Для авторизованного скана нет, но запросы 2-5 те же, плюс `getLastOrderIdByContactId()` идёт без `LIMIT` (`OrderProvider:32-34`) и вытаскивает все id контакта.

### 3. Результат почти всегда выбрасывается

`preFillCheckoutParams()` заполняет только пустые секции, а `canPrefillSection()` работает исключительно по сессии и настройкам — данные заказа ему не нужны вовсе. То есть порядок обратный правильному: сначала поход в БД, потом вопрос «а нужно ли было». На `/order/` цепочка проходит дважды за загрузку (`frontend_head` из лэйаута + `checkout_before_auth` из `formVars()`), при включённой debug-панели — трижды.

### 4. `on_entry` платил за это на каждой странице каталога

`frontendHead()` вызывает `getFillParams()` на строке 87 — **до** проверки `on_entry` на строке 96. То есть даже при выключенной настройке вся цепочка выполнялась вхолостую.

## Решение

### 1. Предзаполнение уходит с каталога: `on_entry` вырезается

Настройка удаляется целиком, а не выключается по умолчанию. Обоснование — в [todo/on-entry-early-prefill.md](../todo/on-entry-early-prefill.md); коротко:

- обещанный сценарий «цена в корзине зависит от доставки» закрыт без неё: корзина — это `/order/`, где `checkout_before_auth` срабатывает при отрисовке формы через `formVars()` → `processAll()`;
- обещанный сценарий «цены в каталоге» не работал физически: `frontend_head` вызывается из лэйаута, после сборки `$content`;
- в стоковом ядре предзаполненные секции вне `checkout2` не читает никто — только `coupon_code` и `use_affiliate`, ключи верхнего уровня, которых плагин не пишет;
- побочно исчезает подавление штатного восстановления формы из `localStorage` через `session_is_alive`.

После правки `frontend_head` не вызывает ни `getFillParams()`, ни `preFillCheckoutParams()`. В нём остаются remember-me, гостевые куки, ассеты, debug-стек и HTML для `<head>`.

Предзаполнение выполняется только в `checkout_before_auth` и в контроллерах явных действий покупателя.

### 2. Гостевой идентификатор — в индексируемой колонке `name`

Кука:

```text
prefill_guest_token = <64 lowercase hex>   // bin2hex(random_bytes(32))
```

Производный идентификатор для имени параметра:

```php
$lookup_id  = substr(hash('sha256', $token), 0, 48);
$param_name = 'prefill_guest_' . $lookup_id;   // 14 + 48 = 62 ≤ varchar(64)
```

В заказ пишется `name = prefill_guest_<48 hex>`, `value = '1'`. Поиск:

```sql
-- последний заказ
SELECT order_id FROM shop_order_params
WHERE name = :param_name ORDER BY order_id DESC LIMIT 1

```

Это точное равенство по существующему индексу `name`. `ORDER BY` может остаться filesort'ом, но сортируются только заказы одного гостя. Публичная коллекция истории по этому имени не строится: см. [issue-55](issue-55-guest-apply-delivery-ignores-order-id.md).

**Почему token и lookup id разделены.** Сырой bearer-token живёт только в HTTP-only куке. В БД лежит усечённый до 192 бит SHA-256, из которого куку не восстановить. Раньше значение в БД **и было** кукой: утечка или показ параметров заказа отдавали чужой идентификатор. Побочно исчезает и необходимость в `hash_equals`: клиент не передаёт указатель на заказ, имя параметра вычисляет сервер.

### 3. Кука выдаётся только после первого заказа

Новый посетитель не должен получать идентификатор за просмотр каталога.

```text
Гость без куки → истории заведомо нет → 0 запросов, кука не создаётся
```

Токен создаётся в `order_action.create`, если гостевой prefill включён и выполнены требования согласия. При существующей валидной куке новый заказ связывается с тем же токеном, поэтому больший `order_id` автоматически становится первым результатом индексного запроса.

Порядок безопасен: событие `order_action.create` эмитится в `postExecute()` (`shopWorkflowCreateAction.class.php:634`) **после** записи параметров заказа с `$delete_old = true` на `:495` — параметр плагина не затирается.

### 4. Маркер источника в сессии + ленивая загрузка

Источник определяется без единого запроса:

```text
storefront:<code>|guest:<lookup_id>
storefront:<code>|user:<contact_id>
```

`shop/prefill_source` хранит только эту строку — ни `order_id`, ни timestamp, ни своего TTL:

- маркер и так живёт ровно столько, сколько Webasyst-сессия;
- вход, выход, смена куки и переход между витринами меняют ключ сами;
- новое оформление явно сбрасывает маркер;
- текущее оформление не должно самопроизвольно перестраиваться из заказа, отредактированного администратором посреди процесса.

Заказ, созданный через backend/API/CLI, не инвалидирует маркер в уже открытой сессии — он станет источником после новой сессии, смены ключа либо явного reset/refill. Это принято ради стабильности оформления; polling и TTL не добавляются.

**Два правила, без которых маркер ломает соседнюю логику:**

1. **Маркер гейтит только обращение к БД, а не весь `preFillCheckoutParams()`.** Восстановление из `shop/prefill_snapshot` обязано отрабатывать на каждом запросе: оно живёт в сессии, стоит ноль запросов и является отдельным контрактом ([issue-53](issue-53-empty-prefill-writes-session.md), тест «очистить город → город восстанавливается из снапшота»), а также целевым поведением [issue-59](issue-59-html-key-marks-section-filled.md) и [issue-72](issue-72-snapshot-overwritten-by-empty-branch.md). Ранний выход по маркеру из всего метода их обесточит.
2. **Для гостя без куки маркер не пишется.** Иначе запись в сессию поднимет PHP-сессию и `Set-Cookie: PHPSESSID` каждому анониму и боту, что ломает инвариант [issue-53](issue-53-empty-prefill-writes-session.md). Отсутствие куки проверяется за ноль запросов, состояние для этого не нужно.

Во всех остальных случаях маркер сохраняется **и при отрицательном результате**: если заказ не найден или в нём нет нужной секции, повторять тот же запрос на каждом `calculate` бессмысленно.

Порядок внутри `preFillCheckoutParams()`:

```text
1. определить доступные для prefill секции (сессия + настройки)
2. закрыть что можно из snapshot
3. остались пустые секции?
     ├─ нет → выход, БД не трогаем
     └─ да
         ↓
4. маркер совпадает с текущим source key?
     ├─ да → выход, БД не трогаем
     └─ нет → вызвать loader (ленивый callable)
         ↓
5. заполнить только оставшиеся секции
6. сохранить checkout + snapshot
7. сохранить маркер (в том числе при пустом результате)
```

Провайдер передаётся ленивым источником:

```php
$session_storage->preFillCheckoutParams(
    $source_key,
    static function () use ($fill_params_provider) {
        return $fill_params_provider->getFillParams();
    }
);
```

Для явных действий, где конкретный `FillParams` уже известен, остаётся eager-метод либо обёртка готового объекта в callback. Отдельный класс гейта или универсальный cache layer не вводится.

### 5. Авторизованный пользователь

Гостевой токен не используется. Источник берётся из поддерживаемой ядром строки:

```sql
SELECT last_order_id FROM shop_customer WHERE contact_id = :contact_id LIMIT 1
```

`contact_id` — первичный ключ. Пустота проверяется по **`last_order_id IS NULL`**, а не по `number_of_orders = 0`: строка `shop_customer` создаётся и без заказов (`shopCustomerModel::createFromContact()`, зовётся в том числе merge-хендлером), а `last_order_id` — nullable.

Известные ограничения, которые схема не чинит и не ухудшает: `number_of_orders` никогда не уменьшается, а удаление заказа мягкое (`state_id = 'deleted'`), поэтому `last_order_id` может указывать на удалённый заказ — ровно как и нынешний `ORDER BY id DESC` без фильтра по состоянию. Про витрину `shop_customer` тоже не знает.

Это опциональная замена: `SELECT id FROM shop_order WHERE contact_id = ? ORDER BY id DESC LIMIT 1` по существующему индексу `contact_id` — тоже один запрос. Выигрыш `shop_customer` в том, что он снимает filesort и отвечает сразу на «есть ли заказы вообще».

### 6. Схлопывание дублей на горячем пути

`getOrderComment()` и `getContactIdFromOrder()` читают одну и ту же строку `shop_order` дважды — объединить в `SELECT id, contact_id, comment FROM shop_order WHERE id = ?`. Мемоизацию `getFillParams()` делать **статической**, а не в поле объекта: `waEvent` пересоздаёт плагин на каждый хук ([issue-73](issue-73-stale-plugin-singleton.md)).

## Безопасность

1. Токен — `bin2hex(random_bytes(32))`, 256 бит криптографической случайности. Текущий `sha256(uniqid() . microtime())` предсказуем: энтропии в нём ровно столько, сколько во времени создания куки.
2. Кука принимает только значение по `\A[a-f0-9]{64}\z`; невалидное считается отсутствующим.
3. В БД — только усечённый до 192 бит SHA-256, не bearer-token.
4. Имя параметра собирается сервером из провалидированного hex и уходит в запрос связанным параметром, а не конкатенацией.
5. Кука: `HttpOnly`, `Secure` на HTTPS, `SameSite=Lax`, срок жизни год. Закрывает `secure = false` с TODO в `GuestHashStorage:117` ([issue-57](issue-57-minor-robustness-findings.md)) и `SameSite` из [issue-74](issue-74-minor-findings-pass-2.md).
6. При `consent_required` без согласия не создаётся ни кука, ни связь в заказе. Логика согласия не меняется.
7. В куке нет `order_id` и персональных данных.
8. Подмена куки на случайное валидное значение даёт индексный промах и пустой prefill.
9. **Отзыв согласия и очистка истории должны удалять связь в БД, а не только куку.** Сейчас `revoke` и `clear` в `FrontendConsent.controller.php:42-47,56-60` стирают только куку — строки в заказах остаются недостижимыми сиротами навсегда. Новая схема впервые делает удаление дешёвым и точным: на момент отзыва сервер ещё знает `lookup_id`, поэтому `DELETE FROM shop_order_params WHERE name = :param_name` идёт по индексу.

## Отклонённые варианты

- **`prefill_guest = <hash>.<id1,id2,…>`** — быстрый PK lookup, но кука растёт, требует парсинга и синхронизации двух частей, искусственно ограничивает историю ~10 заказами и делает `order_id` клиентским вводом, который надо сверять `hash_equals` при каждом чтении.
- **Своя таблица `shop_prefill_guest_order`** — реляционно корректно, но требует `lib/updates/<ts>.php` (у уже установленного плагина `install()` повторно не выполняется), собственного lifecycle и уборки. Ничего не даёт сверх индексного имени, пока связь всё равно живёт ровно до потери куки.
- **Индекс `(name, value)` в `shop_order_params`** — минимум PHP-кода, но плагин не должен владеть схемой одной из крупнейших таблиц ядра. Декларативно это невозможно (`createSchema()` для существующей таблицы — no-op, `addIndex` в MySQL-адаптере нет), а объявление чужой таблицы в своём `db.php` при деинсталляции сделает `DROP TABLE shop_order_params`. Сборщик архива такое имя таблицы и не пропустит.
- **Только маркер поверх старого SQL** — убирает повторы, но первый запрос каждой новой сессии остаётся пропорционален всей истории магазина.
- **Файловый `waCache`** — персональные данные на диске, отдельная инвалидация и второй источник правды ради экономии пары запросов по PK.
- **Подписанная кука с `order_id`** — нужен HMAC-секрет и его ротация, а для истории снова список ID.
- **Кука со снимком `FillParams`** — 1-2 КБ персональных данных с каждым HTTP-запросом, устаревание независимо от заказа.
- **Снимок `FillParams` в своей таблице** — один PK-запрос и единый код для гостя и авторизованного, но плагин перестаёт видеть правки заказа, история начинается только с момента установки, появляется вторая копия персональных данных и новый контракт сериализации.
- **Восстановление `localStorage` через JS + calculate + reload** — промежуточный экран и второй рендер ради незавершённых данных, сохранение которых не входит в задачи плагина.

## Производительность после изменения

| Сценарий | Каталог | Первый чекаут-вызов | Следующие `calculate` |
|---|---:|---:|---:|
| Гость без куки | 0 | 0 | 0 |
| Гость с историей | 0 | 1 индексный lookup + гидратация | 0 |
| Авторизованный без заказов | 0 | 1 PK lookup | 0 |
| Авторизованный с заказом | 0 | 1 PK lookup + гидратация | 0 |

Ключевое отличие от текущего состояния: ни одного запроса, стоимость которого растёт с числом заказов магазина.

## План реализации

1. Удалить `prefill.on_entry` из `storefront.settings.php`, переключатель из `General.html` и строки локали `setting.prefill.on_entry` / `hint.prefill.on_entry` в обоих языках.

## Тесты

Браузерный runbook с точными командами, критериями и подсчётом SQL — [tests/issue-63-browser-test-runbook.md](../tests/issue-63-browser-test-runbook.md). Ниже — приёмочные критерии.

### Каталог и хуки

1. Проход по каталогу: ни одного обращения к заказам в логе плагина, `frontend_head` при этом продолжает отдавать ассеты, debug и обслуживать куки.
2. Настройки: переключателя `on_entry` в админке нет, сохранённое значение нигде не читается.
3. Чекаут предзаполняется на первой же загрузке `/order/` без всякого `on_entry`.

### Гость

1. Новый посетитель проходит каталог и открывает `/order/`: token-cookie не создаётся, SQL к заказам нет.
2. Первый storefront-заказ создаёт токен и параметр заказа длиной ≤ 64 символа.
3. Заказ из backend/API/CLI не получает куку администратора и не трогает storefront-маркер.
4. При обязательном согласии без согласия ни куки, ни параметра заказа не появляется.
5. Возврат гостя: `EXPLAIN` показывает `ref` по индексу `name`, полного перебора по `value` нет.
6. Повторные `calculate` источник не перечитывают.
7. Невалидная или неизвестная кука даёт безопасный промах.
8. Второй заказ получает то же имя параметра; источником становится больший `order_id`.
9. Отзыв согласия и очистка истории удаляют куку, снапшот, маркер **и строки связи в заказах**.
10. Ссылка «Мои варианты» отсутствует, а прямые запросы к списку и `apply-delivery` получают отказ; token-cookie не раскрывает гостевую историю.

### Авторизованный

1. Полностью заполненный чекаут или достаточный снапшот: обращений к `shop_customer` и заказам нет.
2. Пользователь без заказов: один PK lookup за сессию.
3. Пользователь с заказом: источник прочитан один раз, последующие хуки в БД не идут.
4. Login/logout меняет source key, маркер предыдущей личности не используется.
5. После storefront-заказа маркер очищен, следующий цикл видит обновлённый `last_order_id`.

### Регрессии

1. **Снапшот восстанавливается при совпавшем маркере** — стереть город в живой сессии, обновить страницу: город возвращается из снапшота, обращения к БД при этом нет. Это прямая проверка того, что маркер гейтит только loader.
2. **Гость без куки не поднимает PHP-сессию** — проверить отсутствие `Set-Cookie: PHPSESSID` и `session_is_alive = false`.
3. У авторизованного явный выбор варианта и apply delivery обходят маркер и применяют выбранный заказ; у гостя оба endpoint закрыты.
4. Reset/refill и force prefill действительно перечитывают источник.
5. Ручной ввод не перетирается повторным prefill — отдельно [issue-65](issue-65-prefill-overrides-current-input.md).
6. Проверить [issue-59](issue-59-html-key-marks-section-filled.md) и [issue-72](issue-72-snapshot-overwritten-by-empty-branch.md) в изменённой ветке сессии.
7. PHP 7.4 lint и соответствие имени файла классу после переименования storage-класса.

## Совместимость и миграция

- Публичного релиза не было — миграция старых `prefill_guest_hash` не нужна. Старая кука и старые строки новым кодом просто не используются; на локальной копии достаточно один раз пересоздать куку.
- Сохранённые значения `prefill.on_entry` в `shop_prefill_settings` становятся мёртвыми данными; отдельная чистка не требуется, но при желании убирается одним `DELETE ... WHERE name LIKE 'prefill.on_entry%'`.
- Используется только синтаксис PHP 7.4.

### Принятая цена

Пространство имён `shop_order_params.name` пополняется одним значением на гостя. Функционально безопасно (проверено выше), но два следствия стоит признать: «удалить все связи prefill» становится `WHERE name LIKE 'prefill_guest_%'`, то есть сканом — операция админская, не горячая; а в выгрузках параметров заказа администратор увидит непрозрачное `prefill_guest_<48 hex> = 1` вместо самоописательного `prefill_guest_hash`.
