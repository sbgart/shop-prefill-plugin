# Issue 76 — Кастомный CSS витрины замещает `frontend.css` целиком: после обновления плагина стили остаются старыми навсегда

**Статус:** ✅ Закрыта
**Приоритет:** 🟠 Средний → станет 🔴 на втором релизе плагина
**Сложность фикса:** 🔨 Средний (меняется модель хранения, нужна миграция)
**Файлы:** `lib/classes/view/shopPrefillPluginAssetsManager.class.php` (`init`), `lib/classes/css/shopPrefillPluginCssManager.class.php` (`getDefaultContent`), `lib/actions/shopPrefillPluginSettingsGetCss.controller.php`, `templates/actions/settings/blocks/tabs/Design.html`

## Проблема

Редактор CSS отдаёт администратору **весь** `css/frontend.css` (11 293 байта):

```php
// SettingsGetCss::handle()
$default = $css_manager->getDefaultContent();          // содержимое css/frontend.css целиком
…
$current = $custom_css !== '' ? $custom_css : $default; // в редактор — полная копия
```

Сохранённая копия становится **заменой**, а не дополнением:

```php
// AssetsManager::init()
if ($storefront_css_url !== '') {
    $this->getResponse()->addCss($storefront_css_url);   // только пользовательская копия
} else {
    $add_css('css/frontend.' . (!$is_debug ? 'min.' : '') . 'css');
}
```

Значит достаточно администратору один раз поправить в редакторе цвет — и витрина навсегда переходит на снимок стилей той версии плагина, в которой он нажал «Сохранить».

## Последствия

Плагин продаётся и будет обновляться. Любой релиз, где появляется новый класс, новое состояние, новая иконка или правка адаптива, **не доедет** до всех витрин с кастомным CSS. Проявится это не ошибкой, а «поехавшей» вёрсткой у покупателя — и разбираться будет автор плагина, а не тот, кто нажал «Сохранить» полгода назад.

Дополнительно:

- `styles.custom_css` лежит в колонке `TEXT` (64 КБ). Пока в неё пишут полную копию 11 КБ — запас есть, но он тратится не на правки администратора, а на копию файла, который и так есть на диске (см. [issue-57 §8](issue-57-minor-robustness-findings.md)).
- Кнопка «Сбросить» возвращает `default_css` — то есть снова полную копию, а не «нет кастомного CSS». Отличить «сброшено» от «скопировано без изменений» после этого нельзя.

## Рекомендация

1. Перейти на модель **оверрайда**: `frontend.css` подключается всегда, пользовательский файл — вторым, только с переопределениями.

   ```php
   $add_css('css/frontend.' . (!$is_debug ? 'min.' : '') . 'css');
   if ($storefront_css_url !== '') {
       $this->getResponse()->addCss($storefront_css_url);
   }
   ```

2. В редакторе открывать **пустое** поле с подсказкой «здесь только ваши переопределения», а полный `frontend.css` показывать отдельной read-only справкой (или ссылкой на файл) — чтобы было откуда копировать селекторы.
3. Миграция для уже сохранённых полных копий: оставить их работать как есть (флаг `styles.custom_css_mode = 'replace'`), а новые сохранения писать в режиме `override`. Либо разово показать администратору предупреждение в настройках.
4. Пока не сделано — как минимум написать это предупреждение прямо в подсказке под кнопкой «Редактировать CSS»: правки не получат обновлений стилей плагина.

## Решение

Плагин ещё не выпускался — реальных сохранённых полных копий CSS нет, миграция (п.3) не нужна.

Реализовано по пп.1–2:

- `shopPrefillPluginAssetsManager::init()` — `frontend.css` подключается всегда, per-storefront файл (если есть) — вторым, поверх.
- `shopPrefillPluginSettingsGetCssController` — редактор открывается с содержимым `custom_css` как есть (включая пустую строку — нормальное стартовое состояние), без fallback на `default_css`.
- В шаблоне `Design.html` добавлен разворачиваемый по клику read-only ACE-блок с оригинальным `frontend.css` (подсветка CSS, `setReadOnly(true)`) — справка для копирования селекторов, без отдельного AJAX-запроса (`default_css` уже приходит в ответе `GetCss`).
- Кнопка «Сбросить» сменила семантику на «Очистить» — очищает переопределения, а не подставляет оригинал.
