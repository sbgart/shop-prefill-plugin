# Issue 82 — `prefill.frontend(.min).js` подключается без версии, браузер может годами отдавать старый JS из кэша

**Статус:** ✅ Решена (19.08.2026). Найдена 18.08.2026 при браузерной проверке фикса [issue-69](issue-69-hardcoded-russian-strings-frontend.md)

**Приоритет:** 🟠 Средний (тихая деградация после каждого релиза, не блокер)

**Сложность фикса:** 🔨 Низкая

**Файлы:** `lib/classes/view/shopPrefillPluginAssetsManager.class.php:58,62`

## Симптом

При проверке фикса issue-69 в браузере первый прогон показал `window.prefill.dialogManager.messages`
пустым объектом `{}`, хотя PHP уже отдавал новые ключи (`paramsChoiceManager.messages` на той же
странице их содержал). После жёсткого рефреша (Cmd+Shift+R) всё встало на место — значит дело не в
коде, а в том, что вкладка выполняла старую версию `prefill.frontend.js`, закэшированную браузером
ещё с прошлой загрузки страницы в этой же сессии.

## Причина

```php
// shopPrefillPluginAssetsManager::init()
$add_js('js/modules/HttpClient.js');           // без "?"
...
$add_js('js/prefill.frontend.js?');            // debug-режим, строка 58
...
$add_js('js/prefill.frontend.min.js?');        // prod-режим, строка 62
```

Модули (`js/modules/*.js`) подключаются **без** query-строки — ядро Webasyst само добавляет
версионирующий суффикс (в проверке это было видно как `?1.0.0.1787068785`, где хвост — версия
плагина + build-time). А `prefill.frontend.js` / `prefill.frontend.min.js` уже передаются в `$add_js`
с трейлинг-`?`. Похоже на попытку форсировать cache-busting, но эффект обратный: раз query-строка уже
не пуста, механизм ядра, добавляющий версию, либо не срабатывает, либо добавляет версию в уже
битую позицию — на проверенной странице итоговый `<script src>` был
`.../js/prefill.frontend.js?` **без** какого-либо `?v=...` суффикса вообще, в отличие от соседних
модулей.

Итог: URL этого файла не меняется никогда, независимо от версии плагина. Браузер кэширует его по
обычным HTTP cache-заголовкам ответа сервера для статики и может отдавать старую копию сколь угодно
долго после апдейта плагина — до полного сброса кэша посетителем.

## Чем плохо

- После любого релиза плагина у части посетителей с уже открытой (или недавно закэшированной)
  версией страницы контроллер `PrefillFrontendController` может ещё долго работать по старому коду:
  новые модули (`Logger`, `ConsentManager` и т.д.) подключаются с версией и обновляются сразу, а
  главный файл, который их связывает через DI, — нет. Рассинхрон версий внутри одной страницы.
- Баг тихий: ничего не падает, просто часть исправлений (как в issue-69) фактически не доезжает до
  части аудитории до истечения TTL кэша браузера или ручного hard-refresh.
- Затрудняет тестирование фиксов в браузере: разработчик может решить, что фикс не сработал, хотя
  сработал — как и произошло здесь.

## Как проверить

```js
// В консоли на живой странице витрины
Array.from(document.querySelectorAll('script[src*="prefill"]')).map(s => s.src)
```

`prefill.frontend.js` (или `.min.js` в prod) — единственный без `?v=...` в хвосте; у
`js/modules/*.js` версия есть.

## Как чинить

Убрать трейлинг-`?` в обоих вызовах (`shopPrefillPluginAssetsManager.class.php:58,62`) и передавать
путь так же, как у модулей — без query-строки, — чтобы версия ядра приклеивалась штатно:

```php
$add_js('js/prefill.frontend.js');
...
$add_js('js/prefill.frontend.min.js');
```

После фикса проверить тем же снипетом, что у `prefill.frontend(.min).js` появился `?v=...` суффикс,
меняющийся при бампе версии плагина (`/release-start`).

## Что сделано

Убран трейлинг-`?` в обоих вызовах `shopPrefillPluginAssetsManager::init()` — путь передаётся так же,
как у модулей:

```php
$add_js('js/prefill.frontend.js');       // строка 58, debug
$add_js('js/prefill.frontend.min.js');   // строка 62, prod
```

Механика в ядре (`waPlugin::addJs()`, `wa-system/plugin/waPlugin.class.php:326`): версия
приклеивается **только если в URL ещё нет `?`** — `if (false === strpos($url, '?')) $url .= '?'.$this->getVersion();`
плюс `.time()` при `debug = true`. Трейлинг-`?` делал условие ложным, и файл уходил вообще без версии.
`waPlugin::addCss()` устроен идентично, поэтому CSS-пути (`css/frontend(.min).css`) версионировались
корректно и правки не потребовали.

Отдельный случай — per-storefront CSS из `wa-data`: он идёт мимо `addCss()` плагина, поэтому у него
свой явный cache-buster `?{update_time}` в `shopPrefillPluginCssManager::getPublicUrl()`. Генерируемые
`variables_{md5}.css` и `{md5}.js` в busting не нуждаются — имя файла и есть хеш содержимого.

## Проверка

Витрина `/order/`, гостевая сессия (curl с пустой банкой кук) + вкладка браузера.

**debug = true** (модули отдельными файлами):

```
js/modules/HttpClient.js?1.0.0.1787152959
...
js/prefill.frontend.js?1.0.0.1787152959   ← было `?` без версии
```

**debug = false** (временно переключён в `wa-config/config.php`, затем возвращён):

```
css/frontend.min.css?1.0.0
js/prefill.frontend.min.js?1.0.0          ← было `?` без версии
```

Контроллер поднимается штатно: `window.prefill` — объект `PrefillFrontendController`,
`dialogManager.messages` содержит 15 ключей (то самое место, где issue-69 казался несработавшим).
Ошибок в консоли от плагина нет.
