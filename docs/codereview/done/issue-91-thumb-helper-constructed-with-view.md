# Issue 91 — `buildThumbUri()` не строит миниатюру никогда: хелпер создаётся с `waView` вместо `waSystem`

**Статус:** исправлено 09.09.2026 (в тот же день, что и найдено). Проверено на витрине: в свёрнутой
карточке Дзен-режима `<img src>` = `*.100x75.jpg`, файлы созданы рядом с оригиналами, отрисованный
размер 77×58 при natural 100×75.
**Приоритет:** 🟠 Важно до продажи
**Сложность фикса:** 🔧 Небольшой
**Файлы:** `lib/classes/zenmode/shopPrefillPluginZenData.class.php` (`buildThumbUri()`, строки 626–639; `buildPhotosHtml()`, строка 602)

Найдено ревью коммита `86656dc` («расписание и фото пункта выдачи в свёрнутой карточке Дзен-режима»).

## Как это работает сейчас

`buildThumbUri()` создаёт хелпер приложения, передавая в конструктор **представление**:

```php
$thumb = (new shopViewHelper(wa()->getView()))->imgUrl($uri, '100x75');
return is_string($thumb) && $thumb !== '' ? $thumb : $uri;
```

Конструктор `waAppViewHelper` (`wa-system/view/waAppViewHelper.class.php:15-20`) ждёт `waSystem` и
безусловно дёргает у аргумента `getConfig()`:

```php
public function __construct($system)
{
    $this->wa = $system;
    if ($system && $system->getConfig() && method_exists($system->getConfig(), 'getApplication')) {
```

`wa()->getView()` возвращает `waSmarty3View` (`wa-system/waSystem.class.php:175`), у которого нет ни
`getConfig()`, ни `__call()`. Само ядро создаёт хелпер иначе — `new $class($wa)`, где `$wa = wa($app)`
(`wa-system/view/waViewHelper.class.php:1739-1749`).

Проверено исполнением (CLI, бутстрап как в `wa.php`):

```text
view class: waSmarty3View
THROWN(View): Error: Call to undefined method waSmarty3View::getConfig()
helper(waSystem) OK -> imgUrl('http://x/y.jpg') = 'http://x/y.jpg'
```

`Error` реализует `Throwable`, поэтому его молча ловит собственный `catch` метода и возвращает
`$uri` — путь оригинала. Фоллбэк, задуманный на редкую ошибку хелпера, стал единственной веткой.

## Что из этого следует

1. **Миниатюра не строится ни разу.** В свёрнутую карточку 77×58 px уезжает полноразмерный файл —
   ровно то, что метод должен предотвращать. Его же docblock и
   [zen-photos-css-scope-broken.md:107](../../bugs/done/zen-photos-css-scope-broken.md) утверждают обратное:
   «`buildThumbUri()` зовёт тот же `$wa->shop->imgUrl($uri, '100x75')`, что и `details.html`».
   Фактически не зовёт.
2. **Сценарий отказа.** Администратор загружает в настройках пункта выдачи фото с телефона
   (3000×2000, 2–4 МБ). Плагин доставки кладёт в `custom_data[...]['photos']` только `uri` (у `sd`
   это буквально загруженный файл), `thumb_uri` пуст → `buildPhotosHtml()` зовёт `buildThumbUri()` →
   в `<img src>` попадает оригинал. Два фото ПВЗ = несколько мегабайт на мобильном канале ради
   картинок размером с ноготь. Развёрнутый виджет ядра рядом отдаёт те же фото как `100x75`.
3. **Отказ невидим для превью настроек.** `getSampleData()` кладёт в `thumb_uri` готовый плейсхолдер,
   ветка `buildThumbUri()` там не исполняется — проверка шаблона в бэкенде баг не покажет, только
   витрина.
4. **Ошибка нигде не всплывает.** `catch (Throwable)` не логирует: ни в `wa-log/prefill.plugin.log`,
   ни в PHP-лог ничего не попадает.

## Что сделано

1. Хелпер берётся штатным путём — `wa()->getView()->getHelper()->shop` (тот же объект, что `{$wa->shop}`
   в `details.html`); ядро кэширует его в `waViewHelper::__get()`, поэтому конструктор с чтением
   domain-конфига под CDN отрабатывает один раз, а не на каждое фото. Резолвится он один раз на вызов
   `buildPhotosHtml()` и передаётся в `buildThumbUri()` параметром.
2. Ответ хелпера валидируется строже, чем `!== ''`: **на несуществующем файле `imgUrl()` возвращает не
   пустую строку, а корень витрины** (`realpath()` → `false`, дальше `str_replace()` + `getRootUrl()`),
   и такой `src` утянул бы в `<img>` целую страницу. Этой ветки в описании ниже не было — найдена
   исполнением при проверке фикса.
3. Откат на оригинал логируется: недоступный хелпер — `shopPrefillPluginLog::error()`, отсутствующая
   миниатюра — `debug()`. `catch (Throwable)` сохранён сознательно (падение посреди чекаута дороже
   тяжёлой картинки), но беззвучным он больше не является.

## Рекомендация

1. Передавать в конструктор систему, как это делает ядро:
   ```php
   $thumb = (new shopViewHelper(wa('shop')))->imgUrl($uri, '100x75');
   ```
2. **Создавать хелпер один раз на вызов `buildPhotosHtml()`, а не на каждое фото.** После фикса каждый
   вызов `imgUrl()` — это `realpath()` + `file_exists()`, а при первой генерации ещё и
   `shopImage::generateThumb()` с сохранением файла (`shopViewHelper::imgUrl`, строки 786–817).
   Сейчас цена не видна только потому, что конструктор падает сразу.
3. Логировать откат на оригинал (`shopPrefillPluginLog::debug`) — иначе следующая поломка хелпера
   так же уйдёт в тишину. Ловить `waException` (её `imgUrl` гасит сам) достаточно; `Throwable`
   целиком маскирует и ошибки программиста, как эта.
4. Проверить после фикса: ПВЗ с фото, свёрнутая карточка Zen → в `<img src>` путь вида
   `*.100x75.jpg`, файл physически создан рядом с оригиналом в `wa-data/public/shop/`. Живой прогон
   возможен после починки способа доставки `sd` на стенде (открытый пункт в [TODO.md](../../TODO.md)),
   либо на любом ПВЗ СДЭК с фотографиями.
