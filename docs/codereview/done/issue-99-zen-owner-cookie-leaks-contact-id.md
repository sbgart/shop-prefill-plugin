# Issue 99 — Кука `prefill_zen_owner` отдаёт клиентскому JS `contact_id` покупателя

**Статус:** ✅ Исправлена 09.09.2026
**Приоритет:** 🟠 Важно до продажи
**Сложность фикса:** 🔧 Небольшой
**Файлы:** `lib/classes/zenmode/shopPrefillPluginZenLatch.class.php` (`reconcile()` строки 163–167, `currentOwner()` строка 197)

## Как это работает сейчас

Кука-владелец защёлок пишется без `httponly` и без `secure`:

```php
// shopPrefillPluginZenLatch::reconcile(), строки 163-167
$this->response->setCookie(self::OWNER_COOKIE, $owner, [
    'expires'  => 0,
    'path'     => '/',
    'samesite' => 'Lax',
]);
```

Значение — усечённый md5 отпечатка личности:

```php
// currentOwner(), строка 197
return substr(md5($source_key ?? self::OWNER_ANONYMOUS), 0, 12);
```

`$source_key` приходит из `shopPrefillPluginFillParamsProvider::getSourceKey()` и для
авторизованного покупателя равен строке `'user:' . $contact_id`.

Докблок класса обосновывает выбор так:

> В куке лежит именно хеш, а не сырой ключ: сырой — это `'user:<contact_id>'`, а кука видна
> клиенту. Подделка неопасна (защёлка управляет только разворотом блока), поэтому HMAC не
> нужен — достаточно короткого хеша для сравнения.

Рассуждение верно про **подделку** и неверно про **обратимость**: `'user:<id>'` — вход с
энтропией порядка `log2(число контактов)`, и хеш от него разворачивается перебором.

## Что из этого следует

Проверено на стенде 09.09.2026. Алгоритм подтверждён живой кукой: у гостя из чистой банки
пришло `prefill_zen_owner=ebd896e5db7d`, и `substr(md5("\0anonymous"), 0, 12)` даёт ровно её.
Перебор `user:1 … user:2000000` на обычном PHP CLI занимает **0.54 с**:

```
$ php -r 'for($i=1;$i<=2000000;$i++) substr(md5("user:".$i),0,12);'
перебор 2 000 000 контактов: 0.54 c
```

То есть по значению куки `contact_id` авторизованного покупателя восстанавливается мгновенно.

Кто это видит. Кука не `httponly`, поэтому её читает **любой скрипт на странице витрины**:
тема, счётчик аналитики, виджет чата, рекламный тег — всё, что магазин подключает у себя и что
плагин не контролирует. Гостей это не касается: у них `guest:<48 hex>`, вход высокоэнтропийный
и необратимый; утечка ровно про авторизованных.

Масштаб честно: это не захват аккаунта и не доступ к данным — `contact_id` сам по себе ничего
не открывает. Это раскрытие постоянного идентификатора покупателя стороннему коду: он позволяет
связать визиты одного человека между собой и с другими данными, которые тот же скрипт собирает.
Для плагина, который продаётся в магазины, работающие с 152-ФЗ, это ровно тот класс претензии,
который дешевле закрыть до продажи, чем объяснять после.

Отдельно: **кука серверная по построению**. `prefill_zen_owner` не читает и не пишет ни одна
строка JS (проверено грепом по `js/`, `templates/`, `lib/`) — в отличие от самих защёлок
`prefill_zen_{group}`, которые `js/modules/ZenModeToggle.js` ставит и снимает на кликах, и
которым доступ из JS действительно нужен. Значит `httponly` ничего не ломает.

Инвариант нарушен и внутренний: все остальные куки плагина закрыты, причём соседнее хранилище
приняло то же решение по той же причине —

```php
// shopPrefillPluginGeoStorage::writeCookie()
// Источник в куку не кладём: он идентифицирует покупателя, а куке жить год.
```

а `prefill_consent`, `prefill_guest_token` и `prefill_geo` ставятся с
`'secure' => waRequest::isHttps(), 'httponly' => true`.

## Рекомендация

1. Добавить в `setCookie()` владельца те же атрибуты, что у остальных серверных кук плагина:
   ```php
   'secure'   => waRequest::isHttps(),
   'httponly' => true,
   ```
   Это закрывает основной канал (сторонний JS на витрине) и ничего не меняет в логике: значение
   читает только PHP через `waRequest::cookie()`.
2. Заодно убрать обратимость — подмешать в хеш постоянную соль установки, чтобы значение не
   вычислялось из одного лишь `contact_id`. Дешёвый вариант без нового хранилища —
   `md5($source_key . '|' . wa()->getConfig()->getPath('config'))` либо любой уже существующий
   per-install секрет. Пункт 1 без пункта 2 достаточен против стороннего JS; пункт 2 нужен,
   чтобы значение не читалось из бэкапа браузерного профиля и из общего компьютера.
3. Поправить докблок класса: сейчас он утверждает, что хеш скрывает сырой ключ. Написать честно —
   от подделки защиты нет и не нужно, от чтения защищает `httponly` (+ соль).

Проверка: `curl -sk -D - https://wa-dev.loc/order/ -o /dev/null | grep -i 'set-cookie:.*zen_owner'` —
в заголовке должны появиться `secure` и `HttpOnly`; сценарии защёлки из
[плана](../plans/zen-collapse-latch-identity-scope.md) (репро, Z4 кликом «Изменить», логаут,
оформление заказа) прогнать заново — они не должны измениться, `tests/ZenLatchIdentityTest.php`
остаётся зелёным.

## Фикс (09.09.2026)

Оба пункта рекомендации внесены в `shopPrefillPluginZenLatch`:

1. `reconcile()` ставит `prefill_zen_owner` с `'secure' => waRequest::isHttps(), 'httponly' => true`
   — как у остальных серверных кук плагина.
2. `currentOwner()` солит хеш install-специфичной константой
   (`wa('shop')->getConfig()->getIdentityHash()`, тот же `identity_hash` из
   `wa-config/config.php`, которым `shopConfig` метит инсталляцию перед Webasyst ID) через
   новый приватный `installSalt()`. Ошибка чтения конфигурации не роняет дзен-режим —
   деградирует к прежнему, несолёному хешу (B2a).
3. Докблок `currentOwner()` переписан: снят ложный тезис «хеш скрывает сырой ключ», добавлено
   честное обоснование соли и явно сказано, что `httponly` — второй рубеж, не единственный.

Проверено:

- `php tests/ZenLatchIdentityTest.php` — все 26 проверок зелёные (тест дополнен статическим
  `waRequest::isHttps()` в своих заглушках окружения);
- живой прогон curl-ом на стенде: `Set-Cookie: prefill_zen_owner=…; path=/; secure; HttpOnly;
  SameSite=Lax` — оба атрибута на месте.

Соль не устраняет теоретическую возможность подбора при утечке `identity_hash` вместе с
кукой, но снимает главный практический риск — готовые радужные таблицы по `'user:<id>'` и
перебор без знания install-специфичного секрета.

### Разовый побочный эффект смены схемы хеша

Проверено изолированным стендом на реальном классе (заглушки `waRequest`/`waResponse`/`wa()`,
как в `ZenLatchIdentityTest`): браузер, пришедший с кукой владельца, записанной **до** соли,
попадает в ветку «сменилась личность», хотя личность та же.

```
старый владелец: ebd896e5db7d   (substr(md5("\0anonymous"), 0, 12))
новый владелец:  af2c2ac64eec   (substr(md5(identity_hash . "|\0anonymous"), 0, 12))

OK: защёлка покупателя НЕ действует после смены схемы хеша (личность та же!)
OK: сняты защёлки всех трёх групп
OK: владелец перезаписан новым, солёным
OK: в лог ушло «Zen latches dropped: identity changed» — хотя личность НЕ менялась
```

Два следствия, оба разовые — ровно один запрос на браузерный профиль:

1. **Окно нарушения Z4.** Защёлки сняты, значит `shouldCollapseGroup()` идёт дальше кука-ветки
   к проверке данных. Группа, которую покупатель сам развернул кнопкой «Изменить» и минимум
   которой заполнен, свернётся под руками — то самое, что Z4 запрещает.
2. **Ложная строка в логе.** `'Zen latches dropped: identity changed'` заведена, чтобы
   браузерный прогон отличал сверку от совпадения; здесь она врёт. Схема хеша не versioned,
   и отличить «старый формат» от «другая личность» код не может по построению.

Почему не чинится сейчас: плагин не выпущен, установок со старыми куками не существует —
эффект достанется только этому стенду, по одному разу на профиль. Для покупателей первая же
полученная версия будет солёной изначально.

**Когда вернуться:** если вход хеша (соль или формат `source_key`) когда-нибудь изменится
снова — уже на выпущенном плагине, — эффект повторится у живых покупателей. Тогда нужен
маркер схемы в значении куки (префикс вида `2:`), чтобы `reconcile()` мог отличить «старый
формат той же личности» от «другая личность»: пересчитать старый хеш, сверить, и при
совпадении переписать куку молча, не снимая защёлки и не засоряя лог.
