# Issue 64 — CSS и JS плагина подключаются на всех страницах витрины, а нужны только в корзине

**Статус:** ⬜ Открыта
**Приоритет:** 🟠 Средний (скорость витрины, Core Web Vitals покупателя)
**Сложность фикса:** 🔧 Небольшой
**Файлы:** `lib/classes/hooks/shopPrefillPluginFrontendHooks.class.php` (`handleFrontendHead`, `initializeFrontendAssets`), `lib/classes/view/shopPrefillPluginAssetsManager.class.php`

## Проблема

`frontend_head` — хук всех страниц магазина. В нём безусловно вызывается `initializeFrontendAssets()`, который:

- подключает `css/frontend.min.css` (или per-storefront CSS-файл);
- подключает `js/prefill.frontend.min.js` (13 КБ);
- генерирует и записывает на диск файл CSS-переменных (`variables_{md5}.css`);
- генерирует и записывает на диск JS-инициализатор (`{md5}.js`) — с `json_encode` и вызовами `_wp()` для 11 строк локализации;
- добавляет ещё два `<link>`/`<script>` в `<head>`.

Всё это работает и на главной, и в категории, и в карточке товара — там ни одного элемента плагина на странице нет. Весь функционал (Zen Mode, диалог «Мои варианты», чекбокс согласия) живёт исключительно на странице оформления заказа.

Дополнительно на каждой странице выполняется `resolveStorefrontCssUrl()` — `file_exists()` по диску, и `getFillParams()` — запросы к БД (см. [issue-63](issue-63-guest-hash-lookup-full-scan.md)).

## Последствия

- 4 лишних HTTP-запроса (2 статических файла + 2 сгенерированных) на каждой странице каталога.
- Блокирующие `<link rel=stylesheet>` в `<head>` там, где стилизовать нечего.
- Магазин, покупающий плагин ради удобного чекаута, платит за это скоростью всего каталога — это первое, что заметит любой аудит скорости.

## Рекомендация

1. Разделить два действия хука:
   - **предзаполнение сессии** (`prefill.on_entry`) — оставить на всех страницах, это заявленная фича;
   - **подключение ассетов** — только на странице оформления заказа.
2. Признак страницы чекаута на витрине — маршрут корзины/заказа. Проверять по `waRequest::param('module')`/`action` или по URL текущего маршрута; фоллбэк — настройка витрины на случай нестандартной темы.
3. Заодно снимается часть проблемы «мусор в `wa-data`» из [issue-57 §3](issue-57-minor-robustness-findings.md): файлы генерируются реже.
4. Проверить в браузере, что `wa_order_form_ready` по-прежнему ловится: бандл должен быть подключён до рендера формы заказа, а не после.
