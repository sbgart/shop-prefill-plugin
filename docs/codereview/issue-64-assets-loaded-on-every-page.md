# Issue 64 — CSS и JS плагина подключаются на всех страницах витрины, а нужны только в корзине

**Статус:** ✅ Закрыта 20.08.2026 — ассеты подключаются только на странице оформления заказа, проверено на витрине
**Приоритет:** 🟠 Средний (скорость витрины, Core Web Vitals покупателя)
**Сложность фикса:** 🔧 Небольшой
**Файлы:** `lib/classes/checkout/shopPrefillPluginCheckoutPageDetector.class.php` (новый), `lib/classes/hooks/shopPrefillPluginFrontendHooks.class.php`, `lib/shopPrefill.plugin.php`

## Проблема

`frontend_head` — хук всех страниц магазина. В нём безусловно вызывался `initializeFrontendAssets()`, который:

- подключает `css/frontend.min.css` (или per-storefront CSS-файл);
- подключает `js/prefill.frontend.min.js` (13 КБ);
- генерирует и записывает на диск файл CSS-переменных (`variables_{md5}.css`);
- генерирует и записывает на диск JS-инициализатор (`{md5}.js`) — с `json_encode` и вызовами `_wp()` для 11 строк локализации;
- добавляет ещё два `<link>`/`<script>` в `<head>`.

Всё это работало и на главной, и в категории, и в карточке товара — там ни одного элемента плагина на странице нет. Весь функционал (Zen Mode, диалог «Мои варианты», чекбокс согласия) живёт исключительно на странице оформления заказа.

Дополнительно на каждой странице выполнялся `resolveStorefrontCssUrl()` — `file_exists()` по диску, а при отсутствии файла ещё и запись в `wa-data`.

**Замер до фикса** (глобальный debug включён, поэтому модули подключаются по одному):

```text
GET /                      → 11 ссылок на plugins/prefill
GET /torsher-trapezia-02/  → 11
```

## Последствия

- 4 лишних HTTP-запроса в проде (2 статических файла + 2 сгенерированных) и 11 в debug — на каждой странице каталога.
- Блокирующие `<link rel=stylesheet>` в `<head>` там, где стилизовать нечего.
- Магазин, покупающий плагин ради удобного чекаута, платил за это скоростью всего каталога — это первое, что заметит любой аудит скорости.

## Решение

Признак «текущий запрос рендерит форму заказа» вынесен в отдельный класс
`shopPrefillPluginCheckoutPageDetector`. Признаков два, и ни один по отдельности не покрывает все темы:

1. **Сработал любой checkout-хук плагина.** Точный и не зависящий от шаблонов темы (правило B3):
   `checkout_before_auth` вызывает ядро из `shopCheckoutStep::processAll()`. Успевает вовремя,
   потому что шаблон экшена (`order.html` → `$wa->shop->checkout()->form()`) рендерится **до** макета,
   а `frontend_head` срабатывает уже в макете — `waViewController::executeAction()` сначала собирает
   `$content`, и только потом зовёт `$this->layout->display()`. Ловит и нестандартный случай
   «форма вставлена в произвольную страницу витрины».
   Отметку ставит единая точка входа `shopPrefillPlugin::enterCheckoutHooks()`.
2. **Маршрут `frontend/order`.** Подстраховка для темы, которая рендерит форму уже из макета:
   там хуки сработают после `frontend_head` и признак 1 опоздает. Берётся модуль с экшеном
   из `routing.php`, а не URL, — магазин волен повесить чекаут на любой адрес.

Заодно:

- `resolveStorefrontCssUrl()` передаётся в `FrontendHooks` резолвером, а не готовой строкой, — на каталоге
  диск не трогается вовсе;
- убран ранний выход `!guest_enabled && !isAuth()`: он гасил ассеты и там, где они нужны, — см. ниже.

### Побочно закрыто: свёрнутый Zen-блок без кнопки «Изменить» (нарушение Z3)

Ранний выход по гостевым настройкам стоял **до** подключения ассетов. При выключенном
`prefill.guest.enabled` гость на чекауте получал 12 свёрнутых Zen-блоков и ноль JS — кнопка
«Изменить» была мёртвой, чекаут без выхода. Замер прежним кодом (20.08.2026):

```text
СТАРОЕ поведение, гость + guest.enabled=false:
  бандл prefill.frontend.js: 0
  zen-блоки в разметке:      12
```

Теперь гостевые настройки проверяет только `handleGuestCookies()` (он и раньше делал это сам —
внешняя проверка дублировала внутреннюю), а ассеты подключаются по признаку страницы.

Ошибок плагина в консоли ни на одном шаге нет (записи `Errors:` в логе — от ядра, про невалидный

фоне в тёмной теме. К этой правке отношения не имеет (ассеты те же), заведена
[issue-85](issue-85-confirm-button-invisible-in-dark-theme.md).

Настройки, которые трогались и возвращены в исходное: `styles.custom_css` и `prefill.guest.enabled`
глобальной витрины `*`. Тестовые строки `shop_cart_items` удалены.

## Что осталось за рамками

- `/checkout/success/` ассеты больше не получает — на нём плагину работать нечем, вся его разметка
  живёт в форме заказа. Серверная часть `frontend_head` (выдача и продление `auth_token`) там
  по-прежнему отрабатывает: она стоит вне гейта.
- Пункт «мусор в `wa-data`» из [issue-57 §3](issue-57-minor-robustness-findings.md) стал мягче —
  файлы генерируются только на чекауте, — но сам по себе не закрыт.
