# Issue 68 — Диалог «Мои варианты» поднимает все заказы покупателя, гидратирует все и выбрасывает всё кроме пяти

**Статус:** ✅ Закрыта 19.08.2026 — лимит перенесён на варианты, гидратация и чтение заказов сведены к четырём запросам
**Приоритет:** 🟠 Средний (перф + память; страдают лучшие клиенты магазина)
**Сложность фикса:** 🔨 Средний
**Решение:** сбор вариантов страницами до набора лимита (`collectUniqueDeliveryOrderIds()`), сжатая выборка подписи (`getOrdersDeliveryParamsByIds()`), батчевый прогрев строк заказов (`preloadOrderRows()`), число карточек — настройка витрины `my_delivery_variants_limit`
**Файлы:** `lib/classes/fillparams/shopPrefillPluginFillParamsProvider.class.php` (`getFillParamsCollection`), `lib/actions/frontend/shopPrefillPluginFrontendParamsChoice.action.php`, `lib/classes/orders/shopPrefillPluginOrderProvider.class.php` (`getUserOrdersId`)

## Проблема

Цепочка на открытие диалога:

1. `getUserOrdersId($contact_id)` — **без `LIMIT`**: все ID заказов покупателя за всё время.
2. `getOrdersParamsByIds($orders_ids)` — все параметры всех этих заказов одним запросом (по ~20 строк на заказ).
3. Дедупликация: строится «лёгкий» `FillParams` на каждый заказ — это сделано правильно, запросов нет.
4. **Гидратация всех уникальных вариантов**:

   ```php
   foreach ($unique_orders_params as $order_id => $order_params) {
       $fill_params = $this->getFillParamsByOrderParams($order_params, $order_id);
       $this->fill_params_collection->add($fill_params);
   }
   ```

   А `getFillParamsByOrderParams()` с непустым `$order_id` делает на каждый элемент:
   - `getOrderComment($order_id)` — SELECT;
   - `getContactIdFromOrder($order_id)` — SELECT;
   - `new waContact($contact_id)` + `getAuthData()` — загрузка контакта и всех его полей.

5. И только **после** этого экшен режет список:

   ```php
   $items = array_slice($items, 0, 5);
   ```

## Последствия

Покупатель с 200 заказами и 30 разными адресами: ~4000 строк параметров в память + ~60 SELECT + 30 загрузок контакта — ради пяти карточек. Причём `contact_id` у всех этих заказов один и тот же (это заказы одного покупателя), то есть загрузка контакта повторяется 30 раз подряд.

Для гостей то же самое плюс запрос из [issue-63](issue-63-guest-hash-lookup-full-scan.md) без `LIMIT 1`.

## Рекомендация

1. Резать **до** гидратации. Сортировка «свежие первыми» уже есть в провайдере (`array_reverse` по ключам), поэтому лимит можно применить сразу после дедупликации, а `array_slice` в экшене оставить как страховку.
2. Вынести лимит в константу (`FillParamsCollection::DEFAULT_LIMIT = 5`) и параметр `getFillParamsCollection(int $limit = 5)` — сейчас «5» зашито в экшене, а `toArray(?int $limit)` в коллекции никто не вызывает с аргументом.
3. Ограничить выборку заказов на уровне SQL: `getUserOrdersId()` → `LIMIT 50` (с запасом на дубли), `getAllOrderIdsByGuestHash()` — так же.
4. Кэшировать контакт: в цикле `fillAuthDataFromOrder()` `contact_id` повторяется — достаточно статического кэша в `ContactProvider::getContact()`.
5. Комментарий читается отдельным SELECT на заказ (`getOrderComment`) — при батче можно взять `id, comment, contact_id` одним запросом по массиву ID.


## Замер на живой базе (18.08.2026)

`general_log` за одно открытие диалога у контакта 1 (52 заказа, показывается 5 карточек):

```
SELECT id FROM shop_order WHERE (contact_id='1') ORDER BY id DESC LIMIT 50
SELECT * FROM shop_order_params WHERE `order_id` IN ('85','84','83', … 50 штук)
SELECT id, contact_id, comment FROM shop_order WHERE (id='58')
… ещё 12 таких же, по одному на заказ …
```

Итого **15 запросов**, из них 13 — построчные чтения `shop_order` через `getOrderRow()`.
`LIMIT 50` в первом запросе уже есть, так что «все заказы за всё время» — неточность
исходной формулировки: потолок 50, но 13 отдельных PK-запросов вместо одного `IN ()`
остаются, и до пяти карточек доживает меньше трети выбранного.

Важно: на общую стоимость страницы это не влияет — путь срабатывает только по явному
клику на «Мои варианты», не на каждом запросе. Контракт issue-63 не нарушен.


## Что сделано (19.08.2026)

Отдельно от перфа вскрылась смысловая ошибка лимита: он мерялся **в заказах**, а не в вариантах.
Покупатель, полсотни раз подряд заказавший одним способом, терял редкий второй адрес — тот просто
не попадал в окно `LIMIT 50`, при том что дедупликация схлопывала все пятьдесят одинаковых заказов
в одну карточку и четыре слота из пяти пустовали.

1. **Лимит меряется в вариантах.** `collectUniqueDeliveryOrderIds()` добирает историю страницами,
   пока не наберёт нужное число различных вариантов или пока заказы не кончатся. Страница растёт
   вдвое (50 → 100 → 200 → …, потолок `HISTORY_PAGE_MAX = 400`): у покупателя с двумя-тремя адресами
   всё находится на первой, а редкий вариант из глубины истории стоит единиц запросов, а не сотни
   страниц по 50. Заказы на отключённых инстансах доставки больше не «съедают» окно — добор
   продолжается за их счёт.
2. **Дедупликация читает только подпись.** `getOrdersDeliveryParamsByIds()` тянет `name LIKE 'shipping%'` —
   ровно то, что сравнивает `isSameDeliveryOption()`. На живой базе это ~10 строк на заказ вместо ~28,
   поэтому глубокий добор не оплачивается лишним трафиком.
3. **Гидратация — только для выживших.** Полные параметры и строки заказов дочитываются после отсева:
   `getOrdersParamsByIds()` + `preloadOrderRows()` — по одному запросу на всю выдачу вместо N
   построчных `getOrderRow()` (закрывает и [issue-17](issue-17-n-plus-1-comment-contact-per-order.md)).
4. **Число карточек — настройка витрины.** `prefill.my_delivery_variants_limit`, 1–10, по умолчанию 5.
   Диапазон и фоллбэк — `shopPrefillPluginFillParamsCollection::normalizeLimit()`: клампим на чтении,
   потому что `min`/`max` у `<input type="number">` обходятся запросом мимо формы. Экшен больше не
   хардкодит пятёрку, `array_slice` остался страховкой.

5. **Контакт грузится один раз.** `ContactProvider` кэширует и сам `waContact`, и результат
   `getAuthData()` на время запроса. Второе важнее первого: ядро не кэширует **пустые** поля
   (`waContactStorage::get()` пишет кэш только при непустом результате), поэтому каждая карточка
   заново перечитывала `im`, `url`, `socialnetwork` и прочие незаполненные поля.
   Замер на контакте 1 с пятью карточками: `wa_contact_data` — **29 запросов → 9**.

### Замер после фикса (19.08.2026)

Тот же контакт 1 (52 заказа), `general_log` за одно открытие диалога, лимит 8:

```
SELECT id FROM shop_order WHERE contact_id = 1 ORDER BY id DESC LIMIT 0, 50
SELECT order_id, name, value FROM shop_order_params WHERE order_id IN (85,84,…) AND name LIKE 'shipping%'
SELECT * FROM shop_order_params WHERE `order_id` IN ('72','73','74','75','76','81','82','85')
SELECT id, contact_id, comment FROM shop_order WHERE id IN (72,73,74,75,76,81,82,85)
```

**4 запроса вместо 15**, и число построчных чтений `shop_order` больше не растёт с длиной истории.
Весь HTTP-запрос диалога: **79 → 64 SQL** (остальное — инициализация Webasyst, не наша цепочка).

Проверка добора: с временно уменьшенной страницей (`HISTORY_PAGE_SIZE = 3`) и лимитом 10 выдача
совпала с эталонной при странице 50 — те же ID `64 65 72 73 74 75 76 81 82 85`, а страницы шли
`LIMIT 0,3` → `LIMIT 3,6` → `LIMIT 9,12`, то есть смещение и рост страницы не теряют и не дублируют
заказы. Настройка проверена end-to-end: сохранение из бэкенда → 3 карточки в диалоге на витрине.
