# Issue 86 — секции группы delivery заполняются независимо от полноты источника

**Статус:** ⬜ Открыта
**Приоритет:** 🟡 Средний
**Сложность фикса:** 🧩 Требует решения — примитив для гейта готов, применение не сделано
**Файлы:** `lib/classes/sessionstorage/shopPrefillPluginSessionStorageProvider.class.php` (`applyPrefill`), `lib/classes/fillparams/shopPrefillPluginFillParams.class.php` (`hasDataForSection` — зарезервирован, без вызовов)
**Смежные:** [issue-84](issue-84-prefill-inconsistent-across-groups.md) п.2 — вынесена сюда 23.08.2026 при закрытии issue-84 (по образцу issue-52 → issue-79); [issue-65](issue-65-prefill-overrides-current-input.md) — связность **внутри** группы, здесь — **между** источниками и секциями

## Проблема

```php
// applyPrefill()
foreach (self::SECTIONS as $section_id) {
    if ($checker->canPrefillSection($section_id, $checkout_params)) {
        $available[] = $section_id;
    }
}
```

Каждая секция решает за себя. Но вариант доставки зависит от адреса, а не только от собственной секции: адрес принадлежит покупателю (новый город — свой, или от cityselect), `region`/`details` пусты в источнике → подставляем вариант из прошлого заказа под чужой или дефолтный адрес. Пункт самовывоза при этом может физически находиться в другом городе.

Частично прикрыто сигналом `prefill_delivery_unavailable` (`renderDeliveryUnavailableScript()`), но это лечение симптома после того, как ядро не нашло вариант — и сигнал работает только на явном выборе карточки (кука `prefill_user_selected`), не на автопредзаполнении.

## Раскол бывает двух разных видов, и они лечатся по-разному

Первая версия issue-84 предлагала «группа delivery атомарна: занята любая секция — не заполняем ни одну». Разбор 22-23.08.2026 показал, что это смешивает два независимых механизма:

- **Раскол по владению.** Часть секций группы уже занята покупателем (`html`), часть — свободна. Проверка кодом (`SessionStorageProvider::applyPrefill()`, `SectionChecker::isSectionOwnedByCustomer()`) показала: **это состояние недостижимо** после архитектуры issue-65. Ядро заменяет весь `order` в сессии целиком на каждый POST (`shopFrontendOrder.actions.php:37`, `$session_checkout['order'] = $input`), а `html` сопровождает практически любой реальный POST (поле `reload` инициализируется в `true` и остаётся `true` после каждого `update()` в `form.js`). Значит владение бинарно: либо `html` есть у всех шести секций разом, либо ни у одной. «Занята любая — не заполняем» адресует состояние, которого не бывает — писать код под него не нужно.
- **Раскол по полноте источника.** Сам источник (историческая запись заказа) может не содержать данных для части группы — например, у заказа есть `shipping_id`/`shipping_rate_id`, но нет города (импорт, ручной заказ из бэкенда, старый формат данных до какого-то релиза плагина). Это **достижимо и ничем не прикрыто**: `applyPrefill()` пишет каждую доступную секцию вслепую, не спрашивая источник, покрывает ли он группу целиком.

## Рекомендация

Атомарность записи по обеим осям: секция группы `delivery` пишется, только если (1) она не занята покупателем (уже есть, `canPrefillSection()`) **и** (2) источник покрывает всю группу — город и вариант доставки минимум; `details` производная, отдельным условием не гейтится, у самовывоза законно нет улицы.

Готовый примитив для второй половины уже есть и зарезервирован: `shopPrefillPluginFillParams::hasDataForSection()` — сегодня без единого вызова. Ветка `shipping` уже переведена на `getShippingVariantId() !== null` (при удалении `shipping_type_id`, план [delivery-variant-identity.md](../plans/delivery-variant-identity.md)). Перед первым боевым использованием сверить остальные ветки (`auth`, `region`, `details`) с тем, что реально пишут сеттеры — расхождение уже зафиксировано в [issue-53](issue-53-empty-prefill-writes-session.md), раздел «Отвергнутые варианты» (`country_name`/`region_name` вместо `country`/`region`, и три из пяти проверяемых свойств `details` никогда не устанавливаются).

Отдельная пометка происхождения секции (вариант B из первой версии issue-84) после архитектуры issue-65 не нужна: `html` уже и есть отметка происхождения (сессия vs источник) — только он решает вопрос владения, которого не существует. Усиление сигнала `prefill_delivery_unavailable` (вариант C) неприменимо к автопредзаполнению в принципе: сигнал зависит от куки `prefill_user_selected`, которую ставит только JS диалога «Мои варианты».

## Проверка

1. Источник (история заказов) без города, но с вариантом доставки → новый чекаут гостя/покупателя → секция `shipping` не заполняется отдельно от `region`.
2. Прошлый заказ с курьером по Москве → сменить город на Казань (руками или через cityselect) → пересчёт → курьерский вариант московского тарифа не подставляется.
3. Обычный сценарий: покупатель с историей, город не менял, источник покрывает всю группу → доставка предзаполняется как раньше.
