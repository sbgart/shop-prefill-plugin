# Issue 67 — `isSameDeliveryOption()`: `null` у кандидата совпадает с чем угодно, варианты схлопываются

**Статус:** ✅ Закрыта 18.08.2026
**Приоритет:** 🟠 Средний (функциональная потеря данных в диалоге «Мои варианты»)
**Сложность фикса:** 🔧 Небольшой
**Решение:** симметричное сравнение через приватный `areDeliveryValuesEqual()` — скаляры через `(string) ($left ?? '') === (string) ($right ?? '')`, массивы только когда обе стороны массивы
**Файл:** `lib/classes/fillparams/shopPrefillPluginFillParams.class.php:477`

## Проблема

```php
} else {
    // Строгое (но без приведения типов) сравнение
    if ($this_value !== null && $this_value != $other_value) {
        return false;
    }
}
```

Если у `$this` скалярное поле не заполнено (`null`), проверка пропускается. Объекты считаются одинаковыми по этому полю независимо от значения `$other`.

Метод поэтому несимметричен:

```php
$without_street->isSameDeliveryOption($with_street); // true
$with_street->isSameDeliveryOption($without_street); // false
```

Это противоречит комментарию метода — «полное совпадение параметров доставки» — и не позволяет использовать его как отношение эквивалентности для дедупликации. [Issue 23](done/issue-23-is-same-delivery-one-sided-comparison.md) исправила одностороннее сравнение массивов, но скалярная ветка осталась односторонней.

## Где проявляется

### 1. Дедупликация истории

`isSameDeliveryOption()` используется в `getFillParamsCollection()`:

```php
foreach ($seen_delivery_options as $seen) {
    if ($candidate->isSameDeliveryOption($seen)) {
        $is_duplicate = true;
        break;
    }
}
```

Обход идёт от новых заказов к старым, поэтому `$candidate` — более старый заказ. Если у старого заказа отсутствует поле, которое заполнено у более нового, старое значение работает как wildcard.

Например, старый заказ без `street` может быть признан дублем нового заказа с улицей, хотя это могли быть разные адреса. Старый вариант тогда не попадёт в диалог «Мои варианты», а в логе ошибки не будет.

### 2. Подсветка текущей карточки

Второй потребитель находится в `FrontendParamsChoice`:

```php
$item_array['is_current'] = $item_obj->isSameDeliveryOption($current);
```

Здесь `$this` — сохранённый вариант, а `$current` строится из checkout-сессии. При перекрёстно отсутствующих полях несколько разных карточек могут совпасть с текущим состоянием одновременно.

Ранее описанная связь с [Issue 66](issue-66-shipping-variant-id-dot-split.md) больше не актуальна: разбор `variant_id` с точками уже исправлен и проверен отдельно.

## Что подтверждено

### PHP 7.4

Несимметричность воспроизводится автономно на текущем классе:

- вариант без улицы → вариант с улицей: `true`;
- вариант с улицей → вариант без улицы: `false`.

Также в PHP 7.4 нельзя заменять текущую ветку простым нестрогим сравнением всех значений:

- `null == ''` → `true`;
- `null == 0` → `true`;
- `'01' == '1'` → `true`.

Такое исправление формально стало бы симметричным, но сохранило бы нежелательное приведение типов.

### Локальные данные

Read-only проверка `shop_order_params` показала:

- 77 заказов с `shipping_id` и `shipping_type_id`;
- у 34 из них отсутствует ключ `shipping_address.street`;
- у 27 отсутствует `shipping_address.zip`;
- у 11 улица сохранена как пустая строка.

В текущей локальной истории не найдено точной пары, которая уже сейчас схлопывается только из-за `null`: остальные сравниваемые параметры у таких заказов отличаются. Поэтому дефект подтверждён кодом и автономным воспроизведением, но не воспроизведён на существующей карточке в браузере. Тестовые заказы ради проверки не создавались и не изменялись.

## Важный контракт метода

Один метод сейчас обслуживает два сценария с разными источниками данных:

1. два сохранённых заказа при дедупликации;
2. сохранённый заказ и текущее состояние checkout при подсветке.

Эти источники гидратируются неодинаково. В частности, сохранённый заказ может содержать `shipping_custom`, а `getFillParamsByCheckoutParams()` сейчас его не устанавливает. Строгое симметричное сравнение не создаёт эту проблему — текущий код уже не считает массив равным `null` — но и не исправляет возможную ложную отрицательную подсветку для доставок с кастомными параметрами.

Issue 67 должна исправить только ложные положительные совпадения из-за `null`. Состав идентичности варианта доставки и правила сравнения `shipping_custom` не следует незаметно менять в рамках этого небольшого фикса.

Если потребуется корректная подсветка доставок с `shipping_custom`, для неё нужен отдельный анализ: либо гидратировать одинаковый набор данных из checkout и заказа, либо выделить отдельное сравнение текущего checkout по согласованному набору стабильных полей.

## Рекомендуемое решение

Сравнивать значения симметрично и явно разделить массивы и скаляры:

```php
private function areDeliveryValuesEqual($left, $right): bool
{
    if (is_array($left) || is_array($right)) {
        return is_array($left)
            && is_array($right)
            && $left == $right;
    }

    return (string) ($left ?? '') === (string) ($right ?? '');
}
```

В `isSameDeliveryOption()` каждую пару значений нужно проверять через этот метод:

```php
if (! $this->areDeliveryValuesEqual($this->$property, $other->$property)) {
    return false;
}
```

### Семантика нормализации

- `null` и непустое значение — разные значения в обоих направлениях;
- `null` и `''` — одно логически незаполненное скалярное поле;
- `0` и `null` — разные значения;
- строковые идентификаторы `'01'` и `'1'` — разные значения;
- два массива сравниваются по ключам и значениям без зависимости от порядка ключей;
- массив и `null` — разные значения.

Нормализация `null` и пустой строки нужна потому, что отсутствие ключа в старом заказе и сохранённое пустое поле описывают одно состояние: покупатель не указал значение. При этом пустота перестаёт быть wildcard и не совпадает с непустым адресом или идентификатором.

Не нужно применять `trim()`, менять регистр или нормализовать адресные строки: это расширит scope и может объединить значения, которые покупатель действительно вводил по-разному.

## Подводные камни и границы scope

1. **Частичный checkout.** После исправления неполное текущее состояние может не подсветить ни одной карточки. Это безопаснее, чем ложная подсветка одной или нескольких карточек.
2. **`shipping_custom`.** Из заказа и checkout сейчас получается разный набор данных. Это может давать ложное отрицательное совпадение, но не относится к `null`-wildcard и требует отдельного решения.
3. **`shipping_name`.** Поле нужно продолжить пропускать: это текстовое описание, которого нет в checkout и которое может измениться без изменения способа доставки.
4. **`shipping_plugin`.** Нельзя начинать учитывать или гидратировать его только ради этого фикса без отдельной проверки контракта.
5. **Массивы.** Недостаточно проверить только `is_array($left)`: проверка обязана быть симметричной и подтверждать, что массивами являются обе стороны.
6. **Нестрогое сравнение скаляров.** Простое `$left != $right` оставляет опасные правила PHP 7.4 для `null`, нуля и числовых строк.
7. **Производительность.** Дополнительный приватный метод вызывается для небольшого фиксированного списка полей и не создаёт значимой нагрузки или запросов к БД.

## Проверки для закрытия

Добавить автономный регрессионный тест для `shopPrefillPluginFillParams` со следующей матрицей:

1. `null` и непустое значение дают `false` в обоих направлениях;
2. `null` и `''` считаются одинаковой пустотой;
3. полностью одинаковые варианты дают `true`;
4. разные `street`, `zip`, `shipping_id`, `shipping_type_id` и `shipping_rate_id` дают `false`;
5. одинаковые массивы с разным порядком ключей дают `true`;
6. массив и `null` дают `false` в обоих направлениях;
7. для всей матрицы явно проверяется симметричность;
8. точные дубли в цикле дедупликации схлопываются с сохранением самого нового заказа;
9. старый вариант с отсутствующим полем не схлопывается с новым вариантом, где поле заполнено;
10. при частичном checkout не становятся активными несколько разных карточек.

Для браузерной проверки нужен контролируемый сценарий с двумя заказами одного пользователя: одинаковый способ доставки и совпадающие остальные поля, но у одного заказа сравниваемое поле отсутствует, а у другого заполнено. Создавать или менять такие тестовые данные без отдельного согласования не нужно.

## Критерии готовности

- сравнение симметрично для всех поддерживаемых значений;
- `null` больше не работает как wildcard;
- точные дубли по-прежнему схлопываются, сохраняется самый новый заказ;
- разные варианты не теряются из коллекции;
- подсветка не получает несколько ложных активных карточек;
- тест проходит на PHP 7.4;
- Issue 67 закрывается отдельным изменением без рефакторинга `shipping_custom` и без удаления `$active` — последнее остаётся в [Issue 71](issue-71-dead-code-in-release-archive.md).

## Что исправлено

- добавлен приватный метод `areDeliveryValuesEqual()` в `shopPrefillPluginFillParams`: скаляры сравниваются через `(string) ($left ?? '') === (string) ($right ?? '')`, массивы — только когда обе стороны являются массивами (`is_array($left) && is_array($right) && $left == $right`);
- `isSameDeliveryOption()` переведён на вызов этого метода для каждого сравниваемого поля вместо асимметричной ветки `$this_value !== null && $this_value != $other_value`;
- добавлен автономный регрессионный тест `tests/FillParamsSameDeliveryOptionTest.php` — матрица null/непустое, null/'', 0/null, '01'/'1', массивы с разным порядком ключей, массив/null, симметричность в обе стороны, симуляция цикла дедупликации и подсветки при частичном чекауте;
- `shipping_address_custom`, учёт `shipping_custom` и `shipping_plugin` не тронуты, scope не расширялся — как и было согласовано выше.
