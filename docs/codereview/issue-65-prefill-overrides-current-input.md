# Issue 65 — единица предзаполнения мельче связанной группы полей

**Статус:** ⬜ Открыта
**Приоритет:** 🟡 Средний
**Сложность фикса:** 🔧 Небольшой (расширить `SECTION_OWNERSHIP_FIELDS`), но нужен браузерный прогон
**Файлы:** `lib/classes/sections/shopPrefillPluginSectionChecker.class.php` (`SECTION_OWNERSHIP_FIELDS`), `lib/classes/checkout/shopPrefillCheckoutState.class.php` (`applyPrefillInput`)
**Смежные:** [issue-84](issue-84-prefill-inconsistent-across-groups.md) — та же связность, но между источниками и между секциями

>
> **Ревизия 0** утверждала: «на `/order/create/` страховок нет, покупатель правит поле и жмёт „Оформить“». Сценарий недостижим в стоковом checkout2 — разбор в «Страховке №3».
>
> **Ревизия 1** предлагала слияние по листьям (`fillGaps()`: предзаполнение только в пробелы). Отвергнута: она сшивает в одной связанной группе два источника — свой тип доставки с чужим вариантом, свою страну с чужим городом. Разбор в разделе «Почему нельзя и дозаполнять по листьям». Написанные под неё `shopPrefillPluginHelper::fillGaps()` и `tests/HelperFillGapsTest.php` удалены.
>
> Настоящий дефект — гранулярность решения: `canPrefillSection()` считает секцию ничьей по одному ключевому полю, хотя связанная группа шире. Направление слияния при этом менять не надо.

## Проблема

Предзаполнение — атомарная операция над **связанной группой полей**: либо вся группа из одного источника, либо ничего. Смысл имеет группа, а не отдельный лист.

| Группа | Поля | Что значит разорвать |
|---|---|---|
| `region` | `country`, `region`, `city`, `zip` | географическая иерархия: страна из одного места, область и город из другого |
| `details.shipping_address` | `street`, `building`, `apartment`, `podezd`, `floor`, `zip` | один адрес из двух разных адресов |
| `shipping` | `type_id`, `variant_id` | `variant_id` = `{shipping_id}.{rate_id}` и валиден только для своего типа |
| `payment` | `id`, `custom.*` | custom-поля принадлежат конкретному способу оплаты |
| `auth.data` | `firstname`, `lastname`, `middlename`, `email`, `phone` | имя одного человека, фамилия другого |
| `confirm` | `comment` | одно поле, разрывать нечего |

На **записи** плагин это соблюдает — `prepareRegionSectionParams()` и соседи собирают группу целиком из одного `shopPrefillPluginFillParams`. А на **решении** — нет: `canPrefillSection()` объявляет секцию ничьей по одному ключевому полю из `SECTION_OWNERSHIP_FIELDS`:

```php
'region'  => ['city', 'html'],
'details' => ['shipping_address.street', 'html'],
'auth'    => ['data.email', 'data.phone', 'data.firstname', 'html'],
```

Покупатель выбрал страну, но не ввёл город → `region` считается ничьей → в неё льётся вся четвёрка из прошлого заказа, и `deepMergeArrays` перебивает выбранную страну. Ввёл подъезд при самовывозе, где улицы нет по определению → `details` ничья → приезжает чужой адрес целиком.

Сейчас это заметно реже, чем звучит: `html` держит четыре секции свободного ввода занятыми с первого же рендера в браузере (страховка №2). Но опираться на служебный ключ ядра как на единственную защиту — не то же самое, что описать инвариант.

## Три страховки

### №1. Ядро пишет POST в сессию до `processAll()`

```php
// wa-apps/shop/lib/actions/frontend/order/shopFrontendOrder.actions.php:33-38
$session_checkout['order'] = $input;
wa()->getStorage()->set('shop/checkout', $session_checkout);
```

К моменту хука `checkout_before_auth` `canPrefillSection()` видит данные текущего POST. Страховка **посекционная** — внутри секции, признанной ничьей, она не помогает.

### №2. Служебный ключ `html`

Ядро кладёт `{section}[html]` в POST, когда просит вернуть HTML секции. Ключ входит в `SECTION_OWNERSHIP_FIELDS` для `auth`, `region`, `details`, `confirm` и держит их занятыми. См. [issue-59](issue-59-html-key-marks-section-filled.md).

Ограничение: `{section}[html]` отправляется не всегда — в `getData()` он добавляется под условием `!options.only_api && that.reload`. А `calculateAction()` заменяет `order` содержимым POST **целиком**, так что запрос без `html` снимает признак владения с секции.

### №3. JS не даёт POST'у на `create` разойтись с сессией

Именно она закрывает сценарий ревизии 0. [`wa-apps/shop/js/frontend/order/form.js:2843-2853`](../../../../js/frontend/order/form.js):

```js
var finish_form_data_json = JSON.stringify(that.scope.getFormData()),
    is_changed = ( start_form_data_json !== finish_form_data_json );

if (!is_changed) { promise = that.create(); }              // → /order/create/
else             { promise = that.scope.update({ render_errors: true }); }  // → /order/calculate/
```

`start_form_data_json` перезаписывается на каждом `ready`/`changed`, то есть после каждого рендера. Любое расхождение уводит клик в `calculate`, а не в `create`. Значит POST, доехавший до `createAction()`, равен последнему calculate-POST, который ядро уже положило в сессию, — и то, что `createAction()` сессию не пишет, само по себе ничего не ломает.

**Граница:** страховка живёт в JS темы. Кастомная тема, отправляющая форму прямо на `/order/create/`, её не даёт.

## Почему нельзя и дозаполнять по листьям

Напрашивающееся лекарство — писать предзаполнение только в пустые поля, оставляя ввод покупателя. Оно чинит перезапись и ломает связность:

- POST: `shipping[type_id] = ''`, `shipping[variant_id] = '33.courier'` (остался от прежнего выбора) → секция ничья → дозаполняем `type_id = 'pickup'` из прошлого заказа → тип самовывоз с курьерским вариантом;
- POST: `region[country] = 'kaz'`, город пуст → дозаполняем `region`, `city`, `zip` из российского заказа → Казахстан с областью 77;
- POST: подъезд свой, улица пуста → улица от одного адреса, подъезд от другого.

Плюс сторонние плагины. **cityselect** установлен на этой инсталляции и пишет прямо в сессию чекаута — [`shopCityselectHelper.class.php:155-172`](../../../cityselect/lib/classes/shopCityselectHelper.class.php):

```php
$input['country'] = $country;  $input['region'] = $region;
$input['city']    = $city;     $input['zip']    = $zip;
$data['order']['region'] = $input;
$details['shipping_address']['zip'] = $zip;
```

Четвёрку он ставит **целиком** — связность держит сам. Сегодня конфликта нет: непустой `city` делает `region` занятой, и мы туда не пишем. При дозаполнении по листьям конфликт появился бы: геоопределение дало город без региона → его половина плюс наша половина.

Вывод: единица — группа. Оба направления слияния на уровне листа неверны, менять `deepMergeArrays` местами не надо.

## Рекомендация

### 1. Расширить `SECTION_OWNERSHIP_FIELDS` до всей секции

Владение = любое непустое поле секции, а не одно ключевое:

```php
'auth'     => ['data.email', 'data.phone', 'data.firstname', 'data.lastname', 'data.middlename', 'mode', 'html'],
'region'   => ['country', 'region', 'city', 'zip', 'html'],
'shipping' => ['type_id', 'variant_id'],
'details'  => ['shipping_address.street', 'shipping_address.building', 'shipping_address.apartment', 'shipping_address.zip', 'html'],
'payment'  => ['id', 'custom'],
'confirm'  => ['comment', 'html'],
```

`SECTION_DATA_FIELDS` не трогать: это ответ на другой вопрос («есть ли что показывать и восстанавливать»), и его расширение сломало бы дзен-режим и снапшот. Инвариант «DATA ⊆ OWNERSHIP» сохраняется, а вот «списки различаются ровно на `html`» перестаёт быть верным — блок 7 теста `SectionCheckerOwnershipVsDataTest` надо переписать с «различаются на html» на «DATA — подмножество OWNERSHIP», а блок 8 переприбить к новому списку.

**Кастомные поля адреса** (`podezd`, `floor` и прочие из настроек магазина) в статический список не вписать — они у каждого магазина свои. Варианты: считать владением любой непустой ключ внутри `details.shipping_address`, либо оставить статический список и принять, что владение по кастомному полю не определяется. Решать при фиксе; первый вариант честнее и ближе к смыслу «группа».

**Чем платим.** Владение станет срабатывать чаще, предзаполнение — реже. Главный кандидат на ложное владение: страна по умолчанию, которую форма подставляет сама. На практике разницы почти нет — `html` уже делает `region` занятой на том же самом первом `calculate`, — но проверить обязательно (сценарий 1 ниже).

### 2. Проверить `applyPrefillInput()`

Направление `deepMergeArrays` оставить: при атомарной группе источник у неё один, и слияние ничего не рвёт. Починить только флаг — сейчас он выставляется безусловно, хотя слияние могло ничего не изменить, и лог `Prefill applied in checkoutBeforeAuth` врёт:

```php
$before = $this->params['data']['input'];
$this->params['data']['input'] = shopPrefillPluginHelper::deepMergeArrays($before, $filled_order);
$this->is_prefilled = ($this->params['data']['input'] !== $before);
```

### 3. Дописать правило в [RULES.md](../concept/RULES.md)

**P1a. Единица предзаполнения — связанная группа полей, а не поле.** Группа заполняется целиком из одного источника или не заполняется вовсе; непустое поле в группе делает её собственностью покупателя.

### 4. Браузерный прогон

1. **Регресс предзаполнения.** Покупатель с историей → `/order/` → все секции предзаполнены как раньше. Это главный риск расширения списка.
2. **Смена страны.** Сменить страну, город не трогать → пересчёт → страна не откатывается.
3. **Самовывоз.** Прошлый заказ с «подъезд 5» → самовывоз, вписать «подъезд 2» → пересчёт → в поле «2», чужая улица не появилась.
4. **cityselect.** Определить город через плагин → пересчёт → город и регион остались его, наш прошлый адрес не подмешался.
5. **Регресс issue-59.** Стереть город → пересчёт → поле осталось пустым.
