## Проверка в коде 22.08.2026

Сквозной прогон по `form.js`, шагам checkout2 и коду плагина. Отменяет или переформулирует бо́льшую часть выводов ревизий 2-3.

### 1. `html` приходит в 100% реальных POST-ов — «Ограничение №2» недостижимо

Владение четырёх секций держится на служебном `html`, и вся issue исходила из того, что он приходит не всегда (`!options.only_api && that.reload`). Разобраны оба условия:

**`only_api: true`** встречается ровно в одном месте — [`Form.prototype.reload()`](../../../../js/frontend/order/form.js#L4325). У него единственный вызывающий: обработчик события `wa_auth_contact_logout` ([form.js:3625](../../../../js/frontend/order/form.js#L3625)). А это событие **никто не генерирует**: поиск по всему проекту, включая минифицированные файлы, legacy и шаблоны, даёт 8 упоминаний, и все до одного — подписки (`$document.on` / `.off`), ни одного `trigger`. Реальная кнопка выхода шлёт другое событие:

```js
// form.js:3610-3613 — "These code were used to update the block. Now used reload page"
that.$wrapper.on("click", ".js-logout-button", function () {
    $(document).trigger("wa_order_reload_start");   // ← не wa_auth_contact_logout
});
```

`wa_order_reload_start` ведёт к `location.reload()` — полной перезагрузке, а не к AJAX-пути с `only_api`. **`Form.prototype.reload()` — мёртвый код.**

**`that.reload == false`** — тупик: флаг инициализируется `true`, сбрасывается только внутри `Section.prototype.update(data)` и тут же возвращается в `true` через `.always()`. А когда поле не влияет на тариф, `update()` вообще не вызывается — POST не уходит:

```js
// form.js:52-66
reload = !!$field.data("affects-rate") || !!$field.data("reload");
if (reload) { that.update({ reload: true }); }   // ← else-ветки нет
```

Проверен и сам плагин: `ZenModeToggle` зовёт `waOrder.form.update()` (все секции полные), `ParamsChoiceManager` — `location.reload()`. Html-less POST плагин не создаёт.

**Вывод:** случая «запрос без `html`» не существует. Сценарий issue-65 в текущем ядре недостижим, страховка №2 работает всегда.

**Оговорка:** это свойство **текущей** версии Webasyst. Событие в ядре объявлено, слушатели живы — в любом обновлении его могут начать генерировать. Инвариант P1 держится на том, что ядро сегодня не зовёт свой же код.

### 2. Все шесть секций отправляют `html`

Вопреки формулировке в комментарии к `SECTION_OWNERSHIP_FIELDS` («`html` стоит ровно у четырёх секций… и отсутствует у двух»), браузер шлёт его у **всех шести**, включая `shipping[html]` ([form.js:1854, 1860, 1873](../../../../js/frontend/order/form.js#L1854)) и `payment[html]` ([2643, 2649, 2662](../../../../js/frontend/order/form.js#L2643)). Различаются не отправка, а **наши списки владения**. Почему они различаются — пункт 4.

### 3. Полный список событий, вымывающих секцию из сессии

Секция теряет значения, когда она `clean`: в этой ветке `getData()` кладёт **только `[html]`, без полей**. Мест, задающих `clean`, во всём `form.js` ровно два:

| Где | Событие | Что теряется |
|---|---|---|
| [form.js:3603](../../../../js/frontend/order/form.js#L3603) | `region_change` | `shipping` **и** `payment` |
| [form.js:2010](../../../../js/frontend/order/form.js#L2010) | смена способа доставки | `payment` |

Плюс третий путь другой природы — короткое замыкание по ошибке валидации (секции ниже упавшего шага рендерятся пустыми, следующий POST обеднён).

Существенное: `region_change` триггерит не только ядро, но и **cityselect** ([frontend.js:640](../../../cityselect/js/frontend.js#L640)) — то есть выбор города через него тоже вымывает доставку и оплату.

`fast_render` в этот список **не входит**: ядро закрывает его само ветвью `use_session_input` в [`calculateAction()`](../../../../lib/actions/frontend/order/shopFrontendOrder.actions.php#L19-L32), которая берёт вход из сессии и сессию не перезаписывает.

### 4. Владение гейтит и восстановление из снапшота — отсюда асимметрия списков

В `applyPrefill()` снапшот применяется **только к секциям, прошедшим `canPrefillSection()`**:

```php
foreach (self::SECTIONS as $section_id) {
    if ($checker->canPrefillSection($section_id, $checkout_params)) { $available[] = $section_id; }
}
foreach ($available as $section_id) {
    $snapshot_section = $this->getSnapshotSection($section_id, $snapshot, $checker);   // ← только available
```

Отсюда следует всё остальное:

- у `shipping` и `payment` в списке владения намеренно **нет** `html`, хотя браузер его шлёт: добавь — и секции станут занятыми с первого рендера, а снапшот **никогда** их не восстановит. Ровно те две секции, ради которых он и существует (пункт 3);
- их содержательные поля `type_id` и `id` — это и есть механизм, разрешающий восстановление: пусто → можно вернуть.

**Главный вывод: содержательные поля в `SECTION_OWNERSHIP_FIELDS` — артефакт снапшота, а не предзаполнения.** Без восстановления список схлопывается до `['html']` у всех шести секций.

### 5. Единственный потребитель снапшота — Zen Mode, и то косвенно

Снапшот читают только `SessionStorageProvider` (путь предзаполнения) и `Debug` (показ). `ZenMode` берёт `getCheckoutParams()` — сессию, не снапшот ([shopPrefillPluginZenMode.class.php:195](../../lib/classes/zenmode/shopPrefillPluginZenMode.class.php#L195)).

То есть снапшот **не защищает данные покупателя от ядра** — он держит сессию полной, чтобы по ней корректно считался вердикт сворачивания. Для самого предзаполнения он не нужен: браузер дошлёт значения следующим полным POST-ом, они остались в DOM. Для создания заказа тоже — `createAction()` работает с POST.

### 6. Отменённые «дефекты» ревизии 3

- **`payment.id` при единственном способе оплаты — не дефект.** [Авто-выбор](../../../../lib/classes/checkout2/shopCheckoutPaymentStep.class.php#L117) срабатывает только при `1 == count($methods)`, и тогда этот способ — единственный правильный ответ; то, что мы не предзаполняем, ничего не стоит. При двух и более авто-выбора нет, `payment.id` пуст, предзаполнение работает штатно.
- **`region.country` — не дефект.** Его нет в списке владения, он никогда ничего не блокирует. На первой отрисовке хук срабатывает **до** `RegionStep::prepare()`, где подставляется дефолт. Случай 3 — аргумент **против** запланированного расширения списка, а не дефект текущего кода.
- **Куки cityselect и каталог — формулировка была преувеличена.** `cityselect__*` задают отображаемый город, блок региона в чекауте, контент-переменные и редирект между витринами (`detectRedirect`). На цены и остатки они влияют только вместе с плагином `regions`, которого на этой инсталляции **нет**.

Остаётся в силе один: **`details.zip` против cityselect** — владение `details` меряется по `street`, cityselect кладёт `zip` и в `region`, и в `details.shipping_address.zip`; при пустой улице наш исторический `zip` перекрывает его, потому что `deepMergeArrays($checkout_params, $final_params)` отдаёт победу второму аргументу. Впрочем, при принятом решении «предзаполнение перекрывает cityselect» это перестаёт быть дефектом.

### 7. Продуктовое решение, меняющее постановку

Зафиксировано 22.08.2026: **плагин предзаполняет только при входе на страницу чекаута либо по явной просьбе покупателя** — и ничего не пишет, пока покупатель взаимодействует с формой.

Под этим принципом снапшот противоречит правилу буквально: восстановление это `deepMergeArrays` + `setCheckoutParams`, то есть запись в состояние чекаута во время взаимодействия (сменил город → дописали доставку и оплату).

Также решено: предзаполнение из истории заказов должно **перекрывать** автоопределение города cityselect — оно врёт при VPN, прошлый заказ покупателя достовернее.

## Проблема

> **Поправка ревизии 4:** раздел описывает механику верно, но сам сценарий в текущем ядре недостижим — см. пункт 1 выше.

Предзаполнение — атомарная операция над **связанной группой полей**: либо вся группа из одного источника, либо ничего. Смысл имеет группа, а не отдельный лист.

| Группа | Поля | Что значит разорвать |
|---|---|---|
| `region` | `country`, `region`, `city`, `zip` | географическая иерархия: страна из одного места, область и город из другого |
| `details.shipping_address` | `street`, `building`, `apartment`, `podezd`, `floor`, `zip` | один адрес из двух разных адресов |
| `shipping` | `type_id`, `variant_id` | `variant_id` = `{shipping_id}.{rate_id}` и валиден только для своего типа |
| `payment` | `id`, `custom.*` | custom-поля принадлежат конкретному способу оплаты |
| `auth.data` | `firstname`, `lastname`, `middlename`, `email`, `phone` | имя одного человека, фамилия другого |
| `confirm` | `comment` | одно поле, разрывать нечего |

На **записи** плагин это соблюдает — `prepareRegionSectionParams()` и соседи собирают группу целиком из одного `shopPrefillPluginFillParams`. А на **решении** — нет: `canPrefillSection()` объявляет секцию ничьей по одному ключевому полю из `SECTION_OWNERSHIP_FIELDS`:

```php
'region'  => ['city', 'html'],
'details' => ['shipping_address.street', 'html'],
'auth'    => ['data.email', 'data.phone', 'data.firstname', 'html'],
```

Покупатель выбрал страну, но не ввёл город → `region` считается ничьей → в неё льётся вся четвёрка из прошлого заказа, и `deepMergeArrays` перебивает выбранную страну. Ввёл подъезд при самовывозе, где улицы нет по определению → `details` ничья → приезжает чужой адрес целиком.

Сейчас это заметно реже, чем звучит: `html` держит четыре секции свободного ввода занятыми с первого же рендера в браузере (страховка №2). Но опираться на служебный ключ ядра как на единственную защиту — не то же самое, что описать инвариант.

## Три страховки

### №1. Ядро пишет POST в сессию до `processAll()`

```php
// wa-apps/shop/lib/actions/frontend/order/shopFrontendOrder.actions.php:33-38
$session_checkout['order'] = $input;
wa()->getStorage()->set('shop/checkout', $session_checkout);
```

К моменту хука `checkout_before_auth` `canPrefillSection()` видит данные текущего POST. Страховка **посекционная** — внутри секции, признанной ничьей, она не помогает.

### №2. Служебный ключ `html`

Ядро кладёт `{section}[html]` в POST, когда просит вернуть HTML секции. Ключ входит в `SECTION_OWNERSHIP_FIELDS` для `auth`, `region`, `details`, `confirm` и держит их занятыми. См. [issue-59](issue-59-html-key-marks-section-filled.md).

Ограничение: `{section}[html]` отправляется не всегда — в `getData()` он добавляется под условием `!options.only_api && that.reload`. А `calculateAction()` заменяет `order` содержимым POST **целиком**, так что запрос без `html` снимает признак владения с секции.

> **Поправка ревизии 4, 22.08.2026.** Это ограничение **теоретическое**: оба условия недостижимы в текущем ядре. `only_api: true` бывает только в `Form.prototype.reload()`, который никто не вызывает (событие `wa_auth_contact_logout` не генерируется нигде в проекте), а при `that.reload == false` POST вообще не уходит. Разбор — в пункте 1 раздела «Проверка в коде 22.08.2026». Именно на этом ограничении стояла вся issue-65.

### №3. JS не даёт POST'у на `create` разойтись с сессией

Именно она закрывает сценарий ревизии 0. [`wa-apps/shop/js/frontend/order/form.js:2843-2853`](../../../../js/frontend/order/form.js):

```js
var finish_form_data_json = JSON.stringify(that.scope.getFormData()),
    is_changed = ( start_form_data_json !== finish_form_data_json );

if (!is_changed) { promise = that.create(); }              // → /order/create/
else             { promise = that.scope.update({ render_errors: true }); }  // → /order/calculate/
```

`start_form_data_json` перезаписывается на каждом `ready`/`changed`, то есть после каждого рендера. Любое расхождение уводит клик в `calculate`, а не в `create`. Значит POST, доехавший до `createAction()`, равен последнему calculate-POST, который ядро уже положило в сессию, — и то, что `createAction()` сессию не пишет, само по себе ничего не ломает.

**Граница.** Неточность предыдущей редакции: `form.js` — не тема, а ядро. Файл лежит в `wa-apps/shop/js/frontend/order/form.js`, подключается через core-экшен `FrontendOrderForm` (`wa-apps/shop/templates/actions/frontend/FrontendOrderForm.html`) и классы checkout2 (`shopCheckoutConfig`, `shopCheckoutStep`) — ни в одном `wa-apps/shop/themes/*/` его нет, и тема физически не может его «заменить». Тема вызывает стандартный чекаут фреймворковым хелпером (`{$wa->shop->checkout()->cart(...)}` в своём `order.html`) — и тогда страховка на месте автоматически, — либо вообще не подключает этот путь и постит форму мимо него собственным кодом. Второе не гипотетично: в `cityselect` уже есть готовая ветка под план-плагин «Заказ в 1 шаг» — [`shopCityselectPluginFrontendSetCity.controller.php:143`](../../../cityselect/lib/actions/shopCityselectPluginFrontendSetCity.controller.php), `$params['plugin'] == 'buy1step'` — такие плагины типично уходят в `/order/create/` одним POST в обход calculate-цикла. `buy1step` в этой инсталляции не установлен, но класс риска реальный: не «кастомная тема», а любой альтернативный путь оформления, не проходящий через `form.js`.

### Снапшот не переживает сессию — но форму восстанавливает ядро из localStorage

Снапшот плагина смерть сессии действительно не переживает: `shop/checkout`, `shop/prefill_snapshot` и `shop/prefill_source` лежат в одном `waSessionStorage` (`wa-system/storage/waSessionStorage.class.php` — нативная PHP-сессия) и умирают вместе. Персистентный `shopCart` (БД) хранит позиции корзины, а не секции формы. Так что «снапшот пережил сессию и вернул данные без `html`» — невозможно.

**Но у ядра есть собственное восстановление, и плагин о нём не знает.** [`form.js:4405-4448`](../../../../js/frontend/order/form.js) — состояние формы пишется в `localStorage` под ключом `webasyst/shop/order/form`:

```js
function save(form_data) { window.localStorage.setItem(storage_name, JSON.stringify(form_data)); }
function load()          { /* ... */ that.update({ data: form_data }).then(); }
```

Асимметрия важна: `save` вызывается **безусловно** после каждого пересчёта ([строка 4140](../../../../js/frontend/order/form.js), в `.always()`), а `load` — только под флагом `use_storage`, и флаг включается **ровно тогда, когда сессия мертва** ([`FrontendOrderForm.html:246`](../../../../templates/actions/frontend/FrontendOrderForm.html)):

```smarty
use_storage: {if $session_is_alive}false{else}true{/if},
```

`$session_is_alive` — это [`shopCheckoutViewHelper.class.php:439`](../../../../lib/classes/checkout2/shopCheckoutViewHelper.class.php#L439): `!empty($session_checkout['order'])`.

**Плагин это не подавляет** — и это надо было проверить, потому что мы пишем ровно в `$session_checkout['order']`. В `formVars()` переменная `$session_checkout` читается из хранилища **до** `processAll()`, внутри которого срабатывает наш хук, а `session_is_alive` вычисляется из этой ранее снятой копии. То есть флаг отражает состояние сессии **до** предзаполнения, и наша запись восстановление из localStorage не отключает.

Практическая разница TTL делает случай частым, а не экзотическим: `session.gc_maxlifetime = 1440` (24 минуты) против `COOKIE_TTL = 365 * 86400` у гостевого токена (`shopPrefillPluginGuestTokenStorage`). Покупатель, отошедший от формы на полчаса, возвращается с мёртвой сессией и живой кукой — то есть в случай 11 (см. ниже).

Реальное расхождение `html` и поля возникает не от смерти сессии, а внутри **живой** сессии — см. следующий раздел.

## Почему нельзя и дозаполнять по листьям

Напрашивающееся лекарство — писать предзаполнение только в пустые поля, оставляя ввод покупателя. Оно чинит перезапись и ломает связность:

- POST: `shipping[type_id] = ''`, `shipping[variant_id] = '33.courier'` (остался от прежнего выбора) → секция ничья → дозаполняем `type_id = 'pickup'` из прошлого заказа → тип самовывоз с курьерским вариантом;
- POST: `region[country] = 'kaz'`, город пуст → дозаполняем `region`, `city`, `zip` из российского заказа → Казахстан с областью 77;
- POST: подъезд свой, улица пуста → улица от одного адреса, подъезд от другого.

Плюс сторонние плагины. **cityselect** установлен на этой инсталляции и пишет прямо в сессию чекаута — [`shopCityselectHelper.class.php:155-172`](../../../cityselect/lib/classes/shopCityselectHelper.class.php):

```php
$input['country'] = $country;  $input['region'] = $region;
$input['city']    = $city;     $input['zip']    = $zip;
$data['order']['region'] = $input;
$details['shipping_address']['zip'] = $zip;
```

Четвёрку он ставит **целиком** — связность держит сам. Сегодня конфликта нет: непустой `city` делает `region` занятой, и мы туда не пишем. При дозаполнении по листьям конфликт появился бы: геоопределение дало город без региона → его половина плюс наша половина.

Вывод: единица — группа. Оба направления слияния на уровне листа неверны, менять `deepMergeArrays` местами не надо.

## Почему нельзя опираться только на один сигнал (html либо поле)

Напрашивается и обратное упрощение — раз `html` и так держит четыре секции занятыми с первого рендера (Страховка №2), не проще ли отказаться от полей-маркеров (`city`, `street`...) и решать владение только по `html`? Нет — у сигналов разные слепые участки, один не покрывает другой.

- **Слепой участок `html`** уже задокументирован в Страховке №2: ключ не приходит на `only_api`-запросах и запросах без `reload`. Сегодня в этот пробел падает проверка по полю — секция всё ещё числится занятой, если поле (`city`, `street`...) непусто, даже когда `html` в конкретном POST не было. Убрать поле-маркер — не «упростить эквивалентно», а снять защиту именно с этих запросов: под ударом окажутся данные, которые покупатель только что отправил, а не абстрактный пробел где-то в будущем.
- **Слепой участок поля** — оно не отличает «покупатель ввёл» от «форма подставила по умолчанию» (разобрано ниже, «Ложное владение по системным дефолтам»). Здесь `html`, наоборот, надёжен: он маркирует «эту секцию уже показали покупателю», независимо от происхождения значения внутри.

Сигналы дополняют друг друга, а не конкурируют: `html` подстраховывает «секцию показали, но поля пустые», поле подстраховывает «`html` не пришёл, но данные реальные». Нужны оба — рекомендация ниже (п.1) их и не разделяет, просто расширяет список полей на всю группу.

## Ложное владение: непустое поле — не всегда выбор покупателя

Расширение списка владения на всю группу (Рекомендация №1) неявно предполагает «поле непусто ⇒ покупатель это выбрал». Для двух полей это не так — оба всплыли при подготовке фикса.

### Cityselect: пишет раньше и по другому поводу

`cityselect` не висит на `checkout_before_auth` — гонки хуков в одном запросе с prefill нет. Он пишет в `shop/checkout` из отдельных AJAX-контроллеров — `SetCityController`, `SaveAddressController` ([`shopCityselectHelper::setCity()`](../../../cityselect/lib/classes/shopCityselectHelper.class.php)) — которые срабатывают по явному действию покупателя («да, это мой город» либо выбор из автокомплита DaData), но **на любой странице сайта**, необязательно на чекауте, и в любой момент сессии, необязательно перед самим оформлением заказа.

Следствие: если покупатель хоть раз подтвердил город — обычно ради цен и наличия товара в каталоге, на главной или в карточке товара — до того, как дошёл до `/order/`, поле `region.city` в сессии занято этим значением. Дальше предзаполнение из **истории реальных заказов** для `region` не сработает уже никогда в этой сессии, даже если у покупателя есть точный адрес из прошлого заказа. Это не гонка «кто раньше в хуке», а конфликт по смыслу: cityselect считает «город для каталога» и «город для доставки» одним и тем же полем, а это не всегда так.

Чинить ослаблением проверки владения нельзя — сломается ровно тот кейс, ради которого проверка и задумана (см. выше про cityselect в разделе про дозаполнение по листьям: запись идёт атомарной четвёркой, расшивать её нельзя). Это осознанный компромисс, который стоит просто зафиксировать как есть, а не пытаться угадывать источник поля `city` внутри `canPrefillSection()`.

### Системные дефолты: country и payment.id

**`region.country`.** [`shopCheckoutRegionStep::prepare()`](../../../../lib/classes/checkout2/shopCheckoutRegionStep.class.php#L148-L150):

```php
if (empty($selected_values['country_id'])) {
    $selected_values['country_id'] = $this->getDefaultCountryID($countries_by_id);
}
```

`getDefaultCountryID()` ([строка 406-420](../../../../lib/classes/checkout2/shopCheckoutRegionStep.class.php#L406-L420)) читает `shopConfig::getGeneralSettings('country')` — настройку магазина «страна по умолчанию» — и подставляет её на **каждом** `prepare()`, если поле пусто. Значение уходит в рендер формы, оттуда эхом в следующий POST, оттуда в сессию (`calculateAction()` пишет POST целиком). Проверено в БД этой инсталляции:

```sql
SELECT value FROM wa_app_settings WHERE app_id='shop' AND name='country';  -- 'rus'
```

Дефолт реально задан — сценарий не гипотетичен.

**`payment.id`.** Тот же паттерн уже существует **сегодня**, без всякого фикса issue-65 — `'payment' => ['id']` уже в текущем `SECTION_OWNERSHIP_FIELDS`. [`shopCheckoutPaymentStep::prepare()`, строка 117](../../../../lib/classes/checkout2/shopCheckoutPaymentStep.class.php#L117):

```php
if (1 == count($methods) && !$selected_method_id) {
    $selected_method_id = array_keys($methods)[0];
}
```

Единственный активный способ оплаты подставляется автоматически. На магазинах с одним способом оплаты секция `payment`, вероятно, уже сейчас считается занятой с первого рендера — не подтверждено на этой инсталляции (таблицу со списком активных способов не нашёл), но код однозначен. У `shipping` аналогичного авто-выбора единственного варианта нет — там подстановки не найдено, эта секция чище.

**Чем это вредит.** Плоское «поле непусто ⇒ секция занята» для `country` и `payment.id` — конкретный вред, не абстрактный: гость без истории получает дефолт при первом рендере → секция помечается занятой → в процессе оформления он логинится или находится по телефону/email → его настоящий исторический адрес (возможно, другая страна) уже не может переписать секцию, потому что она навсегда занята значением, которое покупатель не выбирал. Разница с сегодняшним поведением проявляется именно в пробеле Страховки №2 (`html` не пришёл) — в обычном браузерном клик-сценарии `html` и дефолт обычно попадают в сессию одновременно, регресс на глаз не виден, но он есть.

**Направление фикса.** Не плоская проверка непустоты, а сравнение со значением по умолчанию: `country` считается занятым, только если он **и непуст, и отличается** от `shopConfig::getGeneralSettings('country')`. Совпадение со значением по умолчанию ничем не вредит — если оно случайно совпадёт с реальным выбором покупателя, перезапись тем же значением — no-op. Для `payment.id` нужна симметричная проверка на случай единственного активного способа оплаты. Это меняет форму фикса: `shopPrefillPluginSectionChecker` сейчас — чистый статический массив без внешних зависимостей, а тут понадобится доступ к настройкам магазина (или дефолты нужно прокидывать в конструктор/метод снаружи).

## Случаи предзаполнения

Стенд для проверки **любого** варианта логики: набор состояний, в которых плагин может застать чекаут. Вариант, который не даёт ожидаемого поведения хотя бы в одном случае, не годится. Случаи 1-3 в постановке задачи, остальные добавлены при разборе.

| № | Состояние | Ожидаемое поведение | Правило |
|---|---|---|---|
| 1 | **Сессия пуста, источник есть** — авторизованный либо гость с токеном, первый заход на `/order/` | Предзаполнить все разрешённые секции целиком | P3 |
| 2 | **Сессия пуста, источника нет** — гость без истории и без куки | Не писать **ничего**, не поднимать PHP-сессию | P5, [issue-53](issue-53-empty-prefill-writes-session.md) |
| 3 | **Только системные дефолты** — `region.country` от `getDefaultCountryID()`, `payment.id` при единственном способе оплаты | Считать секцию **свободной** и предзаполнить: покупатель ничего не выбирал | — (новое, см. «Ложное владение») |
| 4 | **Часть группы заполнил другой плагин** — cityselect положил `country`+`region`+`city`+`zip` (атомарно) либо геоопределение дало город без региона | Не трогать группу: запись сделана по явному действию покупателя | P1 |
| 5 | **Покупатель заполнил часть группы сам** — выбрал страну, город не ввёл | Не трогать группу целиком | P1, P1a |
| 6 | **Покупатель стёр значение** — очистил город/улицу/комментарий | Не возвращать стёртое | P2 |
| 7 | **Мы предзаполнили → покупатель отредактировал** — второй и последующие `calculate` | Не перезаписывать. **Это ядро issue-65** | P1 |
| 8 | **Мы предзаполнили → покупатель не трогал** — эхо-POST | Идемпотентность: повторная запись тех же значений безвредна, но лог не должен врать | п.2 рекомендации |
| 9 | **Короткое замыкание рендера** — ошибка валидации выше по цепочке либо `fast_render`, POST обеднён | Восстановить из снапшота, на каждом запросе, независимо от маркера | N1, N3 |
| 10 | **Запрос без `html`** — `only_api` либо `!reload` | Владение не должно теряться: страховка №2 здесь молчит | S2, Ограничение №2 |
| 11 | **Сессия умерла, форму восстанавливает ядро из localStorage** — `use_storage: true`, JS шлёт старое состояние формы в `calculate` | Разобрано ниже отдельно — самый неочевидный случай | — (новое) |
| 12 | **Сессия умерла, кука гостя жива** — `gc_maxlifetime` 24 мин против TTL куки 365 дней | Вести себя как случай 1: источник доступен, сессия чистая | P3 |
| 13 | **Смена источника посреди чекаута** — гость залогинился либо был найден по телефону/email | Спорно; сегодня не определено | [issue-84](issue-84-prefill-inconsistent-across-groups.md) |
| 14 | **Заказ создан** — `order_action.create` | Сбросить маркер источника и снапшот | — |
| 15 | **Согласия гостя нет или отозвано** | Не предзаполнять, ранее выданные связи удалить | P4, P6 |
| 16 | **Не витрина** — бэкенд, API, CLI, импорт | Ранний выход: сессии чекаута нет | P7, `isStorefrontRequest()` |

### Случай 11 подробно

Последовательность после смерти сессии (TTL 24 минуты — покупатель просто отошёл):

1. `GET /order/` → сессия пуста → `session_is_alive = false`;
2. внутри `processAll()` срабатывает наш хук → предзаполняем из **истории заказов** → форма рисуется заполненной;
3. в шаблон уходит `use_storage: true` (флаг посчитан из состояния **до** нашей записи);
4. JS на инициализации читает `localStorage` и шлёт `update({data: old_form_data})` → `POST /order/calculate/`;
5. ядро пишет этот POST в сессию **целиком** — наше предзаполнение затирается состоянием формы из прошлого визита;
6. наш хук срабатывает второй раз, уже на этом `calculate`.

Два следствия, которые надо учесть при выборе варианта:

- **Приоритет.** В шаге 5 побеждает localStorage, то есть **собственный незавершённый ввод покупателя** — и по P1 это правильнее нашей истории заказов. Плагин этому не мешает (проверено выше), но и не знает об этом: пользователь увидит короткую подмену «предзаполнено из истории → заменено на прошлый ввод». Возможен видимый скачок значений.
- **Третий источник в одной группе.** Если сохранённое в localStorage состояние заполнено **частично** (покупатель не дошёл до города), то в шаге 6 группа `region` придёт полупустой. Логика «непустое поле = занято» может признать её свободной по пустому листу и долить недостающее из истории — и в одной группе окажутся два источника: localStorage и прошлый заказ. Это ровно то, что запрещает P1a, только третьей стороной.

## Варианты другой логики

Все проблемы выше — следствие одного: плагин выводит **происхождение** значения из его **содержимого**. Вопрос «кто это положил: покупатель, мы, ядро, другой плагин?» подменён суррогатным «поле непустое?». Ниже — варианты, фиксирующие происхождение явно.

### Вариант 0. Текущий метод — как реализовано сейчас

Приведён для сравнения на равных: без него непонятно, что именно варианты 1-5 улучшают.

Механизм состоит из четырёх частей:

1. **Проверка владения по содержимому** — `canPrefillSection()` → `isSectionOwnedByCustomer()` → любое непустое поле из `SECTION_OWNERSHIP_FIELDS` (одно ключевое на секцию плюс `html`);
2. **Служебный ключ `html`** как маркер «покупатель секцию видел» (страховка №2);
3. **Снапшот** `shop/prefill_snapshot` — восстановление на каждом запросе, независимо от маркера (N3);
4. **Маркер источника** `shop/prefill_source` — гейтит только поход в БД, одна запись на всю сессию (P8).

**Ключевое свойство: у метода нет памяти о собственных действиях.** Владение заново выводится из содержимого на каждом запросе, поэтому его приходится угадывать. `html` — заимствованный у ядра костыль, который случайно кодирует нужный факт («секцию уже показывали»), и именно на нём держится сегодня бо́льшая часть корректности: убрать его или попасть в запрос без него (случай 10) — и случаи 5, 6, 7, 13 отказывают разом.

Собственные дефекты, не считая зависимости от `html`:

- **Случай 3, `payment`.** `'payment' => ['id']`, а ядро авто-подставляет единственный способ оплаты → секция считается занятой с первого рендера и не предзаполняется никогда.
- **Случай 4, `details.zip`.** Владение `details` меряется по `street`. cityselect кладёт `zip` не только в `region`, но и в `details.shipping_address.zip`. Если улица пуста, `details` признаётся свободной, и наш исторический `zip` перекрывает его: `deepMergeArrays($checkout_params, $final_params)` отдаёт победу второму аргументу — нашим данным. Итог: город и регион от cityselect, индекс из прошлого заказа — расщеплённая группа, ровно то, что запрещает P1a.
- **Случай 8.** `is_prefilled` выставляется безусловно, поэтому лог `Prefill applied in checkoutBeforeAuth` врёт, когда слияние ничего не изменило (см. рекомендацию №2).

Сильная сторона, которую нельзя потерять при замене: **случай 9**. Снапшот — единственная часть механизма, спроектированная под короткое замыкание конвейера шагов, и она работает. Любой вариант обязан её сохранить.

### Вариант 1. Флаг «секция уже предзаполнена»

`shop/prefill_done['region'] = <source_key>`: в секцию пишем не более одного раза за сессию на источник.

Опора — наблюдение о порядке: чтобы покупатель отредактировал поле, форму сначала должны были отрисовать, а значит предзаполнение там уже отработало. **Перезапись всегда происходит на втором и последующих проходах** (случай 7). Убираем второй проход — класс закрывается целиком, независимо от того, чем меряется владение.

Не новая сущность для плагина: `shop/prefill_source` (P8) делает то же самое с гранулярностью «вся сессия»; здесь — по секциям.

Главное следствие: **при этом варианте расширение `SECTION_OWNERSHIP_FIELDS` не нужно**. Случай 5 не наступает (секция уже предзаполнена на первой отрисовке, второй раз не пойдём), а значит не нужна и зависимость `SectionChecker` от настроек магазина, и не появляется ложное владение случая 3.

Дыры: случай 13 (смена источника разрешает новый проход поверх правок) — смягчается тем, чтобы при смене источника пускать только в секции, пустые по `SECTION_DATA_FIELDS`. Случай 11 обрабатывается корректно: в шаге 6 флаг уже стоит, localStorage не перебивается.

### Вариант 2. Сравнение с тем, что мы отдали браузеру

Храним значения, которые сами внедрили. Пришло равное отданному → эхо, не выбор; пришло другое → покупатель правил.

Это тот же приём, которым **ядро пользуется само** — `start_form_data_json` в страховке №3, только зеркально на сервере. Точно отвечает там, где содержимое врёт: отдали `rus`, получили `rus` → не выбор (случай 3); получили `kaz` → выбор (случай 5). Случай 4 обрабатывается верно побочно: города мы не отдавали, он появился → внешний ввод → не трогаем.

Цена: ещё одна структура в сессии рядом со снапшотом, семантически похожая, но отвечающая на другой вопрос — ровно тот тип коллизии, из которого выросла [issue-72](issue-72-snapshot-overwritten-by-empty-branch.md).

### Вариант 3. Не писать в сессию — предзаполнять только `$data['input']` текущего запроса

Предзаполнение как «наполнить первую отрисовку», а не «внедриться в состояние»; дальше состояние возит браузер, а POST в сессию пишет само ядро (страховка №1). Тогда P1 выполняется **структурно**, а не силами проверки.

Против — собственная архитектура: N1/N3 (снапшот существует именно потому, что состояние реально теряется, и он **пишет** сессию) и R2 (Zen Mode, кэш сводки, ParamsChoice читают состояние из `shop/checkout`; на первой отрисовке сессия окажется пустой → группы не свернутся, нарушение Z2). Это не фикс issue-65, а переписывание половины плагина.

### Вариант 4. Спросить браузер, что покупатель реально трогал

У плагина есть свой JS (`OrderFormManager`): помечать поля по `input`/`change`, слать `prefill_touched[]`. Точное происхождение, но корректность начинает зависеть от наличия JS (см. «Граница»), и на первой отрисовке сигнала нет. Годится как дополнительный сигнал, не как основной.

### Вариант 5. Продуктовый выход

Кнопка «заполнить как в прошлый раз» вместо молчаливого авто-предзаполнения: неоднозначности нет вообще, механика (force prefill, reset & refill) уже есть в дебаге. Меняет продукт, а не чинит логику — держать как запасной.

### Сравнение по случаям

Случаи 2, 12, 14, 15, 16 — гейты, срабатывающие до логики владения (нет источника, живая кука при мёртвой сессии, заказ создан, нет согласия, не витрина). Они одинаковы у всех вариантов и в матрицу не вошли. Различают остальные:

Плюс два собственных дефекта (`payment` в случае 3, `details.zip` в случае 4) и врущий лог. Не годится как целевой механизм, но его снапшот (случай 9) обязателен к сохранению.

**Отпадают.** V3 — фатально на случае 9: восстановление снапшота требует записи в сессию, а N1/N3 требуют, чтобы оно работало всегда. V4 — на случаях 4, 10, 11: во всех трёх значение появляется мимо нашего JS. V5 — на случае 1: убирает само авто-предзаполнение, то есть ценность плагина.

**Подходят V1 и V2.** Обе снимают зависимость от `html` (случай 10) и чинят P2 без него же (случай 6). V2 дополнительно закрывает 3 и 13, но платит второй структурой в сессии.

### Выбор варианта

Брать **V1, но хранить значения, а не булев флаг**.

V1 и V2 — одна сущность разной подробности: V1 помнит «что мы писали в эту секцию», V2 — «какие значения». То есть **V2 = V1 + значения**. Если сразу класть в `shop/prefill_done` не `true`, а записанные значения, то:

- логика стартует с семантики V1 — малый диф, закрывает 7 из 8 проблемных случаев V0;
- при появлении случая 13 семантика ужесточается до V2 сравнением значений — **без миграции формата и без второй структуры**, то есть без риска [issue-72](issue-72-snapshot-overwritten-by-empty-branch.md);
- объём сопоставим со снапшотом, который и так лежит в сессии.

Проверка содержимого (`SECTION_OWNERSHIP_FIELDS`) остаётся в обоих случаях — при V1 она несёт случай 4 и служит базой первого прохода. **Расширять её не нужно**, то есть рекомендация №1 ниже отменяется, и вопрос дефолтной страны не возникает.

Проверить до реализации: флаг не должен задевать восстановление из снапшота (N3, P8 — снапшот работает на каждом запросе) и не должен писаться для гостя без куки (P5, иначе `Set-Cookie: PHPSESSID` каждому боту).

### 1. Расширить `SECTION_OWNERSHIP_FIELDS` до всей секции

Владение = любое непустое поле секции, а не одно ключевое:

```php
'auth'     => ['data.email', 'data.phone', 'data.firstname', 'data.lastname', 'data.middlename', 'mode', 'html'],
'region'   => ['country', 'region', 'city', 'zip', 'html'],
'shipping' => ['type_id', 'variant_id'],
'details'  => ['shipping_address.street', 'shipping_address.building', 'shipping_address.apartment', 'shipping_address.zip', 'html'],
'payment'  => ['id', 'custom'],
'confirm'  => ['comment', 'html'],
```

`SECTION_DATA_FIELDS` не трогать: это ответ на другой вопрос («есть ли что показывать и восстанавливать»), и его расширение сломало бы дзен-режим и снапшот. Инвариант «DATA ⊆ OWNERSHIP» сохраняется, а вот «списки различаются ровно на `html`» перестаёт быть верным — блок 7 теста `SectionCheckerOwnershipVsDataTest` надо переписать с «различаются на html» на «DATA — подмножество OWNERSHIP», а блок 8 переприбить к новому списку.

**Кастомные поля адреса** (`podezd`, `floor` и прочие из настроек магазина) в статический список не вписать — они у каждого магазина свои. Варианты: считать владением любой непустой ключ внутри `details.shipping_address`, либо оставить статический список и принять, что владение по кастомному полю не определяется. Решать при фиксе; первый вариант честнее и ближе к смыслу «группа».

**Чем платим.** Владение станет срабатывать чаще, предзаполнение — реже. Для большинства полей это ожидаемо и безопасно. `country` и `payment.id` — особый случай: у обоих есть системный дефолт, который подставляется без участия покупателя и неотличим от реального выбора при плоской проверке «непусто» (разобрано в «Ложное владение: непустое поле — не всегда выбор покупателя» выше). Для этих двух полей нужна не плоская проверка непустоты, а сравнение со значением по умолчанию — см. направление фикса там же.

### 2. Проверить `applyPrefillInput()`

Направление `deepMergeArrays` оставить: при атомарной группе источник у неё один, и слияние ничего не рвёт. Починить только флаг — сейчас он выставляется безусловно, хотя слияние могло ничего не изменить, и лог `Prefill applied in checkoutBeforeAuth` врёт:

```php
$before = $this->params['data']['input'];
$this->params['data']['input'] = shopPrefillPluginHelper::deepMergeArrays($before, $filled_order);
$this->is_prefilled = ($this->params['data']['input'] !== $before);
```

### 3. Дописать правило в [RULES.md](../concept/RULES.md)

**P1a. Единица предзаполнения — связанная группа полей, а не поле.** Группа заполняется целиком из одного источника или не заполняется вовсе; непустое поле в группе делает её собственностью покупателя.

### 4. Браузерный прогон

1. **Регресс предзаполнения.** Покупатель с историей → `/order/` → все секции предзаполнены как раньше. Это главный риск расширения списка.
2. **Смена страны.** Сменить страну, город не трогать → пересчёт → страна не откатывается.
3. **Самовывоз.** Прошлый заказ с «подъезд 5» → самовывоз, вписать «подъезд 2» → пересчёт → в поле «2», чужая улица не появилась.
4. **cityselect.** Определить город через плагин → пересчёт → город и регион остались его, наш прошлый адрес не подмешался.
5. **Регресс issue-59.** Стереть город → пересчёт → поле осталось пустым.
6. **Дефолт страны против реальной истории.** Гость без истории заказов открывает `/order/` → видит дефолтную страну магазина (`rus`) → в процессе оформления логинится под контактом с реальными заказами в другой стране или городе → после логина подставляется настоящий адрес из истории, а не ранее показанный дефолт.
7. **Пробел `html` (Ограничение №2).** Обычный клик в браузере, скорее всего, не воспроизведёт разницу между `html` и полем-дефолтом — они попадают в сессию почти одновременно. Нужен отдельный `only_api`/не-`reload` запрос (curl, гостевая банка кук — см. CLAUDE.md) с `region[country]`, равным дефолту магазина, но без `region[html]` — убедиться, что секция всё ещё не считается ложно занятой.
