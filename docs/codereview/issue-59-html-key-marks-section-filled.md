**Статус:** ✅ Исправлено 19.08.2026 — константа разделена, автотест и браузерный блок пройдены
**Приоритет:** 🟠 Средний (функция тихо перестаёт работать)
**Файл:** `lib/classes/sections/shopPrefillPluginSectionChecker.class.php`
**Тесты:** `tests/SectionCheckerOwnershipVsDataTest.php` (117 проверок), браузерный блок в [TESTS.md](../TESTS.md)

> Рекомендация пересмотрена 19.08.2026: `html` убирать нельзя, он защищает ввод покупателя. Разбор — в разделе «Пересмотр» ниже, итог правки — в «Что сделано» в конце файла.

## Проблема

В списке ключевых полей, по которым секция признаётся заполненной, стоит `html`:

```php
private const SECTION_KEY_FIELDS = [
    'auth'     => ['data.email', 'data.phone', 'data.firstname', 'html'],
    'region'   => ['city', 'html'],
    'shipping' => ['type_id'],
    'details'  => ['shipping_address.street', 'html'],
    'payment'  => ['id'],
    'confirm'  => ['comment', 'html'],
];
```

`html` — не данные покупателя, а служебный флаг рендера: им фронтенд ядра просит вернуть HTML секции. `wa-apps/shop/js/frontend/order/form.js` кладёт его в каждый запрос:

```js
result.push({ name: "region[html]", value: "only" });   // 707, 713, 726
result.push({ name: "auth[html]",    value: 1 });        // 297, 310
// то же для shipping, details, payment, confirm
```

А `shopFrontendOrder.actions.php:33-38` пишет **весь POST** в сессию:

```php
$session_checkout['order'] = $input;
wa()->getStorage()->set('shop/checkout', $session_checkout);
```

Значит после **первого же** взаимодействия с формой в `$_SESSION['shop/checkout']['order']` лежат `auth.html`, `region.html`, `details.html`, `confirm.html`. `isSectionFilled()` возвращает `true`, если заполнено **любое** ключевое поле → эти четыре секции навсегда (до конца сессии) считаются заполненными.

## Последствия

- `canPrefillSection()` для `auth`, `region`, `details`, `confirm` = `false` → предзаполнение по ним не выполняется;
- `getSnapshotSection()` дополнительно вызывает `isSectionFilled($section_id, $snapshot)`. Снапшот — копия ранее смерженных checkout-параметров, то есть тоже с `html`. Секция считается «наполненной» по служебному флагу, и из снапшота может восстановиться блок, где реальных данных нет;
- по факту оба механизма надёжно работают только для `shipping` и `payment` — единственных секций без `html` в списке.

Сценарий: покупатель очистил email в секции auth → в сессии `auth = ['html' => 1, 'data' => ['email' => '']]` → `isSectionFilled('auth')` = `true` → восстановление из снапшота не срабатывает, хотя ровно для этого случая оно и написано.

## Пересмотр 19.08.2026: `html` стоит там намеренно

Первоначальная рекомендация («убрать `html` отовсюду») **неверна** и сломала бы заявленное поведение плагина. Разбор:

Сравним, у каких секций `html` есть, а у каких нет:

| Секция | Ключевые поля | Тип ввода | `html` |
|---|---|---|---|
| `auth` | email, phone, firstname | свободный текст | ✅ |
| `region` | city | свободный текст | ✅ |
| `details` | shipping_address.street | свободный текст | ✅ |
| `confirm` | comment | свободный текст | ✅ |
| `shipping` | type_id | выбор из вариантов | ❌ |
| `payment` | id | выбор из вариантов | ❌ |

Корреляция стопроцентная: `html` стоит ровно у тех четырёх секций, где покупатель вводит текст руками, и отсутствует у двух, где он выбирает из готовых вариантов.

Это реализация приоритета №1 из [CONCEPT.md](../concept/CONCEPT.md#приоритеты-источников-данных) — «Ручной ввод (checkout_params) → **не перезаписываем то, что пользователь ввёл**». Значение `html` в сессии = «браузер уже присылал эту секцию, покупатель держал её в руках» → секция его, руки прочь.

Что сломает удаление `html`:

- покупатель стирает город, чтобы ввести другой → на ближайшем `calculate` prefill видит пустой `city` и **возвращает старый**. Город невозможно очистить;
- то же с улицей в `details`;
- то же с комментарием к заказу — его нельзя будет удалить.

Из выбираемых секций (`shipping`, `payment`) значение нельзя «стереть», можно только переключить, — поэтому там `html` и не нужен.

## Настоящий дефект: одна константа на два разных вопроса

`SECTION_KEY_FIELDS` отвечает сразу на два вопроса, у которых разные правильные ответы:

| Вопрос | Кто спрашивает | Правильный ответ про `html` |
|---|---|---|
| «Можно ли сюда писать?» | `canPrefillSection()` | `html` = **нет**, секция принадлежит покупателю |
| «Есть ли тут данные?» | `getSnapshotSection()`, Zen Mode | `html` **не данные**, игнорировать |

Сейчас оба спрашивают один список, поэтому второй получает ложное «да».

## Рекомендация (исправленная)

1. Разделить константу на две:
   - `SECTION_OWNERSHIP_FIELDS` — как сейчас, **с `html`**; используется в `canPrefillSection()`. Не трогать.
   - `SECTION_DATA_FIELDS` — то же самое **без `html`**; отвечает только на «есть ли реальные данные».
2. Перевести на `SECTION_DATA_FIELDS`:
   - `getSnapshotSection()` — проверка «в снапшоте есть что восстанавливать»;
   - решение о сворачивании в Zen Mode (см. [баг zen-collapse](../bugs/zen-collapse-on-upstream-checkout-error.md)).
3. Проверить в браузере, что после правки город, улица и комментарий по-прежнему **очищаются** и не возвращаются сами.

Blast radius: `isSectionFilled()` и `canPrefillSection()` вызываются только из `shopPrefillPluginSessionStorageProvider` и debug-панели.

Сценарий из раздела «Последствия» («покупатель очистил email → восстановление не срабатывает») — **работает как задумано**: очистка осознанная, возвращать значение нельзя. Машинную потерю чинит снапшот, у которого своя проверка (N1 в [RULES.md](../concept/RULES.md)).

### Что проверяли на остаток

Гипотеза: секцию со свободным вводом опустошает не покупатель, а короткое замыкание конвейера — в POST остаётся `html` без данных, секция числится за покупателем, и снапшот её не чинит.

Проверено вживую 19.08.2026 на сценарии со сломанным email: комментарий к заказу и улица **пережили** короткое замыкание и вернулись после починки. Воспроизвести потерю не удалось — `confirm` и `region` рендерят свои данные в `prepare()`, а адрес ядро помнит само (`shopCheckoutDetailsStep` хранит `details_address` в своём storage).

Гипотеза остаётся теоретической. Если такой сценарий когда-нибудь найдётся — заводить отдельный баг, а не переоткрывать этот.
